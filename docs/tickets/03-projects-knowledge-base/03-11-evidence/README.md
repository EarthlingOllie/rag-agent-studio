## What was built

- **API.** `DELETE /api/organisations/{organisation_id}/projects/{project_id}` (`deleteProject`) with body `{"confirm_name": "<the Project's name>"}`. Owners only (`OwnerScope`: an Editor gets `403 "Only Owners can do this"`). Refused with `409 "Only an archived Project can be deleted. Archive it first."` for an active Project and `400 "Type the Project's name exactly to delete it."` unless `confirm_name` equals the name exactly (case and spaces count); a missing `confirm_name` is `422`. Another Organisation's or an unknown Project is `404 Not found`. On success it answers `202 Accepted` with no body and enqueues the cascade.
- **Cascade (Celery task `projects.delete`, `backend/app/projects/tasks.py`).** Takes the Project ID, the requesting Owner and the request time.
  1. In one transaction (`app.projects.service.delete_project`): locks the Project, records `project.deleted` and deletes the Project row; the foreign keys' `ON DELETE CASCADE` remove its Documents, staged editions, Chunks, Tags and Document Tags, Agents and Agent Drafts, and through the Agents their Conversations, Messages and message retrievals. The Project stops existing at once.
  2. Then it deletes every stored object under the Project's prefix `organisations/<org>/projects/<project>/` through the new object-store operation `ObjectStore.delete_prefix` (S3/RustFS: `ListObjectsV2` pages of up to 1,000 keys, each deleted with one `DeleteObjects`; in-memory fake: a key filter). That covers each Document's original and converted markdown, staged editions' files and uploads that were never confirmed. Upload keys are now built from the same `storage_prefix` helper, so nothing is stored outside it.
  - A Project restored between the request and the task is left alone (the task deletes only an archived Project), and running the task again for a deleted Project does nothing.
- **Audit Event** `project.deleted`: actor the Owner, target `project/<id>`, `before` = `{name, description, document_count, agent_count}`, `after` null, `occurred_at` the request time from the API's clock. It is written in the same transaction as the deletion, so it exists exactly when the Project is gone.
- **Studio.** On an archived Project's page, Owners get **Delete permanently** under Restore. It opens a form ("Delete <name> permanently") that explains what goes ("…removes its Documents, stored files, Agents and Conversations for good. This can't be undone."), with a "Type <name> to confirm" field; the red **Delete <name> permanently** button stays disabled until the field equals the name exactly. Cancel closes it and the form opens empty next time. A refusal shows the API's reason. On success the Project's cached data is dropped, the lists are refetched and the Studio goes to Projects, which says "<name> is being deleted permanently." (route search `?deleted=`). Editors and active Projects are not offered the button.

## Gaps and best guesses

- **No "deleting" state.** The API checks and enqueues; the Project row is deleted when the worker runs, not in the request. Until then (normally under a second) it still reads as archived, and a second request is accepted again (harmless: the task finds nothing). A `deleting_at` column would hide it at once but needs a migration, which would clash with the parallel tickets' migration chain; best guess: not worth it now. The Studio drops the Project from its cache at once and says it "is being deleted".
- **Audit Event at task time.** `project.deleted` is written by the task, atomically with the deletion, with the actor and time of the request, so a Project restored before the task runs leaves no false record. If the worker never runs, there is no event (and no deletion).
- **Retries.** The task has no automatic retry. If deleting stored objects fails after the rows are gone, the objects stay orphaned under a prefix nothing refers to; re-sending `projects.delete` would not reach them, because the Project is gone. Best guess: acceptable for this slice (03-05's `documents.delete_objects` has the same property); a later sweep could list prefixes with no Project.
- **Traces and tombstones.** Spec 07 (retention and tombstones) is not built yet. Conversations are removed with their Agents, as this ticket says; nothing outside the Project keeps Chunk IDs except `message_retrievals`, which go with their Messages.
- **Images built without PDF support and bundled models** (`WITH_PDF=false BUNDLE_MODELS=false`, `EMBEDDER=fake` in e2e), as for 03-05 and 03-07: this ticket changes no conversion or embedding code, and the shared disk can't hold the PyTorch image.
- **Seam confirmation.** The TDD skill asks to confirm seams with the user first; this run is unattended, so the spec's Testing Decisions and the shared test seams were taken as the agreed seams.
- **GitHub Actions is down**; the checks below are local, as the user authorised. No `infra/` file changed, so terraform checks don't apply.
