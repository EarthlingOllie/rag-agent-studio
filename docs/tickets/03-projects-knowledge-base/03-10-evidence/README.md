## Decisions and notes (best guesses recorded instead of asking)

- **Where the pending model lives.** The spec puts "a pending one while a re-embed runs" on the Project. It is the running `re_embed_jobs` row rather than two more Project columns: the job carries the progress and error too, and one running job per Project is enforced by a partial unique index. `ProjectOut` is unchanged (other tickets edit it in parallel); the state is its own route.
- **Choosing again while a job runs** cancels it (its rows deleted, `project.re_embed_cancelled`) instead of being refused, so a stuck or unwanted job can always be stopped: the active model again just cancels, the pending one again is a no-op, a third model starts a new job.
- **No re-chunking.** The spec says the job "walks every Ready Chunk" and writes new vectors alongside: Chunks keep their text and boundaries, sized for the model they were first ingested with. A new model with a smaller token limit than the old Chunks would truncate on the provider side; every registered model's limit is at least 512 tokens and `CHUNK_MAX_TOKENS` defaults to 256, so this doesn't arise with the defaults.
- **What gets embedded.** The headings-then-text string ingestion embeds was Docling's `contextualize`; it is now `embedding_text(heading_path, text)` in `app/documents/chunking.py`, used by both ingestion and the job, so a Chunk embeds identically under every model. For Docling's chunks this is the same string (the existing chunking test still asserts it); it would differ only if Docling attached captions to a chunk's metadata.
- **Progress counts** are rows, not Documents: pending-model rows of active-model rows, so uploads during the job raise both numbers.
- **Who the actor is.** Events the worker records (the switch, a failure) have no actor; the Member who chose is the actor of `project.re_embed_started`.
- **Batch size and retries.** 64 Chunks per batch (`RE_EMBED_BATCH_SIZE`); provider retries reuse ingestion's attempt and backoff settings rather than adding new ones.
- **Migration number.** Written as `0021_re_embed_jobs` on `0020_chunk_guardrail_flags` (candidate's head at `cb228e6`); renumbered to `0024_re_embed_jobs`, revising `0023_erase_organisation`, after candidate gained 08-04's `0021_message_guardrail_outcomes`, 02-06's `0022_theme_images` and 10-01's `0023_erase_organisation`. `alembic heads` shows the single head `0024_re_embed_jobs`.

## Gaps and sandbox notes

- **No live provider embeddings.** No real API keys exist here and paid calls aren't allowed, so provider models were exercised only through the model gateway's fakes (API, worker and e2e), as in 03-09. A re-embed against real Voyage/OpenAI/Bedrock is not evidenced.
- **Local model.** The e2e stack runs `EMBEDDER=fake` because the local model's files can't be downloaded through this sandbox's egress proxy (see 03-09's evidence), and `WITH_PDF=false BUNDLE_MODELS=false` for the images ([build.sh](build.sh) adds only the proxy CA). The deterministic hash embedder covers the local path.
- **Load.** Up to six tickets built at once on a 4-CPU machine (load average 10–15 during these runs); the backend suite took over half an hour.
