# Evidence: ticket 03-05, Dedupe, delete and replace edition

Branch `ticket/03-05-dedupe-delete-replace`, based on `origin/candidate` at `0a6a9e7` (03-02 merged). The claim commit, the first on the branch, set Status `in-progress`.

**Status: done.** All five criteria are met and evidenced below. Gaps and best-guess decisions are listed at the end.

## What was built

- **Dedupe.** Confirming an upload (`POST …/documents`) or a new edition (`POST …/documents/{id}/editions`) computes the SHA-256 and refuses a file whose content hash is already in the Project: a Document's current edition, or a staged edition still being ingested. A Failed Document or Failed staged edition doesn't count, so after "This Document couldn't be processed. Try uploading it again." the same file can be uploaded again, as a new Document or as the Failed Document's next edition. The answer is `409` with `UploadConflictResponse`: `detail` ("This file is already in the Project as handbook.md."), `document_id` and `document_name`. The refused copy's upload and stored file are discarded. Confirmations lock the Project row, so two confirmations of the same file can't both pass the check.
- **Delete.** `DELETE …/documents/{id}` (any Member, as for uploads; `409` on an archived Project). In one transaction it deletes the Document's Chunks, records the `document.deleted` Audit Event (actor, target `document`, `before` = Project ID, name and content hash) and deletes the Document (and its staged edition). After the commit it enqueues the `documents.delete_objects` Celery task with the stored objects: the original and the converted markdown of the current and of any staged edition.
- **Replace edition.** `POST …/documents/{id}/editions` with an upload ID (presign and PUT as for any upload) stages the file as a `StagedEdition` (new table `staged_editions`, migration `0012_staged_editions`) with edition `n+1`, Queued, and enqueues ingestion. The ingestion task claims the staged edition when the Document itself isn't Queued. It writes the new Chunks under edition `n+1` (nothing reads them: reads filter on `Document.edition`) and, **in the same transaction**, swaps: the Document takes the staged edition's number, name, type, size, hash and object key, the old edition's Chunks are deleted, and the staged row is removed. The Document keeps its ID and `created_at`, so its Tags (a link on the Document ID, arriving with 03-06) are kept. The old edition's stored files are then scheduled for deletion. A failed staged edition is marked Failed with its message and leaves the Document as it was; a later replacement overwrites it (and its file is deleted). Replacing is refused (`409`, "This Document is still being processed. Try again once it is Ready or Failed.") while the Document or a staged edition is Queued or Processing.
- **Deleted while processing.** If the Document is deleted while ingestion runs, ingestion writes nothing and schedules deletion of whatever it stored.
- **API shape.** `DocumentOut` and the polled `DocumentStatusOut` carry `replacement: {edition, name, status, error_message} | null`.
- **Studio** (Documents tab). An Actions column (hidden for an archived Project) with **New edition** (a file picker, labelled "New edition of <name>", shown only when nothing is processing) and **Delete** (an inline confirmation, "Delete <name>? It stops being retrieved at once."). The status cell shows "New edition 2 (<name>): Queued/Processing/Failed" and its error. The list keeps polling while a new edition is in progress and re-reads the list once it has been swapped in. Polled statuses older than the list (read before a later upload) are not merged, so they can't hide a just-queued edition. A duplicate upload's error carries a **Show <name>** link to the existing Document's row (`#document-<id>`, highlighted with `:target`).

## Test seams

As agreed by the spec's Testing Decisions and the shared test seams (ADR-0008):
- **API seam plus task seam** (`backend/tests/integration/test_document_editions.py`): the API drives presign, PUT to the in-memory store, confirm/replace/delete; ingestion runs eagerly through the fake converter and deterministic embedder. Outcomes are read back through the API (Document list, status endpoint, Chunk list, Audit Events). Two facts have no API surface and are read directly, as the seams allow: whether a deleted Document's Chunk rows are gone (its Chunk list is a 404 either way) and what the object store holds.
- "Old Chunks serve until the swap" is observed **while** the new edition is Processing: `GatedConverter` (the fake converter held at the start of a conversion by a `threading.Event`) pauses ingestion, the test reads the API, then releases it.
- **Cross-tenant and role suite** (`test_tenant_isolation.py`): both new routes are listed, so another Organisation's Member gets 404 and Editors are allowed.
- **Network seam** (`frontend/apps/studio/src/projects/DocumentsTab.test.tsx`): MSW stand-in for the Documents API, extended with duplicate detection by content, the editions route, the delete route and edition progress on each status poll.
- **End-to-end seam** (`frontend/e2e/tests/document-editions.spec.ts`): Playwright with axe against the compose stack.

## Gaps and best guesses

- **`make image-scan` secret hits (pre-existing).** Trivy's secret scanner flags docstrings in the `anthropic` SDK installed in the API image. This branch changes no dependency, Dockerfile or Makefile line, so candidate has the same result; the vulnerability scan is clean. Best guess for a follow-up (outside this ticket, to avoid clashing with parallel tickets): `--scanners vuln` in `image-scan`, or a `.trivyignore` for those paths, since gitleaks covers secrets in the repository.
- **`make secret-scan` on a clone with every branch.** gitleaks scans all refs, so the finding on the unmerged `ticket/03-09` branch fails it in any full clone; that ticket needs to allowlist its fixture. This branch's own history is clean.
- **Images built without PDF support and bundled models** (`WITH_PDF=false BUNDLE_MODELS=false`), with `EMBEDDER=fake` in e2e, as for 03-02: this ticket changes no conversion or embedding code, and the disk shared by four parallel tickets can't hold the PyTorch image.
- **Tags (criterion 3).** No Tag model exists on this branch (03-06 runs in parallel). The swap keeps the Document row and its ID, and the spec models Tags as a many-to-many link to Documents, so Tags are kept by construction. Best guess: 03-06 adds a test that Tags survive a replacement once both are merged; nothing here needs to change.
- **"Link to the existing Document".** There is no Document page yet (the viewer is 03-03, in parallel). The link goes to the Document's row in the Documents tab (`#document-<id>`), and the API returns `document_id`, so 03-03 can point the link at the viewer.
- **Retries of the deletion task.** `documents.delete_objects` has no automatic retry; deleting a missing object isn't an error, so re-running it is safe. Retries with backoff for transient errors are 03-04's subject.
- **A refused (busy) replacement's upload** stays pending until its URL expires, so the same upload can be confirmed once the Document is Ready. Unconfirmed uploads expiring in storage is not handled by this ticket (nor by 03-02).
- **Delete is open to any Member** (Editor and Owner), like upload, as the user story says "As an Editor".
