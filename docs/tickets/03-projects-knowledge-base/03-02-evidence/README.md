# Evidence: ticket 03-02, Upload a Document to Ready

Branch `ticket/03-02-upload-document-ready`, based on `origin/candidate` at `c8c68ba` (03-01, 02-01 and 02-05 merged). The claim commit `35b16d2`, the first on the branch, set Status `in-progress`. The code is at `b0e206b`. The commit after it only adds this folder and the ticket status.

All logs come from a fresh `git clone` of the branch from GitHub (`clean0302`), with these exceptions:
- `mutation-proof.log` ran in the branch worktree.
- `backend-tests.log`, `lint.log`, `client-drift.log`, `install.log` and `studio-build.log` ran at `b0e206b`.
- `frontend-tests.log` and `e2e.log` ran at `97718d3`. The only later commit, `b0e206b`, adds one backend test and changes no frontend file or API.

Each log starts with its command and ends with its exit code.

**Test services.** Postgres+pgvector, Redis, RustFS and Mailpit come from this ticket's own compose project `rag0302`, with host ports moved ([compose.sandbox.yml](compose.sandbox.yml): Postgres `45732`, Redis `46679`, RustFS `49300`, Mailpit `48325`). The clone's backend tests use database `studio_test_c0302` and Redis DB 13. The worktree uses `studio_test` and DB 15.

**Seams under test.** These come from spec 03's testing decisions and the shared test seams. There was no one to confirm them with, so this is the recorded choice.
- **API seam plus task seam.** Upload is driven through the API in three steps: presign, then a PUT, then confirm. The PUT goes to the in-memory object store in most tests, and to real RustFS in `test_object_store.py`. Celery runs ingestion eagerly, through the fake converter and the deterministic hash embedder.
  - Outcomes are observed through the API: the Document list, the status endpoint, the Chunk list and the Project's `document_count`.
  - Failures come from configuring the fake converter to raise.
- **Storage facts with no API surface yet.** These are the vector, its dimension, the `tsvector` and the indexes. `test_chunk_storage.py` reads them from the table, which the shared seams allow until retrieval exists (spec 04).
- **Converter-plus-chunker seam.** `tests/unit/test_chunking.py` chunks real Docling output that was recorded and committed. It doesn't run Docling.
- **Adapters.** These tests run real code against real dependencies:
  - The S3 adapter against RustFS.
  - The Docling adapter on Markdown and DOCX. Neither needs models, so this runs in the gate.
  - The ports factory.
- **Live suite** (`tests/live`, marker `live`). Real Docling on the sample PDF, DOCX and PPTX, and the local Embedding Model.
- **Network seam.** The Documents tab is tested with Testing Library and MSW, with handlers typed by the generated client. The fake object store is reached at `/studio-documents` on the page's origin, the same as in the stack.
- **End-to-end seam.** Playwright runs against the stack, with axe.

## Decisions and notes (best guesses recorded instead of asking)

- **Docling package.** The core dependency is `docling-slim` with the Markdown, HTML, DOCX, PPTX and chunking extras. These need no PyTorch and no models, so the gate runs real Docling on Markdown and DOCX.
  - PDF needs layout models. They live in a `pdf` dependency group (`docling-slim[format-pdf,models-local]`, plus `torch` and `torchvision` from the PyTorch CPU index), which `uv.lock` locks.
  - The backend Dockerfile installs the group with `WITH_PDF=true` (the default), and downloads the models at build with `BUNDLE_MODELS=true` (the default). Compose passes both through as build arguments.
- **Pending uploads** are kept in Redis with the presigned URL's lifetime, not in a table. Each is keyed by Project and upload ID, so another Project's confirm finds nothing (409).
- **Content hash.** The API always computes it from the stored bytes. The browser may send one to be checked, but the Studio doesn't compute one today. Duplicate detection is ticket 03-05; the hash is indexed for it.
- **Failures.** One readable message is used for any ingestion failure. Categories, retry and backoff are ticket 03-04.
- **Guardrail scan.** The injection scan hook is ticket 03-07, so Chunks have no flag columns yet.
- **Status values.** The API uses lowercase (`queued`, `processing`, `ready`, `failed`), and the Studio shows the glossary's capitalised names.
- **Chunk-size setting.** `CHUNK_MAX_TOKENS` defaults to 256 and is capped at the model's 512. What gets embedded is the Chunk with its headings (`HybridChunker.contextualize`). What is stored is the Chunk text and its `heading_path`.
- **Edition.** Every Document starts at edition 1. Replacing an edition is ticket 03-05.
- **Same-origin uploads.** Locally, presigned URLs are signed for the Studio's address, and Vite proxies `/studio-documents` to RustFS. This avoids configuring CORS on RustFS. In AWS, S3 presigned URLs and CloudFront are spec 09's concern.
- **Single Document read.** No `GET …/documents/{id}` route was added. The list, the statuses and the Chunks were enough for this ticket. The Document viewer (03-03) adds what it needs.
- **`TRANSFORMERS_VERBOSITY=error`** is set in `app/__init__.py`. Docling's chunker imports transformers, which only tokenizes here, and otherwise prints a non-JSON advisory about PyTorch. That would break the "only JSON log lines" tests.
- **Migration number.** `0008_documents` follows `0007_provider_credentials`, the head on candidate. A parallel ticket's migration merged first would need its `down_revision` re-pointed.

## Gaps and sandbox notes (local and test-double routes used)

- **No Hugging Face access.** The egress proxy answers `403 Forbidden` for huggingface.co. So the local `multilingual-e5-small` model and its tokenizer couldn't be downloaded, and:
  - the live embedder tests fail here ([live-suite.log](live-suite.log));
  - the e2e stack ran with `EMBEDDER=fake`, the deterministic embedder the spec allows;
  - the Dockerfile's model bundling (`BUNDLE_MODELS=true`) is untested.
  - `app/embeddings/local.py` is written against fastembed's custom-model API (`add_custom_model` with `onnx/model.onnx` from `intfloat/multilingual-e5-small`), but it has not been run.
- **PDF not converted here.** Installing the `pdf` group (PyTorch, about 1 GB) didn't fit on this sandbox's disk, and its models also come from Hugging Face. The live PDF test fails on the missing `docling_parse`. DOCX and PPTX pass with real Docling.
- **No images built, so e2e ran on a host stack.** The disk filled up (0 bytes free) while the API image was being built, which shared the disk with parallel tickets, so the image build was abandoned. The e2e stack instead used:
  - Postgres+pgvector, Redis, RustFS and Mailpit from `docker compose` (project `rag0302`);
  - the API (`python -m app.serve`), the Celery worker and the Studio's Vite dev server, run on the host from the fresh clone, with the settings in [hoststack.env](hoststack.env).
  This is the same code and configuration compose runs, without the containers.
  - So `make e2e`, `make images` and `make image-scan` (Trivy) were **not run**. The Dockerfile and compose changes (build arguments, RustFS wiring, proxy target) are untested in containers.
- **pip-audit scope.** `make audit` covers the main and dev dependencies. The `pdf` group (PyTorch and others) isn't exported by `uv export` by default, so it wasn't audited.
- **No real cloud, email or paid APIs.** RustFS stands in for S3, and nothing here sends email.
- **Screenshots** were taken by [shots.mjs](shots.mjs) against the running host stack.
