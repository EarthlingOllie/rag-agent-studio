Fixed in `backend/pyproject.toml` (`docling-slim[convert-core,…]`), `uv.lock` re-locked (adds `rtree` 1.4.1 and `scipy` 1.18.1, only to the `pdf` group). To tell a test error from an adapter bug, [live-models/e5-reference-check.py](live-models/e5-reference-check.py) embeds the same texts with the model's own `transformers` weights (safetensors), mean pooling and normalisation, independently of fastembed: the adapter's vectors match it to 9e-8, and the reference ranks the same way ([e5-reference-check.txt](live-models/e5-reference-check.txt)). So the adapter is right and the expectation was wrong. The test now asks two queries that share the topic's words ("How many days of annual leave do I get?", "How long do I have to claim expenses?"), each nearest its own passage in the reference too.

| 2 | The upload flow is presign, then direct upload, then confirm; a SHA-256 content hash is recorded | **API** (`app/documents/api.py`, `service.py`):<br>• `POST …/projects/{project_id}/uploads` (`startDocumentUpload`) takes `{filename, size_bytes}`. It checks the type (415) and the size (413, 50 MB default), keeps the pending upload in Redis until the URL expires, and answers `{upload_id, url, method: "PUT", content_type, expires_at}`.<br>• The browser PUTs to `url`.<br>• `POST …/documents` (`confirmDocumentUpload`) takes `{upload_id, content_hash?}`. ## Decisions and notes (best guesses recorded instead of asking)

- **Docling package.** The core dependency is `docling-slim` with the Markdown, HTML, DOCX, PPTX and chunking extras. These need no PyTorch and no models, so the gate runs real Docling on Markdown and DOCX.
  - PDF needs layout models. They live in a `pdf` dependency group (`docling-slim[format-pdf,models-local]`, plus `torch` and `torchvision` from the PyTorch CPU index), which `uv.lock` locks.
  - The backend Dockerfile installs the group with `WITH_PDF=true` (the default), and downloads the models at build with `BUNDLE_MODELS=true` (the default). Compose passes both through as build arguments.
- **Pending uploads** are kept in Redis with the presigned URL's lifetime, not in a table. Each is keyed by Project and upload ID, so another Project's confirm finds nothing (409).
- **Content hash.** The API always computes it from the stored bytes. The browser may send one to be checked, but the Studio doesn't compute one today. Duplicate detection is ticket 03-05; the hash is indexed for it.
- **Failures.** One readable message is used for any ingestion failure. Categories, retry and backoff are ticket 03-04.
- **Guardrail scan.** The injection scan hook is ticket 03-07, so Chunks have no flag columns yet.
- **Status values.** The API uses lowercase (`queued`, `processing`, `ready`, `failed`), and the Studio shows the glossary's capitalised names.
- **Chunk-size setting.** `CHUNK_MAX_TOKENS` defaults to 256 and is capped at the model's 512. What gets embedded is the Chunk with its headings (`HybridChunker.contextualize`). What is stored is the Chunk text and its `heading_path`.
- **Edition.** Every Document starts at edition 1. Replacing an edition is ticket 03-05.
- **Same-origin uploads.** Locally, presigned URLs are signed for the Studio's address, and Vite proxies `/studio-documents` to RustFS. This avoids configuring CORS on RustFS. In AWS, S3 presigned URLs and CloudFront are spec 09's concern.
- **Single Document read.** No `GET …/documents/{id}` route was added. The list, the statuses and the Chunks were enough for this ticket. The Document viewer (03-03) adds what it needs.
- **`TRANSFORMERS_VERBOSITY=error`** is set in `app/__init__.py`. Docling's chunker imports transformers, which only tokenizes here, and otherwise prints a non-JSON advisory about PyTorch. That would break the "only JSON log lines" tests.
- **Migration number.** `0008_documents` follows `0007_provider_credentials`, the head on candidate. A parallel ticket's migration merged first would need its `down_revision` re-pointed.
