## Decisions recorded (best guesses, no human asked)

- **A separate `ecr` module**, following the spec's module boundaries. It has two repositories, matching what `deploy.yml` already pushes. The Studio repository is kept even though the Studio ships as static S3 assets, because the existing workflow pushes that image.
- **Origin header secret in state.** The value must be in the listener rule and in CloudFront's origin config, so it cannot be write-only. It is 256 bits from two `uuid()`s held by a `terraform_data` with `ignore_changes`, so it stays stable across plans. `origin_secret_version` regenerates it. No `random` provider was added, because the sandbox mirror has only the AWS provider.
- **Session secret** created here as a write-only Secrets Manager value (like 09-03's passwords). `session_secret_version` rotates it.
- **Beat has no AWS permissions** and no database access. It only enqueues work on Redis. Its deployments use 100%/0% so two schedulers never overlap.
- **Worker gets no credentials key.** This follows spec story 12 ("only the API can use the KMS key for credentials"). If worker-side provider embeddings (Voyage, OpenAI, Bedrock) need decrypted credentials, the worker will need a grant later, or the API will need to pass short-lived material. That is for ticket 03-09 to decide.
- **Connection settings as parts.** `DATABASE_HOST/PORT/NAME/USER` + `DATABASE_PASSWORD`, `REDIS_HOST/PORT/TLS` + `REDIS_AUTH_TOKEN`, `DOCUMENTS_BUCKET` and `CREDENTIALS_KMS_KEY_ARN` are passed as environment variables. The backend today reads `DATABASE_URL` and `REDIS_URL`. Assembling those URLs from the parts is app work for ticket 09-06 or the settings module. It is not done here, because app code is out of scope for this ticket.
- **Migrations are not in the API command.** `docker-compose.yml` runs `alembic upgrade head` before the server. In AWS, the spec runs migrations as a one-off task (ticket 09-06), which can reuse the API task definition with a command override.
- **Egress:** each service may reach TCP 443 anywhere (AWS APIs through the VPC endpoints, model providers through NAT), plus only the data stores it uses.
- **`image_tag` defaults to `bootstrap`** in `envs/demo`. Ticket 09-06's deploy workflow sets it to the pushed SHA. `latest` is rejected because repositories are immutable.
- **Checkov skips, each justified inline:** ALB access logs, deletion protection, HTTP listener, HTTPS redirect, TLS policy and HTTP target group (ADR-0011 and demo destroyability). WAF (out of scope). Container Insights (cost). Log group KMS and 1-year retention (cost; logs are scrubbed per ticket 01-03). Secret rotation. Two false positives: CKV_AWS_260 (the source is a prefix list) and CKV2_AWS_5 (the groups are attached through `for_each`). Totals across `infra/`: 253 passed, 0 failed, 45 skipped.

## Needs a real AWS account (not verified here)

- `terraform plan` and `apply` against AWS. Nothing was applied, and no cloud resources were created. These points are unverified:
  - Fargate ARM64 capacity and the default sizes in eu-west-2.
  - Whether the CloudFront origin-facing prefix list (about 55 entries) fits the security group rule quota (60 by default).
  - Whether ECS pulls KMS-encrypted ECR images with this execution role. ECR grants itself through KMS grants, so the deploy role needs `kms:CreateGrant` on the data key when it creates the repositories.
  - Whether the listener rule matches the header CloudFront sends (ticket 09-05).
  - Whether tasks start and pass `/api/health` once an image exists.
- Cross-account Bedrock `AssumeRole` with an external ID. That needs a customer account.
- A Logfire secret encrypted with a key other than the data key would also need `kms:Decrypt` on that key.
- The `terraform plan (demo)` CI job, which stays skipped until `AWS_DEPLOY_ROLE_ARN` is set (ticket 09-01).
- Monthly cost of Fargate, ALB and ECR. Ticket 09-06's README owns the estimate.
