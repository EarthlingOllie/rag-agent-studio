## Decisions recorded (best guesses, no human asked)

- **Two KMS keys, not one.** `credentials` is reserved for ADR-0006 envelope encryption, so ticket 09-04 can grant it to the API task role alone (spec story 12). `data` encrypts RDS, ElastiCache, the Documents bucket and the two platform secrets, which the worker also needs. That adds about $1 a month per key.
- **Secrets never touch state.** The RDS master password and the Redis AUTH token are each two `uuid()` values (244 bits from crypto/rand) passed only to write-only arguments (`password_wo`, `auth_token_wo`, `secret_string_wo`), in the same apply. The modules' `password_version` and `auth_token_version` inputs rewrite both copies together. `replace_triggered_by` rewrites the secret when the instance or replication group is replaced. The `aws_secretsmanager_random_password` ephemeral resource was tried first, but `terraform test` mock providers cannot serve ephemeral resources (tdd.log), so the module seam could not test it. Write-only arguments need Terraform 1.11, so the database and cache modules require `>= 1.11` (CI pins 1.13.4).
- **No RDS-managed master secret.** RDS rotates its managed secret every 7 days, which would break running ECS tasks that read the password at start-up.
- **Redis `auth_token_update_strategy = "ROTATE"`**, so a new token is added next to the old one when the version is bumped.
- **Static assets on SSE-S3.** With SSE-KMS, the key policy would have to trust CloudFront. These are public web builds anyway.
- **No S3 versioning.** Deleting a Document must remove its bytes (spec 03 deletion and retention). Static builds are re-uploaded by every deploy.
- **CORS methods `GET` and `PUT`** (presigned upload and download), with an explicit header list. Ticket 09-05's cdn module supplies the CloudFront origin and the distribution ARN. Until then, the demo environment passes neither, which means no cross-origin access and no static reads. There is no dependency cycle, because Terraform orders module internals by resource.
- **Client security groups are a map with static keys** (for example `api`, `worker`, `beat`), so `for_each` stays plannable when the IDs are unknown. Ticket 09-04 fills them in.
- **Demo defaults:** `db.t4g.micro` single-AZ with 20 GB gp3 storage that autoscales to 100 GB, `cache.t4g.micro` with one node, deletion protection off, no final snapshot, a 7-day key deletion window, and `force_destroy` on the demo buckets. Spec story 27 calls for a one-run destroy. Each value is a variable.
- **Checkov skips, each justified inline:** RDS enhanced monitoring, log exports, Multi-AZ, deletion protection and Performance Insights (demo cost or destroyability). Secret rotation (needs a rotation Lambda). ElastiCache CKV_AWS_31, a false positive because the check does not read `auth_token_wo`, while the tests assert both TLS and AUTH. Redis Multi-AZ (one node). S3 access logging, cross-region replication, event notifications, versioning, and KMS on the static bucket. Checkov's totals are 119 passed, 0 failed and 22 skipped across `infra/`.
