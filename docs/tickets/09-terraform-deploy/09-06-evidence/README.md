# Evidence: ticket 09-06, demo environment and deploy workflow

Branch `ticket/09-06-demo-env-deploy`. Each local log starts with its commands and ends with the exit code. [fresh-clone.log](fresh-clone.log) re-runs `make infra-check` from a new `git clone` of the branch at the last commit that changes code (named in the log's first line). That command runs fmt, the backend and composition checks, the deploy script tests, the CloudFront Function tests, then init, validate and `terraform test` in every module and environment, then TFLint (AWS ruleset 0.50.0) and Checkov. It exits 0 and ends with an empty `git status`. Round 2 also changed backend code, so [backend-lint.log](backend-lint.log) (`make lint-backend`: ruff, ruff format, mypy) and [backend-tests.log](backend-tests.log) (`make test-backend` with the 100% line and branch coverage gate, against fresh Postgres/pgvector, Redis and RustFS containers) were run too. Later commits on the branch touch only `docs/`. GitHub Actions is down, so no workflow ran on GitHub for this branch; everything here ran locally.

Nothing was applied, and no cloud resources, OIDC trust or deploys were created. Terraform ran only with `mock_provider "aws"`. The deploy and destroy scripts ran only against stubbed `terraform`, `aws` and `docker` commands.

## What changed

- `infra/modules/ecs/migrate.tf` (new): the one-off migration task (`alembic upgrade head`) with its own task role (no permissions), execution role (image, own logs, database password only), log group and security group (Postgres and HTTPS only). There is a new `migration_task_size` variable, and new outputs `migration_task`, `migration_security_group_id`, `task_definition_arns` and the two migration policies. The ECS services now have `lifecycle { ignore_changes = [task_definition] }`, so an apply at a new tag does not roll them. The deploy script rolls them after the migrations.
- `infra/envs/demo`: the database admits the migration task's security group. A new `deploy` output carries what the deploy script reads. The `image_tag` description is updated.
- `scripts/deploy/deploy.sh`, `smoke.sh` and `destroy.sh` (new), with tests in `scripts/deploy/tests/`: stubs, and `fake_site.py`, a local HTTP server that stands in for CloudFront.
- `.github/workflows/deploy.yml`: push builds images as before, and pushes them on `main` as `linux/arm64`. Its manual run now deploys at an `image_tag` input. The `apply`/`destroy` choice is gone. `.github/workflows/destroy.yml` (new) is a separate manual run with a typed confirmation.
- `infra/tests/compose.test.sh` (new). `Makefile`: `infra-check` runs the four new test scripts, and `images` takes `IMAGE_PLATFORM`.
- **Round 2, the tasks' settings** (evaluator item 1): `backend/app/core/settings.py` builds `DATABASE_URL` (`postgresql+asyncpg://user:password@host:port/name?ssl=require`) and `REDIS_URL` (`rediss://:token@host:port/0?ssl_cert_reqs=required`) from `DATABASE_HOST/PORT/NAME/USER/PASSWORD/TLS` and `REDIS_HOST/PORT/TLS/AUTH_TOKEN` when the URL itself is unset, escaping the credentials. A whole URL still wins, so `docker compose` and the tests are unchanged. The ecs module adds a `key-wrapper` platform secret (`LOCAL_KEY_WRAPPER_KEY`, 32 bytes base64, write-only, `key_wrapper_secret_version`) injected into all four containers, sets `DATABASE_TLS=true`, `OBJECT_STORE=s3`, `OBJECT_STORE_BUCKET/REGION`, `KEY_WRAPPER=kms` + `KMS_KEY_ID` (the credentials key) and `STUDIO_URL` on the API and worker, and `BEDROCK_PLATFORM_PRINCIPAL` (its own task role) on the API. The unused `DOCUMENTS_BUCKET` and `CREDENTIALS_KMS_KEY_ARN` are gone. Beat and the migration task now also get the database and Redis addresses (not the credentials), because every process validates the same settings. New ecs variable `studio_url`, wired from `module.cdn.url` in `envs/demo`; there is no cycle, because Terraform orders resources, not modules (the task definitions wait for the distribution, which waits for the ALB). New ecs output `task_environment`. `infra/modules/ecs/tests/task-settings.json` records every container's environment and secret names. `.env.example` and `docs/deploy-demo.md` ("What the tasks are given") document the parts.
- Docs: `docs/deploy-demo.md` (new: runbook, outputs, cost), plus a workflow table row in `docs/development.md` and the teardown pointer in `docs/infra-bootstrap.md`.

## Seams under test

These are the shared infrastructure seams in `docs/specs/README.md` and the "deploy smoke check" line of spec 09's testing decisions:
- **Module seam:** `terraform test` with mocked providers. `infra/modules/ecs` has 51 runs (8 new). `infra/envs/demo` has 7 runs (1 new, 2 changed).
- **The settings contract between the ecs module and the backend** (round 2). `task-settings.json` is the shared fixture. The ecs run `task_settings_match_the_recorded_contract` asserts that the four task definitions render exactly that environment and those secret names. `backend/tests/unit/test_aws_task_settings.py` loads each container's environment from it, with secret values in the shapes the modules generate (and a password with `/+:@?#`), through `load_settings()`, then builds the SQLAlchemy engine, the redis-py client and a Celery Redis result backend from the URLs. Celery raises on a `rediss://` URL without `ssl_cert_reqs`. A change to either side that the other does not match fails a suite. `backend/tests/unit/test_settings_from_parts.py` covers building the URLs at the `load_settings()` seam.
- **The deploy scripts' command-line interface**, the highest seam that runs offline. The scripts are what the workflows call, so the YAML only checks the confirmation, builds, and passes inputs through. `deploy.test.sh` has 22 cases and `destroy.test.sh` has 8. Both put stub `terraform`/`aws`/`docker` commands on `PATH`, record every call, and assert on the calls and their order. `smoke.test.sh` has 17 cases, with real `curl` against a local server.
- **Composition:** `compose.test.sh` reads the root modules' `module` sources, because `terraform test` sees one root module at a time.

## Decisions recorded (best guesses, no human asked)

- **Services ignore task definition changes; the script rolls them.** Otherwise `terraform apply` at a new tag would replace the services' task definitions before the migration ran, which breaks spec 09 story 26. A plain `terraform apply` (for example, the PR plan) now registers new revisions without rolling them. Only the deploy script moves services onto them.
- **The migration task has its own roles, log group and security group** rather than reusing the API's. It needs only the database, and the database's ingress lists it by name.
- **ECR is applied first with `-target=module.ecr`,** so the first deploy into an empty account can push images before the full apply. Later deploys skip the push when ECR already has the tag.
- **Images are built for `linux/arm64` under QEMU** (`docker/setup-qemu-action`), because the repository is private and GitHub's ARM runners may not be available on its plan. `deploy.sh` refuses to push an image of another architecture, because Fargate ARM64 would fail with `exec format error`. The push-on-`main` path of the `images` job also builds `linux/arm64`, so those tags are deployable. Branch builds stay native.
- **The confirmation phrase is `destroy demo`,** checked in the workflow (before credentials) and in the script.
- **The smoke check's widget probe uses an unknown Agent by default** (`/widget/a/smoke-check` answers 404 with `frame-ancestors *`). A fresh environment has no live Agent, and that response still proves the API serves the shell with a CSP through CloudFront. `smoke_agent_id` checks a real Agent's 200 response.
- **Unhashed entry points (`index.html`, `embed.js`, `widget/assets/widget.js`) are uploaded `no-cache` and invalidated.** Everything else is content-hashed and cached for a year. The spec named HTML and `embed.js`. `widget.js` is added because the API's shell references it by a fixed name.
- **A missing AWS configuration fails a manual deploy or destroy run with an error.** Unlike the PR plan job, it is not skipped, because someone who asks for a deploy should not get a green run that did nothing.

- **The URLs are built in `settings.py`, not in a container entrypoint** (round 2). The rule is then tested at the `load_settings()` seam under the backend's coverage gate, credentials are escaped with `urllib.parse.quote`, and Celery, the API and Alembic all get the same URL. A whole `DATABASE_URL`/`REDIS_URL` still wins, so nothing changes for `docker compose` or the tests.
- **`LOCAL_KEY_WRAPPER_KEY` is generated in Terraform from two UUIDs**, like the other platform secrets. 43 hex digits and `=` are a valid base64 encoding of 32 bytes, with about 166 random bits. The `random` provider would keep it in state, and ephemeral resources cannot be mocked in `terraform test`. KMS still wraps the data keys (`KEY_WRAPPER=kms`); this key only signs widget tokens, and every process's settings require it.
- **Beat and the migration task get the database and Redis addresses but not the credentials.** They have no network route to the store they do not use.

## Needs a real AWS account or GitHub Actions (not verified here)

- **No workflow ran on GitHub** (Actions is down). The workflows passed `actionlint`, but these are unverified: `workflow_dispatch` inputs, the `demo` environment, the shared concurrency group, `docker/setup-qemu-action` and the QEMU arm64 build time of the backend image with its models (it may be long; `timeout-minutes: 90`), and the OIDC token subject `repo:EarthlingOllie/rag-agent-studio:environment:demo`. The bootstrap's trust policy allows `environment:*`, but no token was exchanged.
- **No `terraform plan` or `apply` against AWS.** Unverified: the targeted ECR apply on an empty account, `iam:PassRole` for the migration roles (the deploy role may pass `studio-*` roles), real `run-task`/`update-service`/`wait` behaviour and timings (the AWS CLI waiters give up after about 10 minutes: `tasks-stopped` polls 100 times 6 s apart, `services-stable` 40 times 15 s apart; a slow first worker start could need a retry), the S3 sync to the KMS-encrypted static bucket, and the CloudFront invalidation.
- **The tasks' settings were only checked offline** (round 2). Their names and values are checked against `Settings` and the database, Redis and Celery clients are built from them, but nothing connected to real RDS or ElastiCache. Unverified: asyncpg's `ssl=require` against `rds.force_ssl`, and Celery and redis-py over ElastiCache TLS with the AUTH token. One more thing needs a real CloudFront: whether the API sees requests as HTTPS behind the HTTP origin hop (for Secure cookies and generated links), a point 09-05 also raised.
- **Email is not set up for the demo.** The ecs module leaves `MAILER` at its default (`outbox`), because spec 09 provisions no SES identity. Invites and password resets are kept in memory, not sent. This is a product decision for a later ticket, not a start failure.
- **The cost figures are estimates from on-demand list prices,** not a measured bill. Check them in the AWS Pricing Calculator or Cost Explorer after a real day.
- The smoke check against real CloudFront: SSE, `frame-ancestors` from a real Agent, and SPA fallback on `/`.
