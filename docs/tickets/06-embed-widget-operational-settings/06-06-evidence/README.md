## What was built

- **Data** (migration `backend/migrations/versions/20261108_0035_token_budget.py`, `0035_token_budget` on 06-05's `0034_rate_limits`): `agents.daily_token_budget` (default 1,000,000) beside the other Operational Settings (ADR-0009: not in any Draft or Version), and `agents.budget_exhausted_at`, the Budget alert flag.
- **Daily counter** (`backend/app/embed/admission.py`): a Redis counter per Agent per UTC date, `widget-budget:<public ID>:<YYYY-MM-DD>` (kept two days, then expired). `Admission.record_usage` adds each Visitor reply's actual `input_tokens + output_tokens` (the provider-reported usage the runtime already records on the Message) with `INCRBY` after the reply is saved; `tokens_used` reads a day's total. The date comes from the Clock port, so tests move it and a new UTC date starts a new counter: the reset needs no job.
- **Admission** (`Admission.admit`): checks the Token Budget first (today's usage at or over the budget refuses with `Refusal.TOKEN_BUDGET`), then the rate limits. A budget refusal is not counted against the rate-limit windows.
- **Serving** (`backend/app/embed/service.py`, `api.py`): `prepare_turn` passes the Agent's current budget to admission and returns an `AdmittedTurn` (the prepared turn plus the limits used). A refusal streams `200 text/event-stream` with one event, `event: unavailable` / `data: {"reason": "budget_exhausted", "message": <the Agent's Unavailable text>}`; nothing is saved and no model is called. After each answered reply its usage is recorded; when the day's total reaches the budget, or when a message is refused for the budget, `service.budget_exhausted` raises the alert.
- **Alert and email** (`service.budget_exhausted`): one conditional `UPDATE … SET budget_exhausted_at = now WHERE id = :agent AND (budget_exhausted_at IS NULL OR budget_exhausted_at < today 00:00 UTC) RETURNING id`. Only the call that raises today's flag sends, so the email to every Owner of the Organisation (`mail.templates.token_budget_exhausted`, through the mailer port; Mailpit locally, the outbox in tests) goes once per Agent per UTC date, even with concurrent replies. A flag left from an earlier day counts as none, so a late Beat run can't swallow the next day's email.
- **Beat task** (`backend/app/embed/tasks.py`, `embed.clear_budget_alerts`; scheduled in `app/worker/celery_app.py` as `clear-token-budget-alerts`, `crontab(minute=0, hour=0)`, Celery `timezone="UTC"`): clears every flag raised before today (UTC). A flag raised today stays.
- **API**: `GET`/`PATCH …/operational-settings` gain `daily_token_budget` (1 to 1,000,000,000; explicit `null` refused); a change is audited (`agent.operational_settings_changed`, before/after) and applies to the next message. New `GET …/agents/{agent_id}/token-usage` (`getTokenUsage`, Editors and Owners): `{date, tokens_used, daily_token_budget, exhausted, resets_at}` for today. `AgentOut` gains `budget_exhausted` (the alert flag), on the Agent list and the Agent.
- **Studio** (`frontend/apps/studio`): a **Token Budget** group in the Embed section's Operational Settings with the budget meter (`role="progressbar"`, "Tokens used today", "N of M tokens used today (P%)."; when spent, "Today's Token Budget is spent: Visitors see the unavailable text until midnight UTC, or until you raise the budget.") and "Tokens per day" with its own Save; saving refreshes the meter. `LiveStatus` shows a **Budget exhausted** badge (with an explanatory `title`) wherever it is shown: the Agent list rows and the Agent page header.
- **Widget**: unchanged behaviour; an `unavailable` event of either reason shows the Unavailable text (comment updated, test added).
- **Playground**: untouched. It never goes through admission and never records usage.
- Generated API client regenerated; `GLOSSARY.md` updated.

## Gaps and best guesses

- **Best guesses, recorded instead of asking:**
  - **Default and range:** 1,000,000 tokens a day by default; 1 to 1,000,000,000; no "unlimited".
  - **What counts:** input plus output tokens the provider reported for each Visitor reply (the Message's `input_tokens + output_tokens`), including the Guardrail-free fallback answer (0 tokens, as no model is asked). The LLM classifier's own calls (08-03) are not counted against the budget; they are not recorded per Message today.
  - **Overshoot:** usage is known only after a reply, so the reply that crosses the budget is answered in full and the day ends a little over budget (the spec: "incremented with actual usage after each reply"). Concurrent replies admitted just before can overshoot further.
  - **When the alert is raised:** by the reply that reaches the budget, or by the first refusal (e.g. after the budget was lowered below today's usage), whichever comes first; the spec names the first refusal, and raising it when the budget is spent tells Owners sooner. Either way one email per Agent per UTC date.
  - **Alert vs budget:** the badge follows the flag, which Beat clears at midnight UTC as the spec says; raising the budget during the day makes the Agent answer again at once but leaves the badge until midnight (the meter shows the budget is no longer spent).
  - **Refusal shape:** like 06-05, `200` with one `unavailable` event, reason `budget_exhausted`.
  - **Owners:** every Owner of the Agent's Organisation at the time; Editors are not emailed.
- **Not built (other user story):** the alert badge for an Agent whose rate limits are "being hit heavily" (user story 31), as in 06-05.
- **Sandbox limits** (as in earlier tickets): images are built with `WITH_PDF=false BUNDLE_MODELS=true` ([build.sh](build.sh) adds only the egress proxy CA) and the e2e stack runs `EMBEDDER=fake` and the fake model gateway (no real provider or key); emails go to Mailpit. The live suite and the Trivy scan were not run. `registry.terraform.io` is blocked here, so `make infra-check` used a scratch `TF_CLI_CONFIG_FILE` with a filesystem mirror of `hashicorp/aws` (as earlier tickets did); no infra changed in this ticket. The e2e run covers this ticket's spec and its neighbours (listed in Results), not the whole suite.
