## What was built

- **API** (`backend/app/embed/api.py`, `service.py`), both authenticated only by `Authorization: Bearer <Conversation token>`, like sending a message:
  - `GET /api/widget/agents/{public_id}/conversation` (`getWidgetConversation`): **Resume**. 200 `{messages: [{role: "user"|"assistant", content, citations: [{label, document_name}]}]}`, in order, each answer with the sources it cited (`C<rank>` and the Document's name, null once the Document is deleted). A reload counts as activity, so it moves `last_activity_at` on: the 24-hour window slides. 401 ("This chat has expired. Reload the page to start a new one.") for a missing, tampered, another Agent's, ended or expired token; 404 ("This assistant is no longer available.") once the Agent is archived, in an archived Project or no longer live.
  - `DELETE /api/widget/agents/{public_id}/conversation` (`endWidgetConversation`): **ending a Conversation**. 204; the stored token hash is cleared, so the token is refused by all three widget routes from then on. The Conversation and its Messages are kept. Works after the Agent is retired too.
  - The token check (signature, stored hash, Agent, 24-hour expiry) is now one function, `_conversation`, shared by sending, resuming and ending.
- **Widget** (`frontend/apps/widget/src`):
  - `storage.ts`: `tokenStore(agent)` keeps the Conversation token in the iframe's `localStorage` under `rag-widget:conversation:<public ID>`. Browsers partition iframe storage per top-level site, so a reload or another page of the same site gets it back. Every access is wrapped: where storage is blocked (it throws), `load` returns nothing and `save`/`clear` do nothing, so the token lives in memory only and a reload starts afresh.
  - `Widget.tsx`: on load with a kept token it shows "Loading your chat…" and resumes: the earlier Messages appear (with "Sources: …") and the next question continues the Conversation. A refused (expired or ended) token is forgotten silently and the next question starts a new Conversation. Any other failure keeps the token, shows the error, and lets the Visitor carry on. A 404 at any point (resume, start, or a message mid-Conversation) replaces the chat with the **no longer available shell** ("This assistant is no longer available.", `role="status"`) and forgets the token. A 401 on a message forgets the token, so the next question starts a new Conversation instead of failing again.
  - **New chat** ends the current Conversation (best effort `DELETE`), clears the log and focuses the message box. **End chat** does the same and shows "You ended the chat." with **Start a new chat**. Both are disabled while an answer streams. Ending before anything was asked calls nothing.
  - `chat.ts`: `resume`, `endConversation`; `ChatError` now carries the HTTP status.
- **Generated API client** regenerated (`make gen-client`). `GLOSSARY.md` and `docs/development.md` updated (below).
- No migration: ending a Conversation clears `conversations.token_hash` (already nullable, added by 06-01).

## Gaps and best guesses

- **Best guesses, recorded instead of asking:**
  - **A Resume slides the 24-hour window**, as a message does. The spec says the token expires "24 hours after last activity, sliding" and a Visitor reloading or navigating the site is active, so a Visitor who keeps returning keeps their Conversation; a Visitor who leaves for 24 hours loses it.
  - **New chat ends the old Conversation** on the server as well as forgetting it, rather than leaving a live token nobody holds. End chat does the same and then shows "You ended the chat." with a button to start again, rather than closing anything: the open/close bubble and returning focus to the launcher are 06-03's and 06-07's (in bubble mode, End chat can also close the panel then).
  - **Ending is recorded by clearing the token hash**, not a new `ended_at` column, so no migration is needed now (06-02 and 06-03 run in parallel and may add their own). The Conversations viewer (07-01) can add an ended marker if it wants to show one.
  - **Ending is best effort in the widget:** if the `DELETE` is refused or unreachable, the widget still forgets the token; an unended token expires in 24 hours anyway.
  - **A resume that fails for another reason** (a 5xx or the network) keeps the token and shows the generic error, so a brief outage doesn't throw the Conversation away.
  - **A question saved without an answer** (the provider failed) comes back on resume as a question with no reply, as it is stored.
  - Resume returns citations as the label and Document name only (what the stream sends), not passages; expandable passages are 06-03's citation work.
- **Left to later tickets, as the spec splits it:** the branded bubble/inline layout, greeting and starter questions (06-03); rate limits and the Token Budget's `unavailable` event (06-05, 06-06); focus trap, live-region and axe on the open widget (06-07).
- **Not tested:** the real 24-hour wait in a browser (the API tests use the controllable clock; the e2e stack has no clock control). Real browsers' third-party storage blocking is simulated in e2e by making `localStorage` throw, as Safari and Firefox's strict modes do; this sandbox has only Chromium.
- **Sandbox limits** (as in earlier tickets): images are built with `WITH_PDF=false BUNDLE_MODELS=false` (`build.sh` adds only the egress proxy CA), and the e2e stack runs `EMBEDDER=fake`. The live suite and the Trivy image scan were not run. No real provider is called: the stack uses the fake verifier and the gateway's fake chat model.
