## What was built

- **Data** (migration `backend/migrations/versions/20261107_0032_rate_limits.py`, `0032_rate_limits` on `0031_operational_settings`): `agents.conversation_messages_per_minute` (default 10) and `agents.ip_messages_per_minute` (default 30), columns on the Agent beside its other Operational Settings, not in any Draft or Version (ADR-0009).
- **Admission control** (`backend/app/embed/admission.py`): `Admission(redis, clock).admit(limits, token, ip)` returns `None` (admitted) or a `Refusal` reason (`conversation_rate`, `ip_rate`). Two sliding one-minute windows in Redis, each a sorted set of admitted message times: `widget-rate:conversation:<sha256 of the Conversation token>` and `widget-rate:ip:<Agent public ID>:<IP>`. One Lua script prunes both windows, refuses if either is full, and only otherwise records the message in both, so refusals never count, waiting always works and two concurrent messages can't both take the last place. Times come from the Clock port (tests move it); Redis expiry only clears idle windows.
- **Client IP** (`backend/app/embed/client_ip.py`): `client_ip(peer, x_forwarded_for_lines, trusted)` walks the connection peer and then `X-Forwarded-For` from the right, skipping trusted proxies; the first untrusted address is the Visitor. Anything a client wrote itself is ignored; garbage stops the walk at the last address believed; IPv4-mapped IPv6 is unwrapped. New setting `TRUSTED_PROXIES` (comma-separated networks or addresses, `backend/app/core/settings.py`; a bad entry fails startup naming it). Empty (the default) means the peer is the Visitor.
- **Serving** (`backend/app/embed/service.py`, `api.py`): `prepare_turn` checks the Conversation token, then admits the message with the Agent's current limits, and only then saves the question (spec 06: "Visitor messages go through admission, then the runtime"). A refusal (`NotAdmittedError`) answers `200 text/event-stream` with one event, `event: unavailable` / `data: {"reason": "rate_limited", "message": <the Agent's Unavailable text>}`; nothing is saved and no model is called. An invalid token is still a 401 and doesn't use up the IP's allowance.
- **Operational Settings API**: `GET`/`PATCH …/operational-settings` gain `conversation_messages_per_minute` (1–1000) and `ip_messages_per_minute` (1–10000); a change is audited (`agent.operational_settings_changed`, before and after of the changed keys) and applies to the next message. Explicit `null` is refused (there is no "unlimited").
- **Widget** (`frontend/apps/widget/src/chat.ts`): an `unavailable` event ends the answer like a provider failure: the Visitor sees the Agent's unavailable text in the alert (the Live Version's own unavailable message when it has one, as 06-02 already did for 503s and `error` events), their question stays, and they can ask again.
- **Studio** (`frontend/apps/studio/src/projects/AgentEmbed.tsx`): a **Rate limits** group in the Embed section's Operational Settings, "Messages per minute per Conversation" and "Messages per minute per IP address", with its own Save ("Saved. Messages over a limit get the unavailable text from now on."), disabled until the settings load.
- **Playground**: untouched. Its route (`app/playground/api.py`) never calls admission control.
- Generated API client regenerated.

## Gaps and best guesses

- **Left to later tickets, as the spec splits it:** the Token Budget (06-06) will add its counter to `admit` and an `unavailable` event with its own reason; the alert badge for an Agent whose limits are "being hit heavily" (user story 31) is not in this ticket's criteria and was not built; refusals are not yet logged or counted for the Studio.
- **Best guesses, recorded instead of asking:**
  - **Window and defaults:** one-minute sliding windows; 10 messages per Conversation and 30 per IP address by default; maxima 1000 and 10000; no "unlimited".
  - **Per-IP is per Agent** (`widget-rate:ip:<public ID>:<ip>`), since limits are each Agent's Operational Settings; one IP flooding one Agent doesn't affect others.
  - **Order:** the token is checked first (a bad token is a 401 and uses no allowance), then admission, then the Agent's liveness and the question is saved. A refused message is not saved and does not count.
  - **Refusal shape:** `200` with a single `unavailable` SSE event `{reason: "rate_limited", message}`, not a 429, so the widget reads every outcome from one stream (spec: "A refusal returns the unavailable event"). Which limit was hit is not told to the Visitor.
  - **Client IP:** only `X-Forwarded-For` is read. CloudFront appends the viewer's address to it and the ALB appends CloudFront's, so with the VPC CIDR and CloudFront's origin-facing ranges in `TRUSTED_PROXIES` the viewer is found. `CloudFront-Viewer-Address` and RFC 7239 `Forwarded` are not used. Sign-in throttling (01-06) still uses the connection peer as uvicorn reports it; it was left alone to keep this ticket scoped.
- **Not merged with the latest candidate:** `origin/candidate` moved to `5ba01fd` (06-07) after the checks started; a trial merge is clean (no conflicts) but was not committed, as each full re-verification takes about two hours on this shared machine. The orchestrator's merge should re-run the checks.
- **Not configured in AWS:** the ECS task definitions (09-04/09-06) don't set `TRUSTED_PROXIES` yet, so in AWS every Visitor would currently be counted under the ALB's address until the VPC CIDR and CloudFront ranges are added; this ticket changes no infra. Locally, compose keeps uvicorn's `FORWARDED_ALLOW_IPS="*"` from 01-06.
- **Sandbox limits** (as in earlier tickets): images are built with `WITH_PDF=false BUNDLE_MODELS=false` (`build.sh` adds only the egress proxy CA) and the e2e stack runs `EMBEDDER=fake`. The live suite and the Trivy scan were not run. Infra checks were not run; this ticket changes no infra.
