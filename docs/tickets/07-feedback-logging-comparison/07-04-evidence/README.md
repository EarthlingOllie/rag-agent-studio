## What was built

- **Analytics module** (`backend/app/analytics/`), a deep module behind one query:
  - `stats.py`: `wilson(successes, n)` (Wilson score interval, z = 1.959964) and `Histogram`: fixed buckets 10% wide (bucket 0 below 1, then [1.1^(i-1), 1.1^i), the last open-ended), mergeable across days, stored as `{bucket: count}`; `percentile(p)` is the nearest-rank percentile interpolated inside its bucket.
  - `models.py`, migration `0037_usage_daily` (after 06-06's `0036_token_budget`): `usage_daily` (per Agent Version per UTC day: Conversations, Messages, token replies, token sum and histogram, frozen cost sum, thumbs up and down, rating sum and count, fallback count, first-token and latency histograms; unique per Version and day) and `usage_rollup_state` (per Organisation, the last day whose rollup is final).
  - `usage.py`: one day's usage per Version from the raw tables. Only Visitor Conversations (never the Playground, never Draft answers). Day of each number: a reply (and its tokens, cost, latency, fallback, Message Feedback) on the day it was made; a Conversation on the day this Version first replied in it; a Conversation Rating on the day of the Conversation's first reply.
  - `rollup.py` + `tasks.py`: the Beat task `analytics.roll_up_usage`, scheduled hourly at minute 5 (`app/worker/celery_app.py`). Under a Postgres advisory lock, each run finalises, per Organisation, every day before today that isn't final yet (normally just yesterday; days a stopped Beat missed are caught up), then recomputes today. Each day is recomputed in full and replaces its rows (idempotent); a final day is never recomputed. `at=` (ISO time) redoes a run as of a time.
  - `service.py` `version_metrics(agent, versions, start, end, today)`: days before today from `usage_daily`, today (the live partial day) from the raw tables; Wilson intervals and percentiles at query time; low confidence below 30 (votes, ratings, Conversations).
  - `api.py`: `GET /api/organisations/{org}/projects/{project}/agents/{agent}/metrics` (`getVersionMetrics`, Editors and Owners), `version` (repeatable; every Version when left out), `start`/`end` UTC dates (default the last 30 days to today; at most 366 days; start after end → 422). Per Version: `conversations`, `messages`, `low_confidence`, `tokens {n, mean, p95}`, `cost {total_usd, per_conversation_usd}`, `thumbs_up {up, down, n, rate, low, high, low_confidence}`, `rating {n, mean, low_confidence}`, `fallback {count, rate}`, `latency {n, first_token_p95_ms, total_p95_ms}`, `is_live`.
- **Messages are stamped with the app's Clock** (`playground/service.py`: the question's and the answer's `created_at`), as Conversations already were, so the rollups count each reply on the right day (and tests can drive days with the controllable clock).
- **Studio Analytics tab** (`frontend/apps/studio/src/projects/AnalyticsTab.tsx`, `analytics.ts`; replaces the placeholder): Agent picker, Version picker (Live by default, else the newest), From/To UTC days, and seven KPI cards: Volume, Tokens per reply (mean, p95, n), Cost per Conversation (and total, at the prices of the time), Thumbs-up rate (rate, "95% interval a% to b%", "n = N votes (u up, d down)"), Mean rating ("x.x of 5", n), Fallback rate, p95 latency (total and first token, n). **Low confidence**: the card is muted and dashed and says "Low confidence (fewer than 30 votes)" (or ratings, Conversations).
- **Generated API client** regenerated. **Glossary**: new **Version KPIs**, **Usage rollup**, **Wilson interval**, **Low confidence**.

## Gaps and judgement calls

- **Seams not confirmed with a human.** The TDD skill asks for seams to be agreed first; no human is reachable, so the spec's own seams were used.
- **Late changes after a day is final aren't counted.** A thumb or rating changed after its day was finalised (normally after 00:05 UTC the next day) doesn't move that day's rollup (the spec finalises the previous day and recomputes per day). Each number belongs to a fixed day (the reply's, the Version's first reply in the Conversation, the Conversation's first reply), so nothing is ever counted twice. The window is small: a Conversation token expires after 24 hours without activity.
- **Finalisation is per Organisation** (`usage_rollup_state.finalised_through`), not one global flag, so catching up one Organisation never recomputes another's final days; 07-07's purge can check "day ≤ finalised_through" before clearing text.
- **Days before today are read only from `usage_daily`**, as the spec says (rollups plus the raw current day). Until the first run after midnight, yesterday shows its last hourly rollup (up to an hour old); the test above shows this.
- **Tokens per reply** are input plus output tokens of replies that asked a model; fallback replies and refusals are left out of tokens (they count in volume, fallback rate and latency). Cached tokens aren't recorded on Messages yet, so they aren't separated.
- **Cost** is the sum of each reply's frozen cost (replies with no known price add 0), divided by the Version's Conversations.
- **Low confidence** threshold: fewer than 30 samples (votes for thumbs, ratings for the mean rating, Conversations for volume). Tokens, cost, fallback and latency cards carry their n but no flag.
- **Guardrail block rate** is in the spec's rollup list but not this ticket's KPI list; it is left to 08-06 (Guardrail analytics), which can add a column the same way. The KPI tab shows one Version at a time; comparison and time series are 07-05 and 07-06.
- **The rollup works out one day in Python** from that day's replies (histograms built in Python, shared by the rollup and the live day): fine at this product's scale; a very large day could move the histogram bucketing into SQL.
- **Messages' `created_at`** now comes from the app's Clock (as Conversations' already did), so tests drive days with the controllable clock; in production it is the same instant as the database's `now()`.
- **E2E** asserts the live partial day (the Editor sees the Visitor's feedback immediately); the Beat task in the stack is shown separately ([rollup-in-compose.log](rollup-in-compose.log)). The e2e Project has no Documents, so its replies are fallbacks; token and cost values are covered at the API and network seams.
- **Migration numbering:** `0037_usage_daily` follows candidate's `0036_token_budget` (06-06, merged while this ticket was in progress; renumbered in `87d418a`). If another ticket merges a `0037` first, re-chain `down_revision` at merge time.
- **Merged test:** 06-06's worker-entrypoint test asserted its task was in `app.tasks`, which holds only when an earlier test imported the module; the merged test checks both tasks' modules are in the worker's includes instead (the tasks register when the worker loads them).
