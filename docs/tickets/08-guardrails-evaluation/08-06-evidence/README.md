## What was built

- **Block rate in rollups and KPIs.** `usage_daily.guardrail_blocks` (migration `0038_guardrail_analytics`, reversible, after 07-04's `0037_usage_daily`) counts a Version's Visitor replies that were the refusal text because the input Guardrail blocked the question (`layer=input, action=blocked`, the same test `app.guardrails.outcomes.blocked` the Playground and the eval runner use; it moved there from `pipeline.py`). The live partial day counts them the same way (`app/analytics/usage.py`). `GET …/agents/{id}/metrics` returns `guardrail_blocks: {count, rate}` per Version (rate = blocks / replies; null without a reply). The Studio's Analytics tab adds a **"Guardrail block rate"** KPI card ("50%", "2 of 4 replies were blocked by the input Guardrail"; under 1% shows one decimal).
- **Conversations filter by Guardrail outcome.** `GET …/conversations?guardrail=` takes `blocked | flagged | logged | replaced | allowed` (a reply whose Guardrail outcome took that action, JSONB containment), `any` or `none`; it combines with every other filter; 422 for anything else. Each row gains `guardrail_events` (replies with a Guardrail outcome). The Studio's Conversations tab adds a **Guardrail** select (kept in the URL, `?guardrail=blocked`) and a Guardrail column ("None", "1 event", "2 events").
- **Block rate alert.** After each hourly rollup (`app/analytics/rollup.py` → `app/analytics/alerts.py::check_block_rates`), each Agent's Visitor replies in the hour up to the run are compared with the week before that hour. A **spike** is ≥ 5 blocked messages, ≥ 20% of the hour's messages and ≥ 3× the baseline's rate. A spike sets `agents.block_rate_alert_at` (same migration) and emails every Owner once through the configured mailer (`templates.block_rate_spike`, with a link to the Conversations viewer filtered to the Agent's blocked Conversations); while the spike lasts no further email is sent; the first run without a spike clears the flag; a later spike alerts again. `AgentOut.block_rate_alert` drives a **"Block rate spike"** badge beside "Budget exhausted" (`LiveStatus`: Agent list and Agent page), the same badge mechanism as spec 06's Budget alert.
- API client regenerated; `GLOSSARY.md` updated.

## Gaps and judgement calls

- **Seams not confirmed by a human** (none available); the spec's shared seams were used.
- **Spike thresholds are code constants** (`WINDOW` 1 h, `BASELINE` 7 days, `SPIKE_MIN_BLOCKS` 5, `SPIKE_MIN_RATE` 20%, `SPIKE_FACTOR` 3) in `app/analytics/alerts.py`, documented in the glossary. The spec says "a baseline" and "a threshold" without numbers; these are my best guess for a demo-scale product, not per-Agent settings.
- **What counts as a block:** only the input Guardrail's `blocked` action (block mode, including an LLM-classifier outage failing closed). Warned/logged messages were answered and canary replacements are output-side; both stay visible through the Conversations filter (`flagged`, `logged`, `replaced`).
- **The hour is measured from the reply's timestamp** up to the rollup's run time (the hourly Beat task, minute 5), so a spike is noticed within about an hour of starting and cleared within an hour of stopping. The Budget alert clears at midnight; this one clears as soon as an hour is normal, which suits an attack better.
- **Email to Owners**: the spec asks for the badge "using the same badge mechanism as spec 06"; spec 06's alert also emails Owners, so this one does too, once per spike. Delivery is through the configured mailer: the outbox double in tests, Mailpit (the local mail sink) in compose. No real email was sent.
- **The spike badge is not driven end to end in Playwright**: that would need an hour of traffic or a hook to run Beat from the browser test. It is covered at the API/task seam, the network seam, and in the running stack by `spike_in_stack.py` (real widget API, the real worker running the Beat task, the real API flag and the Mailpit email).
- GitHub Actions is down; all checks ran locally, one at a time (the user authorised merging on local results).
- **Migration numbering:** `origin/candidate` was still `527d5d6` when this branch was finished (rechecked after the last run), so `0038_guardrail_analytics` follows `0037_usage_daily` with one Alembic head. Sibling tickets running in parallel may add their own `0038`; whoever merges second must renumber and rerun the checks. Not merged here (this step's instructions: no PR, no merge).
- **The Editor in the spike test** is created but not asserted on: the emails are filtered to the Owners' addresses (the shared test database holds other tests' Agents). The recipients query is the Budget alert's (Owners only).
