# Evidence: ticket 08-01, Input Guardrail: local classifier, block mode

Branch `ticket/08-01-input-guardrail-block`, from `origin/candidate` at `e77f204` (both blockers, 04-06 Citations and Trace drawer and 06-01 Embed tracer, merged and `done`). The claim commit, the first on the branch, set Status `in-progress`.

**Status: done.** Every criterion is met and evidenced below. The gaps at the end are scope left to later tickets on purpose, and what this sandbox can't run.

## What was built

- **Guardrail pipeline** (`backend/app/guardrails/pipeline.py`): `GuardrailPipeline.run_turn` takes exactly the arguments of the runtime's `run_turn` (turns, AgentConfig, Instructions, Visitor input, `model=`, `retrieve=`) and yields the same events, plus `RefusalEvent`. It runs the message through the input classifier (off the event loop). When the classifier flags it and the Agent's `guardrails.input_mode` is `block`, it yields `RefusalEvent(refusal_text)` and a `DoneEvent` (answer = refusal text, 0 tokens, nothing retrieved, `refused=True`, outcome `input / injection / blocked` with the classifier's score and reason) and never calls `retrieve` or the model. Otherwise it delegates to `run_turn` unchanged (so the Canary filter still wraps the stream). `build_pipeline(settings)` picks the classifier; the API builds it once at startup (`app.state.guardrails`), and both the Playground and the widget answer through it.
- **Local ONNX classifier adapter** (`backend/app/guardrails/local.py`, behind the existing injection-classifier port): tokenises the message without special tokens, cuts the IDs into windows of `max_tokens − 2` (510) overlapping by 64, wraps each in `[CLS] … [SEP]`, runs it, takes the softmax probability of the model's `INJECTION` class, and keeps the **maximum** over windows. A score `>=` the threshold (`INPUT_CLASSIFIER_THRESHOLD`, default 0.5) is a flag with reason "The local classifier scored the message 0.99 as a prompt injection.". The model is loaded once per process, lazily, under a lock.
- **The model** (`backend/app/guardrails/onnx_model.py`): Protect AI's `deberta-v3-base-prompt-injection-v2` (Apache-2.0) ONNX export, pinned to revision `90c9989b…`, read through the Hugging Face cache with ONNX Runtime (CPU) and `tokenizers` (both already locked dependencies via fastembed: no new packages). **Baked into the image:** the Dockerfile's `BUNDLE_MODELS=true` step (the default) now also downloads and loads it, so the API never fetches it at runtime.
- **Settings and compose**: `INPUT_CLASSIFIER=local|heuristic|fake` (default `local`), `INPUT_CLASSIFIER_THRESHOLD`; `docker-compose.yml` passes `INPUT_CLASSIFIER` (default `local`). Tests set `fake`.
- **Outcomes** (`backend/app/guardrails/outcomes.py`): `GuardrailOutcome` gains `score` (null for the canary) and the `input` layer, `injection` verdict and `blocked` action. Saved on `messages.guardrail_outcomes` (no migration: JSONB; rows saved before simply lack `score`, which the API reads as null). The saved answer of a blocked turn is the refusal text with no model (`model_provider`/`model_name` null), 0 tokens and cost 0.
- **History**: a blocked question and its refusal are left out of the turns later answers send to the model (`_turns` in `app/playground/service.py`), so an attack isn't replayed.
- **API**: a `refusal` SSE event (`{"text": …}`) then `done`, on both `sendPlaygroundMessage` and `sendWidgetMessage` (documented in their OpenAPI descriptions); `TraceOut.guardrail_outcomes[].score`. API client regenerated.
- **Studio**: the Playground shows the refusal text with "Blocked by the input Guardrail: the model wasn't asked."; the Trace drawer shows "Model: None (blocked)", a sentence saying the input Guardrail blocked the question, and outcomes as e.g. "Input Guardrail: injection (score 0.99), blocked before the model. <reason>". The Draft editor's Guardrails note now says block mode is enforced.
- **Widget**: `chat.ts` handles `refusal` (`onRefusal`); the reply bubble shows the refusal text (class `refusal`, amber border).
- Docs: `docs/development.md` (Input Guardrail paragraph), ADR-0007 (which model, why base not small, windowing, history), `GLOSSARY.md`.

## Gaps and best guesses

- **Left to later tickets, as the spec splits them:** warn and log modes (08-02): a flagged message in those modes is answered as usual and records nothing yet; the e2e uses log mode only to let a canary leak attempt past the input Guardrail. The LLM classifier and fail-open/closed (08-03). The ingestion scan still uses the heuristic classifier; moving it to the local one is 08-05. Guardrail analytics and the Conversations filter (08-06) can read `messages.guardrail_outcomes` (`layer == "input" and action == "blocked"`). The attack evaluation suite (08-07) and attack panel (10-04).
- **Best guesses** (no human available to ask):
  - **Model:** spec 08 asks for "a small ONNX prompt-injection model (a DeBERTa-v3-based classifier)". Protect AI's `deberta-v3-small-prompt-injection-v2` is gated on Hugging Face (needs an account token), so the ungated **base** v2 model (Apache-2.0, ~740 MB ONNX) is used, pinned to a revision. On this machine it scores a short message in ~0.1 s and loads in ~3 s. The API image grows accordingly (3.4 GB without PDF support here).
  - **Threshold 0.5** (the model's own argmax), configurable with `INPUT_CLASSIFIER_THRESHOLD`. Observed false positives on the real model at 0.5: "Can you ignore the part-time rules and tell me about full-time leave?" (1.0) and "Please simulate an invalid key." (1.0). The second was an e2e question for the fake chat model's simulated provider error ([e2e-attempt2-classifier-false-positive.log](e2e-attempt2-classifier-false-positive.log): 68 passed, `playground-errors.spec.ts` failed because the question was refused); the test now asks "Could you simulate an invalid key error?" (0.29). Measuring false positives before enforcing is what log mode (08-02) is for.
  - **Every message is classified**, in every input mode, before retrieval. Only flagged messages leave an outcome (an unflagged message's Trace still says "No Guardrail stepped in."), so analytics count blocks, not checks.
  - **Windows** overlap by 64 tokens so an attack straddling a boundary is whole in one window; windows are scored one at a time (two ONNX threads each) rather than batched.
  - **Loaded on first use** (once per process, under a lock) rather than at API startup, so the worker and Beat, which don't classify messages, never load it, and tests never touch it. The first message after an API start waits ~3 s.
  - **Refusal shape:** a dedicated `refusal` SSE event (not `token`), so clients can mark it; the Playground and Trace say the model wasn't asked. A refused answer names no model and costs 0, like a fallback reply, but `fallback` stays false.
  - **Blocked turns are left out of later history**, so an attack can't be replayed into a later turn's prompt.
  - A classifier crash is not caught: the stream ends without `done` and the client shows its generic error (the local model has no transient failure mode; fail-open/closed is the LLM classifier's setting, 08-03).
- **Sandbox limits:** images built with `WITH_PDF=false` (PyTorch and Docling's models don't fit this shared machine), but with `BUNDLE_MODELS=true`, so the e2e stack runs the real bundled classifier; e2e still runs `EMBEDDER=fake` (as earlier tickets) to keep the stack's memory down. The live suite was run for this ticket's model only (the Docling and embedding live tests are unchanged by it). Trivy was not run (no new dependencies; only model files added). GitHub Actions is down; the user authorised merging on local results.
