# Evidence: ticket 08-03, LLM classifier

**Ticket:** [`08-03`](../03-llm-classifier.md) · **Spec:** [Guardrails and evaluation](../../../specs/08-guardrails-evaluation-spec.md) · **Branch:** `ticket/08-03-llm-classifier`

## What was built

- **LLM classifier adapter** (`backend/app/guardrails/llm.py`): `LlmClassifier.classify(message)` makes a structured-output Pydantic AI call (`Agent(model, output_type=LlmVerdict)`, temperature 0) with a fixed classifier prompt (`CLASSIFIER_PROMPT`), the message shown between `<message>` markers as untrusted data: every spelling of the closing marker inside it (any letter case, whitespace inside the brackets, e.g. `</MESSAGE>`, `</message >`, `< /message>`) is escaped to `&lt;/message&gt;`, so the only closing marker the judge sees is the real one. `LlmVerdict` is `label` (`injection`/`benign`), `score` (0 to 1) and `reason`. `injection` gives an `InjectionFlag` whose reason reads "The LLM classifier (<model>) flagged the message: <reason>". Its model is built lazily by a callable, so the gateway failing to build it counts as a provider failure too. Any of the runtime's `PROVIDER_ERRORS` (Pydantic AI's `ModelAPIError`s, `UnexpectedModelBehavior` for an answer off the schema after one retry, the gateway's `ModelUnavailableError`/`UnsupportedCredentialError`) and no answer within `LLM_CLASSIFIER_TIMEOUT_S` (new setting, default 10 s) raise `LlmClassifierError(kind)`, the kind classified as the Playground's provider errors are.
- **Through the model gateway, with the Agent's own credential** (`backend/app/playground/service.py`): `save_question` resolves the configuration's `guardrails.classifier` (credential + model) into `PreparedTurn.classifier`, as it does the Reranker; `answer` hands the pipeline `guardrails.llm_classifier(partial(gateway.chat_model, credential, model), model)`. The Playground answers with the Draft's setting, the widget with the Live Version's.
- **Pipeline and fail mode** (`backend/app/guardrails/pipeline.py`): the local classifier runs first; only a message it passed goes to the LLM classifier, and only when the Agent's input mode is **block** (warn and log mode, from 08-02, act on the local classifier's flag alone for now; see Gaps). A flag from either blocks in block mode (refusal text, no retrieval, no model call). When the LLM classifier fails, `guardrails.fail_mode` decides: **closed** (the default) treats the message as flagged and records `{layer: input, verdict: unchecked, action: blocked}`; **open** answers it and adds `{layer: input, verdict: unchecked, action: allowed}` to the answer's outcomes. Each reason says which model, why it couldn't check ("the provider rejected the API key", "… over its rate limit or quota", "the model isn't available from the provider", "the provider failed", "it didn't answer within 10 s") and what the fail mode did.
- **Guardrail outcomes** (`backend/app/guardrails/outcomes.py`): verdict `unchecked` and action `allowed` added; regenerated API client. The Studio's Trace drawer renders `allowed` as "let through without the check" (`TraceDrawer.tsx`). The Guardrails settings note now says the LLM classifier is enforced (`DraftEditor.tsx`); the classifier picker and the fail-mode select already existed (04-07).
- **Credential reference:** the AgentConfig field and its Credential-reference registration (`CREDENTIAL_USES` in `app/agents/validation.py`) were already present from 04-07; this ticket makes the classifier actually use that credential, and tests the reference from the Live Version.
- **Fakes for the whole stack** (`backend/app/gateway/fakes.py`): asked as a classifier (a call with output tools), the fake chat model returns a verdict: `injection` (score 0.9) for a message containing `FAKE_JAILBREAK_PROMPT` ("you are DAN"), `benign` otherwise; it raises the `FAKE_FAILURES` provider errors as before, and a 503 on `FAKE_CLASSIFIER_OUTAGE` ("simulate a classifier outage") only as a classifier, so the e2e can show fail-open answering. No real provider or key is used anywhere.
- **Docs:** `GLOSSARY.md` (LLM classifier, Fail mode; Injection classifier, Input Guardrail and Guardrail outcome updated), ADR-0007 (paragraph on the LLM classifier's decisions), `docs/development.md`.

## Test seams

- **API seam** (`backend/tests/integration/test_llm_classifier.py`, 28 tests): the in-process API against real Postgres/pgvector and Redis; the gateway's chat builder returns a `FunctionModel` per model name: `Judge` for the classifier model (answers the structured-output tool, or raises a given provider error, answers off-schema, or is slow) and `Answerer` for the answering model (records every call, so "never reached the model" is observed directly). Assertions are on the SSE events, the saved Conversation and the Trace, through the Playground and widget APIs.
- **Gateway fake, unit** (`backend/tests/unit/test_model_gateway.py::test_the_fake_chat_model_plays_an_llm_classifier_for_the_whole_stack`): `LlmClassifier` over the real fake adapter.
- **Frontend, network seam** (`AgentPage.test.tsx::the Trace says when the LLM classifier flagged a message or couldn't check it`).
- **E2E** (`frontend/e2e/tests/llm-classifier.spec.ts`): against the compose stack with the real bundled local classifier and the fake gateway.

## Gaps and best guesses

- **Best guesses** (no human available to ask):
  - **Order and cost:** the LLM classifier runs only on messages the local classifier passed (the spec says "local, then LLM"); a message the free local check flags never costs a provider call.
  - **A label decides, not a threshold:** `injection` flags regardless of the score, which is recorded. The fixed prompt asks for a calibrated score, but a threshold on a model's self-reported score adds a setting with little meaning.
  - **Failure** includes an off-schema reply (after Pydantic AI's one retry), the gateway being unable to build the model, and a timeout (`LLM_CLASSIFIER_TIMEOUT_S`, 10 s), not only HTTP errors from the provider.
  - **Outcome shape:** a failed check is the verdict `unchecked` with action `blocked` (closed) or the new action `allowed` (open), with no score, so analytics (08-06) can count unchecked messages separately from detections.
  - **Warn and log modes** (08-02) landed on `candidate` while this ticket was open and were merged in (conflicts in `outcomes.py`, `pipeline.py`, the Trace drawer, the Draft editor note and the docs, resolved to keep both). The LLM classifier stays **block mode only**: in warn and log mode the pipeline acts on the local classifier's flag as 08-02 built it and never calls the paid LLM classifier (test `test_an_agent_not_in_block_mode_never_pays_for_the_llm_classifier` still holds). Running it in warn/log too (its flag would become `flagged`/`logged`, and fail-closed would need a warn/log meaning) is a follow-up that changes 08-02's behaviour, so it was left out of this merge; ADR-0007 and the Draft editor note say the LLM classifier is enforced in block mode.
- **Not done here:**
  - The classifier call's tokens and Cost are not added to the answer's usage or the Trace (the spec doesn't ask; noted in ADR-0007).
  - The demo provider's built-in model (seed, spec 10) doesn't answer classifier calls; an Agent using it as its LLM classifier fails per its fail mode. Only the fake and real providers judge.
  - No live-suite test against a real provider: the brief forbids real keys and paid calls; the structured call is exercised with `FunctionModel`s and the fake adapter. The local classifier's live suite is unchanged by this ticket and wasn't rerun.
  - **Sandbox limits:** as 08-01, images are built with `WITH_PDF=false` and `BUNDLE_MODELS=true` (the e2e runs the real bundled local classifier), `EMBEDDER=fake`. GitHub Actions is down; the user authorised merging on local results.
