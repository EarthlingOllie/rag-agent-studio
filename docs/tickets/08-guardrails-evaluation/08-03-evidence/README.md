# Evidence: ticket 08-03, LLM classifier

**Ticket:** [`08-03`](../03-llm-classifier.md) · **Spec:** [Guardrails and evaluation](../../../specs/08-guardrails-evaluation-spec.md) · **Branch:** `ticket/08-03-llm-classifier`

## What was built

- **LLM classifier adapter** (`backend/app/guardrails/llm.py`): `LlmClassifier.classify(message)` makes a structured-output Pydantic AI call (`Agent(model, output_type=LlmVerdict)`, temperature 0) with a fixed classifier prompt (`CLASSIFIER_PROMPT`), the message shown between `<message>` markers as untrusted data (a `</message>` inside it is defused). `LlmVerdict` is `label` (`injection`/`benign`), `score` (0 to 1) and `reason`. `injection` gives an `InjectionFlag` whose reason reads "The LLM classifier (<model>) flagged the message: <reason>". Its model is built lazily by a callable, so the gateway failing to build it counts as a provider failure too. Any of the runtime's `PROVIDER_ERRORS` (Pydantic AI's `ModelAPIError`s, `UnexpectedModelBehavior` for an answer off the schema after one retry, the gateway's `ModelUnavailableError`/`UnsupportedCredentialError`) and no answer within `LLM_CLASSIFIER_TIMEOUT_S` (new setting, default 10 s) raise `LlmClassifierError(kind)`, the kind classified as the Playground's provider errors are.
- **Through the model gateway, with the Agent's own credential** (`backend/app/playground/service.py`): `save_question` resolves the configuration's `guardrails.classifier` (credential + model) into `PreparedTurn.classifier`, as it does the Reranker; `answer` hands the pipeline `guardrails.llm_classifier(partial(gateway.chat_model, credential, model), model)`. The Playground answers with the Draft's setting, the widget with the Live Version's.
- **Pipeline and fail mode** (`backend/app/guardrails/pipeline.py`): the local classifier runs first; only a message it passed goes to the LLM classifier. A flag from either blocks in block mode (refusal text, no retrieval, no model call). When the LLM classifier fails, `guardrails.fail_mode` decides: **closed** (the default) treats the message as flagged and records `{layer: input, verdict: unchecked, action: blocked}`; **open** answers it and adds `{layer: input, verdict: unchecked, action: allowed}` to the answer's outcomes. Each reason says which model, why it couldn't check ("the provider rejected the API key", "… over its rate limit or quota", "the model isn't available from the provider", "the provider failed", "it didn't answer within 10 s") and what the fail mode did.
- **Guardrail outcomes** (`backend/app/guardrails/outcomes.py`): verdict `unchecked` and action `allowed` added; regenerated API client. The Studio's Trace drawer renders `allowed` as "let through without the check" (`TraceDrawer.tsx`). The Guardrails settings note now says the LLM classifier is enforced (`DraftEditor.tsx`); the classifier picker and the fail-mode select already existed (04-07).
- **Credential reference:** the AgentConfig field and its Credential-reference registration (`CREDENTIAL_USES` in `app/agents/validation.py`) were already present from 04-07; this ticket makes the classifier actually use that credential, and tests the reference from the Live Version.
- **Fakes for the whole stack** (`backend/app/gateway/fakes.py`): asked as a classifier (a call with output tools), the fake chat model returns a verdict: `injection` (score 0.9) for a message containing `FAKE_JAILBREAK_PROMPT` ("you are DAN"), `benign` otherwise; it raises the `FAKE_FAILURES` provider errors as before, and a 503 on `FAKE_CLASSIFIER_OUTAGE` ("simulate a classifier outage") only as a classifier, so the e2e can show fail-open answering. No real provider or key is used anywhere.
- **Docs:** `GLOSSARY.md` (LLM classifier, Fail mode; Injection classifier, Input Guardrail and Guardrail outcome updated), ADR-0007 (paragraph on the LLM classifier's decisions), `docs/development.md`.

## Gaps and best guesses

- **Best guesses** (no human available to ask):
  - **Order and cost:** the LLM classifier runs only on messages the local classifier passed (the spec says "local, then LLM"); a message the free local check flags never costs a provider call.
  - **A label decides, not a threshold:** `injection` flags regardless of the score, which is recorded. The fixed prompt asks for a calibrated score, but a threshold on a model's self-reported score adds a setting with little meaning.
  - **Failure** includes an off-schema reply (after Pydantic AI's one retry), the gateway being unable to build the model, and a timeout (`LLM_CLASSIFIER_TIMEOUT_S`, 10 s), not only HTTP errors from the provider.
  - **Outcome shape:** a failed check is the verdict `unchecked` with action `blocked` (closed) or the new action `allowed` (open), with no score, so analytics (08-06) can count unchecked messages separately from detections.
  - **Warn and log modes** are ticket 08-02's (being built in parallel): today, as in 08-01, a message flagged (or failing closed) in warn or log mode is answered as usual without an outcome; a fail-open outcome is recorded in every mode. When 08-02 lands, its flagged-message handling applies to the LLM classifier's flags and to fail-closed unchanged, since both are an ordinary flag in the pipeline.
- **Not done here:**
  - The classifier call's tokens and Cost are not added to the answer's usage or the Trace (the spec doesn't ask; noted in ADR-0007).
  - The demo provider's built-in model (seed, spec 10) doesn't answer classifier calls; an Agent using it as its LLM classifier fails per its fail mode. Only the fake and real providers judge.
  - No live-suite test against a real provider: the brief forbids real keys and paid calls; the structured call is exercised with `FunctionModel`s and the fake adapter. The local classifier's live suite is unchanged by this ticket and wasn't rerun.
  - **Sandbox limits:** as 08-01, images are built with `WITH_PDF=false` and `BUNDLE_MODELS=true` (the e2e runs the real bundled local classifier), `EMBEDDER=fake`. GitHub Actions is down; the user authorised merging on local results.
