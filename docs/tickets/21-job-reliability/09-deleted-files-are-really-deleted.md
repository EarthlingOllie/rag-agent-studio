# 09: Deleted files are really deleted

**Ticket:** `21-09` · **Spec:** [Job reliability](../../specs/21-job-reliability-spec.md)

**What to build:** When an Editor deletes a Document or replaces an edition, its stored files are removed even if the first attempt fails or the worker dies, and the work that follows a new edition is always finished.

**Blocked by:**
- `21-03`

**Status:** done

- [x] A deletions table holds object keys or prefixes to delete; rows are written in the transaction that removes the last reference to them
- [x] Deleting a Document and discarding or replacing an edition write their keys to the table instead of sending them in a message
- [x] The sweeper deletes each entry from storage and then removes the row; an entry whose objects are already gone is removed without error
- [x] A kill between the database commit and the storage delete leaves no orphaned object after the next sweep
- [x] After a new edition is ingested, removing the old edition's files and refreshing Expected source Stale flags are finished by the sweeper if the worker died before doing them
- [x] The object-deletion job no longer carries keys in its message
- [x] Tests cover the new behaviour at the highest seam (see [shared test seams](../../specs/README.md#shared-test-seams)); 100% line and branch coverage holds
- [x] New domain terms are added to `GLOSSARY.md`; ADRs updated if a decision changed

## Evidence

Seams: the API seam with the task seam ([shared test seams](../../specs/README.md#shared-test-seams)). Deleting and replacing go through the Documents routes; a lost message comes from the Job publisher fake (`jobs.lose_next()`), a dead worker from the in-memory object store's kill switch (`"delete"`) or from the publisher fake killing the job that sends a given task (`jobs.kill_when_sending(task)`), a failed delete from the store's `failure`. The sweeper task is called directly with the controllable clock. Stored files have no API surface, so tests read the in-memory store, and the deletions table's row count by SQL, as the existing deletion tests read Chunk rows. New tests: `backend/tests/integration/test_deleted_files.py`.

1. **The deletions table.** Migration `0061_object_deletions` creates `object_deletions` (`id`, `created_at`, `key`, `prefix`), mapped as `ObjectDeletion` in `backend/app/jobs/models.py`. `deletions.schedule(session, keys, prefix=…)` (`backend/app/jobs/deletions.py`) adds rows in the caller's transaction, and each caller does so in the transaction that removes the last reference: `service.delete_document` (current and staged edition's original and markdown), `service.replace_document` when it overwrites a Failed staged edition, `pipeline._swap` (the old edition's), and `_ingest_claimed`/`_settle` when they find the Document deleted. Prefix entries are drained with `delete_prefix`: `test_an_entry_can_be_a_prefix_whose_every_object_is_deleted` (whose first sweep fails and keeps the entry).
2. **Deleting and discarding or replacing write keys instead of messages.** `delete_document` no longer returns keys and `Replacement.discarded` is now a flag; the API sends `enqueue_object_deletion()` with no arguments after the commit. Tests: `test_a_deleted_documents_files_are_removed_by_the_sweeper_when_the_job_is_lost`, `test_a_discarded_failed_replacements_files_are_removed_by_the_sweeper`, and the existing `test_document_editions.py` deletion tests, unchanged, still pass.
3. **The sweeper deletes, then removes the row; already-gone objects are fine.** `deletions.drain` takes each entry with `FOR UPDATE SKIP LOCKED` in its own transaction, deletes it from storage and only then deletes the row. A failed delete is logged and the entry kept. The sweep task (`backend/app/jobs/tasks.py`) drains after its job recoveries. Tests: `test_files_whose_first_delete_failed_are_deleted_by_the_next_sweep`, `test_an_entry_whose_files_are_already_gone_is_removed_without_error` (table empty afterwards), `test_the_deletion_job_delivered_again_after_it_finished_does_nothing`, `test_a_second_drain_skips_the_entry_the_first_is_deleting` (a sweep during a held delete deletes the other entry and leaves the held one to its job).
4. **A kill between commit and storage delete leaves no orphan.** `test_a_worker_killed_before_deleting_from_storage_leaves_nothing_after_the_next_sweep`: the deletion job dies at the store's delete after the Document's delete committed; the files are still there; one sweep removes them. The lost-message test covers a kill before the job is even sent.
5. **Follow-on work after a new edition.** The swap writes the old edition's keys to the table and sets `documents.recheck_due` in the same transaction. After the commit the ingestion sends the deletion job, runs `on_new_edition` (the Expected source re-check) and clears the flag for that edition. The sweeper runs `pipeline.finish_new_editions` for every Document still flagged. `test_the_work_after_a_new_edition_is_finished_by_the_sweeper_if_the_worker_died` kills the ingestion as it sends the deletion job. The old files and the old Stale flags are still there. After one sweep, the old files are gone and the Expected sources are re-matched (one now `passage_missing`, one cleared). With the sweeper's `finish_new_editions` call removed, the test fails.
6. **The object-deletion job carries no keys.** `JobPublisher.delete_objects()` sends `Job("documents.delete_objects", ())`; the task `delete_stored_objects()` takes no arguments and drains the table. Tests: `test_object_deletions_after_ingestion_are_sent_through_the_publisher` asserts the message is exactly `Job(DELETE_OBJECTS_TASK, ())`, and the broker-headers test sends it keyless.
7. **Seams and coverage.** Every new test above runs at the API seam with the task seam, apart from the prefix test, which writes an entry through `deletions.schedule` because no route writes a prefix yet (21-10 will). Every line and branch of the changed modules is run by the suite (see the coverage note under Gaps).
8. **Glossary and ADRs.** `GLOSSARY.md` gains **Deletions table** (under Knowledge, after Staged edition). ADR-0020 already describes the table and the sweeper draining it, so it is unchanged. `docs/development.md` gains a "Deleted files are really deleted" paragraph, and its Job publisher paragraph no longer says the deletion job carries keys.

## Gaps and best guesses

- **Best guess:** the sweeper drains every entry it finds, with no age threshold. `SKIP LOCKED` keeps it off an entry a live job is deleting, and deleting twice is harmless. So a sweep that lands just after a commit does the job's work early, which costs nothing.
- **Best guess:** the Expected source re-check is marked by a flag on the Document (`recheck_due`), not by a row in a separate table. It is cleared only for the edition that set it, so a newer swap's flag survives an older ingestion finishing late. Re-checking twice is harmless, so the sweeper does not wait for a dead-after time either.
- **Best guess:** drains and finished re-checks are not counted as recoveries, so the sweep task's return value and the `Sweeper recovered …` spans are unchanged. A sweep that did any writes one log span, `Sweeper finished {deleted} object deletions and {finished} new editions`.
- **Best guess:** the in-memory store's `failure` now fails deletes as well as reads, and its kill switch has a `"delete"` point; no existing test set `failure` and then deleted.
- **Best guess:** `object_deletions` has no `organisation_id` and is listed in `PLATFORM_TABLES` (`backend/app/tenancy/models.py`), so `test_every_table_below_the_platform_level_carries_an_organisation_id` accepts it. An entry has to outlive the Organisation whose files it deletes, so it can't cascade with it.
- **Out of this ticket (21-10):** Project deletion writing its storage prefix to the table. The table and the drain already handle prefixes.
- **Local run (2026-11-26):** RustFS ran in Docker. The backend suite ran in chunks (`run-chunks-w3.sh`, adapted to this worktree with its own test database and Redis). Sibling worktrees were running their suites at the same time, so three chunks were killed for lack of memory and were run again with fewer workers. Every test passed in the end: the RustFS `test_object_store` and `test_seed` included, and the HNSW probe too. The `test_logging` subprocess tests timed out once under that load and then passed on their own (9 passed). The combined coverage report missed one line, the in-memory store's failing `delete_prefix`, and the prefix test now covers it. Ruff, ruff format, mypy and `make link-check` pass.
