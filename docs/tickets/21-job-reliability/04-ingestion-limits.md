# 04: Ingestion limits: interruption cap, conversion limit and durable retries

**Ticket:** `21-04` · **Spec:** [Job reliability](../../specs/21-job-reliability-spec.md)

**What to build:** A Document that keeps being interrupted becomes Failed with the Failure category "interrupted" instead of restarting for ever, conversion that runs too long is stopped, and an automatic retry always happens even if the broker lost it.

**Blocked by:**
- `21-03`

**Status:** done

- [x] The third interruption of a Document sets it to Failed with the Failure category `interrupted` and a message that suggests Retry
- [x] Interruptions are counted apart from provider retries; a manual Retry resets both
- [x] Conversion that runs past 30 minutes is stopped and the Document is Failed with the existing conversion error; the limit is a setting
- [x] The time of the next automatic retry is stored on the row and the attempt number is read from the row, never from the message
- [x] A Document waiting for an automatic retry whose message was lost is retried by the sweeper once its time has passed, and gets no more provider attempts than the maximum
- [x] The API's Failure category enum gains `interrupted`; the Documents list and Document viewer show it with its message and Retry
- [x] One Playwright journey: an ingestion is interrupted through a test-only switch on the fake converter, the Document returns to Queued and becomes Ready; axe passes on the Documents list
- [x] New Studio UI uses the design system ([docs/design/README.md](../../design/README.md), `frontend/apps/studio/src/design`): its tokens, recipes and shared patterns (dialogs, toasts, badges, code blocks, meters, diffs, empty and loading states, bulk bar, segmented control, pagination, editable list), never Tailwind palette classes or `dark:`; the palette ratchet passes
- [x] Tests cover the new behaviour at the highest seam (see [shared test seams](../../specs/README.md#shared-test-seams)); 100% line and branch coverage holds
- [x] New domain terms are added to `GLOSSARY.md`; ADRs updated if a decision changed

## Evidence

Seams: the API seam with the task seam, as the [shared test seams](../../specs/README.md#shared-test-seams) name them. Ingestion starts through the upload, replace and retry routes. A kill comes from the converter fake's kill switch, a lost, held or late message from the Job publisher fake (`jobs` fixture, which gains `deliver_next`), and the sweeper task is called directly with the controllable clock. Outcomes are read through the Documents and Chunks endpoints and the traces. New tests are in `backend/tests/integration/test_ingestion_limits.py` (13). The Studio is tested at the network seam, and the journey runs in Playwright.

1. **The third interruption fails the Document as interrupted.** Migration `0061_ingestion_limits` adds `interruption_count` and `retry_at` to `documents` and `staged_editions`. When the sweeper finds a stale row, `IngestionPolicy.recover` (`backend/app/documents/jobs.py`) counts the interruption. Below `INGESTION_MAX_INTERRUPTIONS` (default 3) the row goes back to Queued. At the cap it is Failed with `FailureCategory.INTERRUPTED` and `limits.interrupted_message`: "Processing was interrupted 3 times. Retry it, or upload it again." Tests:
   - `test_the_third_interruption_fails_the_document_as_interrupted`: Processing after the first two, Failed after the third, three kills.
   - `test_a_new_edition_interrupted_three_times_fails_while_the_current_one_keeps_answering`: the replacement fails and edition 1's Chunks keep answering.
   - `test_a_ready_document_processed_again_and_interrupted_three_times_loses_its_chunks`.
   - `test_the_interruption_cap_is_a_setting`.
2. **Interruptions are counted apart from provider retries; a manual Retry resets both.** Every claim still counts one in `attempt_count`. `recover` takes the interrupted run off again, so `attempt_count` counts only automatic attempts that ran to an end, and `interruption_count` counts the interruptions. `retry_document` sets `attempt_count`, `interruption_count` and `retry_at` back to zero or null, and a new replacement does the same. Tests:
   - `test_interruptions_are_counted_apart_from_provider_retries`: after two interruptions, three provider failures and success, `attempt_count` is 4.
   - `test_a_manual_retry_gives_an_interrupted_document_three_fresh_attempts`: after Failed as interrupted, Retry, then two more interruptions, it is Ready with `attempt_count` 1.
   - `test_an_editor_retries_a_failed_document_until_it_is_ready` now expects `attempt_count` 1 after a manual Retry. Before this ticket it expected 2.
3. **Conversion past 30 minutes is stopped and fails with the conversion error; the limit is a setting.** `pipeline._convert` runs the converter in a thread of its own under `asyncio.wait_for(…, INGESTION_CONVERSION_TIMEOUT_SECONDS)` (default 1800). On `TimeoutError` it logs a warning and fails with `FailureCategory.CONVERSION` and `limits.CONVERSION_FAILED`. The executor is shut down without waiting, so the job ends and the worker slot is free. Test: `test_conversion_that_runs_past_its_limit_is_stopped_and_fails_as_a_conversion_error`. It asserts the 1800 s default, sets the limit to 0.3 s and holds the converter: the Document is Failed, `conversion`, with no Chunks.
4. **The next retry's time is on the row; the attempt number is read from the row.** `_start` reads the attempt number from the claimed row's `attempt_count`, and `ingest` passes it on as `Attempt.number`. `_settle(QUEUED, retry_in=delay)` stores `retry_at = now + backoff` with `queued_at`, and the claim clears it. `JobPublisher.ingest_document` no longer sends `attempt`. The `documents.ingest` task still accepts `attempt` from messages sent before this ticket, and ignores it. Tests:
   - `test_the_attempt_number_comes_from_the_row_not_the_message`: a message that says `attempt=4` for a Document on its first attempt gets an automatic retry and becomes Ready with `attempt_count` 2. Taking the number from the message would have failed it.
   - `test_an_automatic_retry_is_sent_through_the_publisher` (updated): the retry message has no kwargs.
5. **A lost retry message is sent by the sweeper once due, with no more than the maximum attempts.** A `JobTable` now names its `retry_at` column. The sweeper sends a Queued row again once `retry_at <= now` and it hasn't been sent since (`queued_at < retry_at`), and records the reason `retry due` in the traces. Otherwise the queued-too-long rule applies, unless a retry is still due later. Tests:
   - `test_an_automatic_retry_whose_message_was_lost_is_sent_by_the_sweeper_once_due`: nothing is sent at 9 s; at 11 s the retry is sent, with trace reason `retry due`, and the Document becomes Ready with `attempt_count` 2.
   - `test_lost_retries_never_give_more_provider_attempts_than_the_maximum`: every retry message is lost and the sweeper sends each one. A late copy of a lost message, still saying `attempt=1`, does nothing. The Document is Failed after 4 attempts, and the embedder was called exactly 4 times.
6. **API enum and Studio.** `FailureCategory` gains `interrupted`, in `openapi.json` and `schema.gen.ts`, which `make gen-client` regenerated. The Documents list labels it "Interrupted" (`CATEGORY_LABELS`, now exported) with its message, and the row's menu offers Retry. The Document viewer now shows the category under the status. For a Failed Document in a Project that isn't archived, it shows a Retry button, and a refused retry shows the API's reason. Tests:
   - `DocumentsTab.test.tsx`: the `interrupted` case of the category labels, and `a Document interrupted too many times says so, suggests Retry and offers it`.
   - `DocumentViewer.test.tsx`: an Editor retries from the viewer and sees Queued; a refused retry says why; an archived Project's Document shows no Retry.
7. **Playwright journey.** `frontend/e2e/tests/interrupted-ingestion.spec.ts` uploads a Markdown file whose first line starts with `INTERRUPT_MARKER` (`%INTERRUPT-ONCE `). The converter's test-only switch (`interrupt_if_marked`, `app/documents/converter.py`) interrupts it at its first conversion. The fake converter always honours the marker. With `CONVERTER_TEST_INTERRUPTS=true`, `InterruptibleConverter` puts it in front of Docling, because the compose stack converts with Docling (`test_the_end_to_end_stack_can_interrupt_an_ingestion_whatever_converts_it`). The journey sees the Document stay Processing and run axe on the Documents list. Once the sweeper has put it back to Queued and it has been ingested again, it sees Ready with Chunks and no Interrupted label, and runs axe again. `make e2e` starts the stack with the switch on and `JOB_HEARTBEAT_SECONDS=2`, `JOB_DEAD_AFTER_SECONDS=20` (`E2E_STACK_ENV`; `docker-compose.yml` passes the three through, defaulting to off, 30 and 300). The backend test `test_a_file_marked_for_interruption_is_interrupted_once_then_becomes_ready` holds the resent job and shows the Queued step through the API. See Gaps for how the journey was run.
8. **Design system.** The viewer's Retry uses `button.secondary` and `Notice` from `src/design`. The category label uses the `text-danger` token, as the list's does. There are no palette classes and no `dark:`. `pnpm palette-ratchet` passes.
9. **Seams and coverage.** The tests above run at the API seam with the task seam, the network seam and Playwright. `pnpm test` passes at 100% coverage (1285 tests), along with `pnpm lint`, `pnpm typecheck`, `check-embed-size` and `palette-ratchet`. The backend suite passes with 100% line and branch coverage combined (16689 statements, 2122 branches), and ruff, ruff format, mypy and `make link-check` pass; see Gaps for how the suite was run.
10. **Glossary and ADRs.** `GLOSSARY.md`'s Failure category entry already names `interrupted` ("ingestion was cut short three times running; Retry starts the count again"); it was amended with the spec, so it is unchanged. ADR-0020 is unchanged; this ticket applies it. `docs/development.md` gains an "Ingestion limits" paragraph.

## Gaps and best guesses

- **Best guess:** an interrupted run doesn't count as a provider attempt. The claim counts every run in `attempt_count`, and `recover` takes the interrupted one off again. So `attempt_count` in the API means "automatic attempts that ran to an end, since it was last queued by hand".
- **Best guess:** "stopped" means the job stops waiting for conversion and the Document is Failed. A Python thread can't be killed, so the abandoned conversion runs on in the background until Docling returns, and its result is dropped. Docling's own `document_timeout` (PDF pipeline only) was not wired in, to keep the converter port unchanged.
- **Best guess:** the sweeper sends a due retry as soon as its time has passed (Beat runs it every minute), not after an extra grace period. If the countdown message arrives as well, the claim makes it a no-op.
- **Best guess:** the e2e switch remembers which files it has interrupted by a sentinel file in the temporary directory, keyed by the file's hash, so "once" holds across a worker's processes. Each run's file carries a unique token.
- **Best guess:** the Queued step of the journey lasts milliseconds on a live stack, because the sweeper sends the job again in the same pass and an idle worker claims it at once. The journey checks Processing, then Ready, more than the dead-after time later. The backend test holds the resent message and asserts Queued through the API.
- **Not run here: `make e2e` on the compose stack.** In this session, services may be started only from the main checkout, so the journey ran against the worktree's code as local processes:
  - API, Celery worker and Beat from `backend/` against a fresh database `studio_e2e_2104` and a private Redis;
  - RustFS from the shared compose service;
  - the Studio on Vite, converting with Docling, `EMBEDDER=fake`, and the three e2e settings above;
  - Playwright with `/usr/bin/google-chrome`, one worker and `--disable-dev-shm-usage`.

  `interrupted-ingestion.spec.ts` passed (35 s), together with `ingestion-failures.spec.ts`. The worker log shows `JobKilled('convert')` raised from the task and `Sweeper recovered documents.ingest …: no heartbeat`. Billiard reports the `BaseException` as a task error, so the child process survives; the row was still left Processing with no heartbeat, as after a real kill.
- **Local run of the backend suite.** The suite ran in chunks against the local PostgreSQL 16 (database `studio_test_2104`), a private Redis and the shared RustFS. It is the `run-chunks-w3.sh` split, with the last chunk halved and re-run where the sandbox stopped it: one chunk was killed for memory and one by the two-hour limit, while sibling suites ran on the same machine. 3224 tests passed: 471 unit and live, then 614, 537, 426 and 1176 integration. Four `test_logging.py` tests timed out waiting 20 s for a server process to start under a load average near 20. Run again on their own, all 9 tests in that file passed. The combined coverage report is 100%. `test_object_store` and `test_seed` passed, since RustFS was running.
- **Migration numbering:** `0061_ingestion_limits` follows `0060_ingestion_claims`. At the wave-5 integration the sibling migrations were renumbered after it, 0062..0066.
