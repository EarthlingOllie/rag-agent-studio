# 10: Deleting a Project

**Ticket:** `21-10` · **Spec:** [Job reliability](../../specs/21-job-reliability-spec.md)

**What to build:** An Owner who deletes an archived Project sees it as Deleting at once; it can't be used or restored, and its rows and files always go, even if the first attempt is lost.

**Blocked by:**
- `21-09`

**Status:** done

- [x] The delete request records a deleting mark and who asked, in the request's transaction, and returns as it does today
- [x] A Deleting Project is left out of Project lists and pickers, and refuses uploads, edits, restoring and Visitor messages with a clear reason
- [x] The cascade deletes the Project's rows and writes its storage prefix to the deletions table in one transaction; the sweeper removes the files
- [x] A deletion whose message was lost, or whose worker died at any point, is finished by the sweeper
- [x] Running the deletion twice, or as two copies at once, is harmless
- [x] The archived Projects view shows Deleting until the Project is gone, and the confirmation says a deleted Project can't be restored
- [x] Only Owners can delete; another Organisation's Project is unreachable
- [x] New Studio UI uses the design system ([docs/design/README.md](../../design/README.md), `frontend/apps/studio/src/design`): its tokens, recipes and shared patterns (dialogs, toasts, badges, code blocks, meters, diffs, empty and loading states, bulk bar, segmented control, pagination, editable list), never Tailwind palette classes or `dark:`; the palette ratchet passes
- [x] Tests cover the new behaviour at the highest seam (see [shared test seams](../../specs/README.md#shared-test-seams)); 100% line and branch coverage holds
- [x] New domain terms are added to `GLOSSARY.md`; ADRs updated if a decision changed

## Evidence

Seams: the API seam with the task seam, and the Studio's network seam ([shared test seams](../../specs/README.md#shared-test-seams)). Requests go through the Project routes; a lost message comes from the Job publisher fake (`jobs.lose_next()`), a dead worker from the in-memory object store's kill switch (`"delete"`), a failed delete from the store's `failure`, a second copy from a transaction holding the Project's row lock. The sweeper task is called directly with the controllable clock. Rows and stored files of a deleted Project have no API surface, so tests read them by SQL and from the in-memory store, as the existing deletion tests do. Tests: `backend/tests/integration/test_project_deletion.py`, one Visitor case in `backend/tests/integration/test_embed.py`, and `frontend/apps/studio/src/projects/ProjectsPage.test.tsx` / `ProjectPage.test.tsx`.

1. **The request records the mark and who asked, and returns as before.** Migration `0068_project_deletions` (renumbered from 0067 at the wave-8 integration) adds `projects.deletion_requested_at` and `deletion_requested_by` (members, `SET NULL`). `service.request_deletion` locks the Project, checks it is archived and the name typed, sets both and commits, then the route sends `projects.delete` and answers `202` with no body, as before. The Audit Event is recorded as the requester at the request time, read from the row. Asking again while Deleting is accepted and keeps the first requester. Tests: `test_a_project_shows_as_deleting_at_once_and_is_gone_after_a_lost_job_is_swept`, `test_deletion_is_an_audit_event` (unchanged), `test_asking_again_while_deleting_is_accepted_and_keeps_who_asked_first`, and the existing refusals (`test_only_an_archived_project_can_be_deleted`, `test_the_project_name_must_be_typed_exactly`, `test_refused_deletions_record_no_audit_event_and_delete_nothing`).
2. **A Deleting Project is out of lists and refuses changes, restoring and Visitors with a reason.** It stays archived, so the main list (the Studio's Projects list and every picker built on it) leaves it out. `active_project` raises `ProjectDeletingError`, a `ProjectArchivedError`, so every route that refuses an archived Project refuses it; the app's HTTP error handler `projects.api.refuse_with_the_reason` gives the reason "This Project is being deleted. A deleted Project can't be restored." for those refusals, and restoring answers it with `409`. Visitors get "This assistant is no longer available." and a `404` for messages. Tests: `test_a_deleting_project_refuses_restoring_and_changes_with_the_reason` (restore, rename, upload, Tag; an archived Project not being deleted keeps the archived reason), `test_a_deleting_projects_agents_answer_no_visitor`.
3. **One transaction deletes the rows and writes the prefix; the sweeper removes the files.** `service.delete_project` records `project.deleted`, deletes the Project (the foreign keys cascade) and calls `deletions.schedule(..., prefix=True)` with `organisations/<org>/projects/<project>/`, then commits; the task drains the Deletions table. Tests: `test_deletion_cascades_to_everything_in_the_project` (unchanged), `test_files_whose_first_delete_failed_are_deleted_by_the_next_sweep`.
4. **A lost message or a dead worker is finished by the sweeper.** Each sweep runs `service.finish_deletions()` before draining the table. Lost message (or a worker that died before the cascade committed, which leaves the same state): `test_a_project_shows_as_deleting_at_once_and_is_gone_after_a_lost_job_is_swept`. Died after the commit, at the storage delete: `test_a_worker_killed_after_the_rows_go_leaves_the_files_to_the_next_sweep`.
5. **Twice, or two copies at once, is harmless.** The cascade takes the row `FOR UPDATE SKIP LOCKED` and does nothing unless the Project is still Deleting. Tests: `test_running_the_cascade_again_does_nothing`, `test_a_second_copy_skips_the_project_the_first_is_deleting` (a copy and a sweep pass a held Project by; it is then deleted once, one Audit Event), `test_the_cascade_leaves_a_project_whose_deletion_was_never_asked_for`, `test_a_cascade_sent_with_who_asked_and_when_is_still_run`.
6. **The archived Projects view shows Deleting; the confirmation says it can't be restored.** `ProjectOut.deleting`; the archived table shows a **Deleting** badge in place of Restore, a Deleting Project's page shows a notice and no actions, and the dialog reads "… for good. A deleted Project can't be restored." Tests: `a Deleting Project is listed among the archived ones as Deleting, with no Restore`, `an Owner permanently deletes an archived Project from the ⋯ menu after typing its name` (now ends on the Deleting row), `a Deleting Project's page says it is being deleted and offers nothing to do`.
7. **Only Owners; another Organisation's Project is unreachable.** Unchanged `OwnerScope`: `test_editors_cannot_delete_a_project`; new `test_another_organisations_project_cannot_be_deleted` (404 through the stranger's Organisation, refused through the owner's, and the Project is not Deleting).
8. **Design system.** The badge is a new `Badge` kind (`deleting`, danger tokens), the notice is the shared `Notice` (`warning`). No palette classes or `dark:`; `pnpm palette-ratchet` passes (0 uses).
9. **Tests and coverage.** All new behaviour is tested at the seams above. Every line and branch of the changed backend modules (`app/projects/service.py`, `tasks.py`, `models.py`, the new code in `api.py`, `app/jobs/tasks.py`, `app/main.py`) is covered by the targeted run; the frontend suite runs with its 100% thresholds.
10. **Glossary and ADRs.** `GLOSSARY.md` already defines **Deleting** under Project (added with the spec), so no new term. ADR-0020 gains a paragraph on why a Project deletion uses the deleting mark and a `SKIP LOCKED` one-transaction cascade instead of a claim and heartbeat. `docs/development.md` gains a "Deleting a Project" paragraph, and its permanent-deletion and sweeper entries are updated.

## Gaps and best guesses

- **Best guess:** the sweeper finishes a Deleting Project at once, with no queued-too-long wait. `SKIP LOCKED` keeps it off a Project a live cascade holds, and running twice is harmless, as with the Deletions table drain (21-09).
- **Best guess:** no claim or heartbeat columns: the cascade is a single transaction with no outside call, so a dead worker's transaction rolls back and its lock goes with its connection. Recorded in ADR-0020.
- **Best guess:** a Deleting Project's refusals keep the routes' existing `except ProjectArchivedError` handling; one app-level HTTP error handler swaps in the Deleting reason when the refusal was raised while handling `ProjectDeletingError` (the exception's context). This avoids touching some forty route handlers.
- **Best guess:** asking to delete a Project already Deleting answers `202` and keeps the first requester and time. The message now carries only the Project ID; the task ignores the extra arguments older messages carry.
- **Best guess:** a Deleting Project's page stays readable (as an archived one is) and shows a notice; no Restore or Delete is offered.
- **Migration numbering:** `0068_project_deletions` (renumbered from 0067 at the wave-8 integration) revises `0067_suggestion_run_claims`; it is the alembic head.
- **Local run:** targeted backend tests (project deletion, projects, embed, deleted files, the interrupted-job and alert-email sweeper tests, migrations, OpenAPI, job publisher, worker entrypoint, ingestion limits, seed, documents, embedding models) pass; ruff, ruff format, mypy, `make check-client`, `make link-check`, frontend lint, typecheck, tests and palette ratchet pass. The full backend suite runs at integration.
