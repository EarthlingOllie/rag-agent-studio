# 03: Tracer: interrupted ingestion restarts

**Ticket:** `21-03` · **Spec:** [Job reliability](../../specs/21-job-reliability-spec.md)

**What to build:** A Document whose ingestion was cut short, or that was saved but never reached the queue, goes back to Queued and becomes Ready without anyone doing anything. This builds the claim, the heartbeat and the sweeper that every later ticket adds a policy to.

**Blocked by:**
- `21-01`

**Status:** done

- [x] A job reliability module holds the claim, the heartbeat and the sweeper; a job type supplies only its policy (what counts as queued and in progress, and what to do with a stale row). Ingestion is its first job type
- [x] Ingestion claims its row with one conditional update: a Queued row, or a Processing row whose heartbeat is stale. A job that can't claim exits without doing anything
- [x] While it holds the claim, a job writes a heartbeat every 30 seconds, including during conversion and embedding
- [x] The final write and the settle step check the job still holds the claim, so an older copy that is somehow still running can't write the Document
- [x] A sweeper task runs every minute from Beat and once when a worker starts, under an advisory lock so two never overlap
- [x] The sweeper re-sends a Document or staged edition that has been Queued for more than 15 minutes
- [x] The sweeper returns a Processing Document or staged edition with no heartbeat for 5 minutes to Queued and re-sends it; the Studio shows it as Queued and then Ready
- [x] A replaced Document whose new edition was interrupted is ingested again while its current edition keeps answering
- [x] An ingestion that restarts leaves exactly one set of Chunks; a job delivered twice, or run as two copies at once, produces one result
- [x] Documents already stuck on Processing or Queued when this ships are recovered by the first sweep
- [x] The heartbeat interval, the dead-after time and the queued-too-long time are settings with the defaults above
- [x] Each recovery is recorded in the traces with the job, its identifier and the reason
- [x] Celery runs with a prefetch of one and late acknowledgement; requeue-on-worker-lost stays off
- [x] The adapter fakes (converter, embedder, object store) gain a hook that aborts a job at a chosen point without running its error handling; tests use it with the controllable clock and call the sweeper directly
- [x] The test that asserts the Beat schedule and the task list includes the sweeper
- [x] Tests cover the new behaviour at the highest seam (see [shared test seams](../../specs/README.md#shared-test-seams)); 100% line and branch coverage holds
- [x] New domain terms are added to `GLOSSARY.md`; ADRs updated if a decision changed

## Evidence

Seams: the API seam with the task seam, as the [shared test seams](../../specs/README.md#shared-test-seams) name them. Ingestion starts through the upload, replace and confirm routes; a kill comes from an adapter fake's kill switch, a lost or held message from the Job publisher fake (`jobs` fixture), and the sweeper task is called directly with the controllable clock (`clock` fixture). Outcomes are read through the Documents and Chunks endpoints and the traces. New tests: `backend/tests/integration/test_interrupted_ingestion.py`; `backend/tests/integration/test_worker_entrypoint.py` gains three.

1. **One module, a policy per job type.** `backend/app/jobs/reliability.py` holds `claim`, `holds`, `heartbeat` and `sweep`. A job type supplies a `JobPolicy`: its `JobTable`s (mapped class, key, queued and in-progress statuses), `recover` for a stale row and `resend`. Ingestion's is `backend/app/documents/jobs.py` (`INGESTION` over `documents` and `staged_editions`); the sweeper task lists it in `POLICIES` (`backend/app/jobs/tasks.py`). Job code never reads the heartbeat columns.
2. **One conditional update claims.** `reliability.claim` is a single `UPDATE … WHERE status = queued OR (status = processing AND heartbeat stale) RETURNING`, which sets a new `claim_id` and counts the attempt. `pipeline._start` claims the Document, else its staged edition, and returns `None` when neither is claimable. Tests: `test_a_job_delivered_again_after_it_finished_does_nothing`, `test_a_second_copy_of_a_running_job_exits_without_doing_anything` (the second copy never reaches the converter).
3. **Heartbeat every 30 s while the claim is held.** `reliability.heartbeat` wraps everything after the claim in `pipeline.ingest`: conversion, which runs in a thread, embedding and the final write. `test_a_live_job_keeps_writing_heartbeats_so_the_sweeper_leaves_it_alone` holds conversion, moves the clock 10 minutes and sweeps: nothing is recovered and the Document becomes Ready after one conversion. With beats switched off (interval 3600 s) the same test fails, as it should.
4. **Final write and settle check the claim.** `holds()` locks the row and checks its `claim_id` before the Chunks are written (`_ingest_claimed`) and in `_settle` (Failed, or Queued for a retry). Tests: `test_an_older_copy_still_running_after_a_restart_cannot_write_the_document` (the restarted copy's Chunks are kept, same IDs) and `test_an_older_copy_that_fails_after_a_restart_cannot_mark_the_document_failed`.
5. **Sweeper every minute, at worker start, under an advisory lock.** The Beat entry `job-sweeper` runs `jobs.sweep` every 60 s. `worker_ready` in `backend/app/worker/main.py` sends it once through the Job publisher (`JobPublisher.sweep`). `pg_try_advisory_lock` guards each sweep. Tests: `test_beat_schedules_…_and_sweeper`, `test_a_worker_that_starts_sends_the_job_sweeper_once`, and `test_two_sweeps_never_overlap` (a second sweep during the first returns `None` and sends nothing).
6. **Queued over 15 minutes is sent again.** `test_a_document_that_never_reached_the_queue_is_sent_again_after_fifteen_minutes` checks that nothing is sent at 14 minutes and the job is sent at 15. `test_a_resent_job_lost_again_is_sent_again_fifteen_minutes_later` shows `queued_at` restarts on each send. `test_a_replacement_that_never_reached_the_queue_is_sent_again` covers the staged edition.
7. **Processing without a heartbeat for 5 minutes goes back to Queued and is sent again.** `test_a_document_whose_worker_died_goes_back_to_queued_and_becomes_ready` kills the job at the converter, the embedder and the object store's write. At 4:59 it is left alone. After 5 minutes it is swept, and the API shows Queued (resend held), then Ready once the job is released.
8. **An interrupted replacement is ingested again while the current edition answers.** `test_a_replaced_document_whose_new_edition_was_interrupted_is_ingested_again`: the replacement is processing while the Document is Ready and serves its 2026 Chunks. After the sweep it is edition 2 with the 2027 Chunks.
9. **Exactly one set of Chunks; twice-safe.** After a restart each test above lists exactly the expected Chunks; leftovers of the edition are deleted before the write. Delivered twice: nothing changes. Two copies at once: the second exits. An older copy: its write is refused (items 2 and 4).
10. **Rows stuck before this shipped.** Migration `0069_ingestion_claims` adds `queued_at`, `claim_id` and `heartbeat_at` to both tables. For rows already Queued or Processing it takes their `updated_at` as those times. The sweeper also treats a missing time as stale. `test_documents_stuck_before_the_sweeper_shipped_are_recovered_by_the_first_sweep` builds both shapes and one sweep makes both Ready. The upgrade and downgrade round trip (`test_migrations.py`) covers the migration.
11. **Settings.** `JOB_HEARTBEAT_SECONDS` (30), `JOB_DEAD_AFTER_SECONDS` (300) and `JOB_QUEUED_TOO_LONG_SECONDS` (900) live in `backend/app/core/settings.py` and are read as `Timings.from_settings`. Test: `test_the_thresholds_are_settings_with_their_defaults`.
12. **Traces.** Each recovery is a Logfire log span `Sweeper recovered {job} {job_id}: {reason}` with attributes `job`, `job_id` and `reason` (`no heartbeat` or `queued too long`). The kill and lost-message tests read them from an in-memory span exporter.
13. **Celery settings.** `worker_prefetch_multiplier=1`, `task_acks_late=True`, `task_reject_on_worker_lost=False` in `configure_celery`. Test: `test_celery_takes_one_message_at_a_time_acknowledges_late_and_never_requeues_a_lost_one`.
14. **Kill hook.** `backend/app/jobs/faults.py` defines `KillSwitch` and `JobKilled`, a `BaseException`, so `except Exception` handlers don't run. The switch sits on `FakeConverter` (`"convert"`), `HashEmbedder` (`"embed"`) and `InMemoryObjectStore` (`"put"`). The `jobs` fake swallows `JobKilled` where it delivers a job (`jobs.killed`). Tests use it with the controllable clock and call `sweep_jobs` directly.
15. **Beat and task list test.** `test_beat_schedules_the_health_check_budget_alert_reset_usage_rollup_purge_and_sweeper` asserts `jobs.sweep` in the schedule at 60 s and `app.jobs.tasks` in the includes.
16. **Seams and coverage.** Every test above runs at the API seam with the task seam. The new and changed modules (`app/jobs/*`, `app/documents/jobs.py`, `pipeline.py`, `tasks.py`, `app/worker/*`) have every line and branch run by the suite; see Gaps for the sandbox's coverage run.
17. **Glossary and ADRs.** `GLOSSARY.md` already says, under Document status (amended with the spec), that a Document whose ingestion is cut short goes back to Queued and is ingested again. The claim, heartbeat and sweeper are ADR-0020's mechanism, not domain terms, so the glossary is unchanged. ADR-0020 is unchanged; this ticket applies it. `docs/development.md` gains a "Job reliability" paragraph and a sweeper row under Scheduled jobs, and the shared test seams name the kill switches.
18. **The sweeper tests see only their own rows.** The test database is shared by the tests a worker runs, and every controllable clock starts at the same time, so a row an earlier test left Queued or Processing would be recovered by these tests' sweeps too and change their counts. The autouse fixture `no_jobs_left_by_earlier_tests` in `test_interrupted_ingestion.py` settles such rows as Failed before each test there. To check it, a stale Queued and a stale Processing Document were planted in each xdist worker database. Without the fixture, `pytest -n 3 tests/integration/test_interrupted_ingestion.py` failed 6 tests. With it, five runs of that file plus `test_worker_entrypoint.py` under `-n 3`, each on freshly planted rows, all passed (23 passed each time). The same files also passed straight after a full suite run, on the databases it left behind.

## Gaps and best guesses

- **Best guess:** a stale row is recognised by its heartbeat time, and a row with no heartbeat or queued time at all counts as stale too. The migration backfills those times from `updated_at`, so "the same rules" apply to rows stuck before this shipped.
- **Best guess:** after a resend, `queued_at` restarts, so a job whose message keeps getting lost is sent at most once every 15 minutes, not every minute.
- **Best guess:** the sweeper sends the job again for every stale row it recovers. A later job type whose recovery doesn't queue the row (paid jobs, ending Interrupted) gets a message that finds nothing to claim (ADR-0020: re-sending is always safe). Its ticket can add a "don't resend" branch with its own test.
- **Best guess:** if writing a heartbeat ever raises, the beats stop. The sweeper later takes the job for dead, which is safe: it is restarted and the old copy loses its claim. No retry loop was added.
- **Best guess:** the kill switch fakes a kill at the object store's write (storing the converted markdown), not at its read. The API's confirm also reads the object, so a read kill would fire in the request, not the job.
- **Out of this ticket (21-04):** the interruption cap, the `interrupted` Failure category, the conversion limit and durable retry times. Until 21-04, an edition that keeps being interrupted restarts every time.
- **Out of this ticket (21-09):** follow-on work after a new edition (deleting the old edition's files, re-checking Expected sources) when the worker dies right after the swap.
- **Not done here:** the Playwright journey the spec's testing decisions mention. It is not one of this ticket's criteria.
- **Local run:** the sandbox has no Docker. The suite ran in chunks (`run-chunks-w3.sh`) against a local PostgreSQL 16 and Redis. The run on 2026-11-26 after the test-isolation fix (logs in `/var/tmp/pg-21-02/chunks-w3/`, chunks c0 to c3) had 3201 passed (470 + 614 + 525 + 1592). The only failures are the sandbox baseline: 4 failed and 6 errors in `test_object_store` and 1 error in `test_seed` (`rustfs_app`), all because RustFS isn't running. The HNSW probe, flaky under load, passed in this run. The combined coverage report misses only RustFS-only lines. Ruff, ruff format, mypy and `make link-check` pass.
- **Full gate with RustFS (2026-11-26):** the gap above is closed. The whole backend suite ran on the session branch at 85c326c with RustFS up (`docker compose up -d rustfs`), in parts of at most eight integration files under `-n 2` with `--cov-append` (logs in `/var/tmp/pg-21-02/gate-w5/`). 3,232 tests ran and 3,229 passed, and every RustFS test passed. Combined coverage is 100% line and branch, so the gate holds with no RustFS gap. Three tests failed in the parts and passed on their own: two `test_logging.py` server-start timeouts under load, and the retention test `test_without_a_time_the_purge_runs_as_of_now`. That test saw Messages left behind by earlier tests that use a past clock. It is fixed on `wt/gate`, and ticket 21-02 has the details. Nothing in this ticket's code changed.
