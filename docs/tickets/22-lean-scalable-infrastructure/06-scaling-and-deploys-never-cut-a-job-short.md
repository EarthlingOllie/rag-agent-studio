# 06: Scaling and deploys never cut a job short

**Ticket:** `22-06` · **Spec:** [Lean, scalable infrastructure](../../specs/22-lean-scalable-infrastructure-spec.md)

**What to build:** A worker holding a job is protected from scale-in until the job ends, and a deploy waits up to 30 minutes for running jobs before it stops them.

**Blocked by:**
- `22-04`

**Status:** done

- [x] A Scale-in protection port: the production adapter calls the ECS task-protection endpoint, the fake records calls, and a no-op adapter is used where there is no ECS (local, tests)
- [x] The job reliability module sets protection when a job is claimed, renews it with the heartbeat and clears it when the job finishes, fails or is abandoned
- [x] Protection carries an expiry a few minutes ahead, so a dead worker is never protected for ever
- [x] A failure to set or clear protection is logged and never fails the job
- [x] Worker task roles may set protection on their own task only
- [x] After starting a roll, the deploy script waits up to 30 minutes for protected tasks, then clears protection on the old tasks and lets the roll complete; the limit is an argument
- [x] The deploy role may read and clear task protection in this project's cluster only
- [x] Task-seam tests with the fake assert protect, renew and release, including when the job fails
- [x] The deploy scripts' tests cover the wait and clearing protection after it
- [x] The fake is listed with the other ports in the shared test seams
- [x] Tests cover the new behaviour at the highest seam (see [shared test seams](../../specs/README.md#shared-test-seams)); 100% line and branch coverage holds

## Gaps and best guesses

- **Deferred (needs a live deploy, ticket 22-09):** that the ECS agent's endpoint accepts the calls with the pool's task role (in particular that `ecs:UpdateTaskProtection` honours the `aws:ResourceTag/Name` condition on the propagated tag; if it does not, protection fails, is logged, and jobs still run), that a scale-in really skips a protected task, that a deploy's old protected tasks keep running until their jobs end or the wait clears them, and that the deploy role can list, read and clear protection with these permissions. None of this can be shown offline.
- **Protection follows the heartbeat.** It is set when the job's heartbeat starts, which every heartbeating job does right after taking its claim, and released when the heartbeat block ends. Live Verdicts have no heartbeat (under two minutes, inside the workers' two-minute stop timeout) and the sweeper and deletion jobs are short, so they are not protected.
- **Several jobs per task.** ECS protects a task, not a job, and a worker runs two jobs at once in separate processes. The adapter keeps one file per holding claim in the task's `/tmp` and clears protection only when no other claim's file is younger than the expiry; a process killed without releasing leaves a file that stops counting after the expiry.
- **The wait looks only at worker pools.** The API and Beat never set protection, so the script does not ask about their tasks. `get-task-protection` takes at most ten tasks per call; a pool has at most three by default.
- **A deploy whose wait clears protection** interrupts the jobs still running on old tasks. They are then restarted (ingestion, Re-embeds) or ended as interrupted (Runs) by the sweeper, as after any worker death (ADR-0020).
