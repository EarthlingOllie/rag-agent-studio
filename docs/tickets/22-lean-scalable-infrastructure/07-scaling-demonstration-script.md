**Ticket:** `22-07` · **Spec:** [Lean, scalable infrastructure](../../specs/22-lean-scalable-infrastructure-spec.md)

**What to build:** One script puts real work on a deployed, seeded demo and prints a timeline of each service scaling out and back in, so the scaling can be shown and repeated.

**Blocked by:**
- `22-05`

## Evidence

Seam: the deploy scripts' tests (`make infra-check`), as the ticket and spec 22's testing decisions say. `scripts/deploy/tests/scale.test.sh` runs the real `scripts/deploy/scale.sh` with the stubbed `terraform` and `aws` (`scripts/deploy/tests/stubs`; `aws` answers each poll from a timeline file, one line of task counts and queue depths per poll) and a stubbed Studio API, `scripts/deploy/tests/fake_api.py`, a local HTTP server that answers the routes each case gives (sign-in, Projects, uploads and the presigned PUT, Agents, Runs, archive, delete) and logs every request with its session cookie and body, so the real `curl` calls run. `sleep` is stubbed except in the interruption case. Nothing calls AWS. The spec's "Node test runner suite" for the deploy scripts is in fact these shell tests (the Node runner covers only the module functions), so the new tests sit with the other deploy script tests.

TDD ([tdd-red.log](22-07-evidence/tdd-red.log)): the demo environment's deploy-output assertion and `scale.test.sh` were written first and failed (the output had no job queues; the script did not exist); the script then grew case by case until all 36 cases passed. [stub-timeline.md](22-07-evidence/stub-timeline.md) shows the output of the happy-path case (stubs, not AWS).

1. **Takes the Studio URL and Owner credentials and needs a seeded demo.** `scale.sh [options] <Studio URL>` with `OWNER_EMAIL` and `OWNER_PASSWORD` in the environment (not on the command line, where `ps` would show the password), plus `TF_STATE_BUCKET` and `AWS_REGION` to read the deploy output as `seed.sh` does. It signs in through `POST /api/auth/sign-in` and refuses an MFA challenge or a Member who is not an Owner of their Organisation; without seeded Agents it stops with "seed the demo first (scripts/deploy/seed.sh)". Tests: `fails_when_the_owner_cannot_sign_in`, `fails_when_the_owner_uses_mfa`, `fails_when_the_member_is_not_an_owner`, `fails_when_the_demo_is_not_seeded`, `fails_when_the_studio_is_unreachable`, `rejects_bad_arguments` (8 cases), `needs_<variable>` (4), `fails_when_the_environment_is_not_deployed`, `fails_when_the_deploy_output_has_no_job_queues`, `fails_when_a_service_has_no_scalable_target`.
2. **Creates a throwaway Project, uploads the seed Documents several times under different names, starts Evaluation Runs on seeded Agents and sends API requests for a few minutes.** The Project is `Scaling demonstration <UTC time>`. Each file in `seed/documents` is uploaded `--copies` times as `scale-<n>-<file>` through the Studio's own flow (start upload, PUT to the presigned URL, confirm). A Project refuses a file whose content it already holds, so each copy is made different: a comment appended to text files and PDFs, the archive comment set on Office files (still a valid zip). Runs are started on every unarchived Agent of the other unarchived Projects at each poll of the load: an Agent with a Run in progress (409 with the conflict) is asked again later, any other refusal (an empty Evaluation Set) drops it with the reason, up to `--runs` in all. `--api-workers` loops send `GET /api/organisations/<id>/projects` for `--api-seconds`. Tests: `puts_work_on_the_demo_and_prints_a_timeline_until_every_service_is_back_at_its_minimum` (20 uploads by default, named copies 1-5 of each seed file, 20 different file contents, none the seed file unchanged, every request after sign-in carries the session, Runs on the HR helper only, API traffic), `takes_the_copies_and_runs_as_arguments`, `copies_pdf_and_text_documents_too`, `refuses_a_document_it_cannot_copy`, `fails_and_cleans_up_when_an_upload_is_refused`, `fails_and_cleans_up_when_the_presigned_upload_fails`, `fails_when_the_project_cannot_be_created`.
3. **Polls ECS and CloudWatch and prints a timeline of queue depth and running tasks per service until every service is back at its minimum.** Minimums come from `aws application-autoscaling describe-scalable-targets`. Every `--poll-seconds` it reads `aws ecs describe-services` (running and desired tasks of `api`, `worker-general`, `worker-runs`) and `aws cloudwatch get-metric-data` (each queue's latest one-minute maximum of `ApproximateNumberOfMessagesVisible` and `...NotVisible`) and prints a row: time, elapsed, `waiting+in flight` per queue (`-` when CloudWatch has no data point, counted as empty as the scaling alarms do), `running/desired` per service. It stops once the load is over and every service is at its minimum (running and desired) with both queues empty, then prints each service's minimum, peak and final count. The cluster, services and queue names come from `terraform output -json deploy`, which gained `queue_names` (`infra/envs/demo/outputs.tf`; asserted in `demo.tftest.hcl` `outputs_everything_the_deploy_workflow_needs`). Tests: the happy path (the exact read-only calls, one poll per timeline line, rows including one without data, the summary), `a_longer_load_keeps_polling_while_it_lasts`, `a_queue_still_holding_jobs_keeps_it_polling`.
4. **Deletes its Project when it finishes or is interrupted.** An EXIT trap (INT and TERM exit through it) stops the API loops, archives the Project and deletes it with its name as `confirm_name`, and says so; if the delete is refused it fails with "Archive and delete it in the Studio". A failure or interruption also cancels the Runs it started. Tests: every case that got as far as the Project checks it was archived and then deleted, `deletes_its_project_and_cancels_its_runs_when_interrupted` (SIGTERM mid-timeline; the API traffic stops too), `says_so_when_its_project_could_not_be_deleted`, and the cancellation in `fails_naming_the_runs_pool_when_it_never_scaled_out`.
5. **Exits non-zero, saying which service, if a pool or the API never scaled out.** A service whose running tasks never rose above its minimum fails with `::error title=Did not scale out::<service> never scaled out: it stayed at <n> task(s).`; a desired count alone does not count. One still above its minimum at `--timeout-minutes` fails with `Did not scale in` naming it. Tests: `fails_naming_the_runs_pool_when_it_never_scaled_out`, `fails_naming_the_api_when_it_never_scaled_out`, `a_desired_count_alone_is_not_a_scale_out`, `fails_naming_the_service_that_never_came_back_to_its_minimum`.
6. **Load sizes and durations are arguments with defaults that finish in about fifteen minutes.** `--copies 5`, `--runs 3`, `--api-seconds 300`, `--api-workers 8`, `--poll-seconds 30`, `--timeout-minutes 25`: five minutes of load, then the pools' five idle minutes plus cooldowns with the module's defaults. Tests: `shows_its_defaults_in_the_usage`, `takes_the_copies_and_runs_as_arguments`, and the happy path runs the default copies.
7. **The deploy scripts' tests, with a stubbed `aws` and a stubbed API, cover the timeline and the clean-up.** Rows 3 and 4; `scale.test.sh` is in `make infra-check` next to the other deploy script tests.

## Gaps and best guesses

- **Deferred to 22-09 (needs a real deploy):** the script against real AWS and a real seeded demo: the presigned uploads through S3, the IAM read permissions of whoever runs it (`application-autoscaling:DescribeScalableTargets`, `ecs:DescribeServices`, `cloudwatch:GetMetricData`), CloudWatch's lag on SQS metrics, the timing of the defaults, and the timeline that shows each service scale out and back.
- **About fifteen minutes is a best guess.** The API's target-tracking scale-in waits for fifteen one-minute datapoints below target by AWS's design, so the API may be the last back and a run can take closer to twenty minutes; `--timeout-minutes` defaults to 25 to allow for it.
- **Few Runs.** The seeded demo has one Agent with an Evaluation Set (the HR helper), and an Agent takes one Run at a time, so the script keeps asking at each poll of the load and starts the next Run when the last has finished, up to `--runs`. With the Demo model a Run is quick, so the runs pool shows a step from zero to one rather than to two; a busier runs pool would need Agents with Evaluation Sets in the throwaway Project, which the ticket does not ask for.
- **The Runs are not in the throwaway Project.** They run on the seeded Agents (as the ticket says), so they stay in those Agents' Evaluation history after the Project is deleted; finished Runs are not cancelled, only those still in progress after a failure or interruption.
- **Configuration from the deploy output.** The cluster, services and queue names come from `terraform output -json deploy` (new `queue_names`) as `seed.sh` reads it; the minimums come from the scalable targets themselves, so a changed `scaling` input is picked up without a new output.
- **Unique copies.** Office copies get a different zip archive comment, a valid zip whose parts are unchanged; PDFs get a trailing comment after `%%EOF`, which readers tolerate. Ingesting them through Docling on AWS is part of 22-09.
- **The guide's "showing it scale" section** belongs to ticket 22-08, which documents how to run this script and read its timeline; this ticket adds the development guide paragraph only.
