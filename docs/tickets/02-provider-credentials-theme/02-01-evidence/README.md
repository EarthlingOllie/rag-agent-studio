## Decisions and notes (best guesses recorded instead of asking)

- **A failed check on add stores nothing.** The Owner gets 400 with the reason, and a `credential.check_failed` event is recorded with no target ID. A failed rotation keeps the old key. A failed re-check is stored on the credential, which then shows "Check failed".
- **Bedrock is in the registry but not in this ticket's add route.** It can't be added yet; `provider` accepts only anthropic, openai or voyage, and Bedrock credentials arrive with 02-02. `region`, and the `aws_role` and `aws_access_keys` auth kinds, are modelled ready for it.
- **Capabilities.** By default a credential gets every capability its provider offers. An Owner may choose a subset. They are always stored in the registry's order.
- **Masked suffix** is the last 4 characters. Keys must be 8 to 512 characters with no whitespace. Surrounding whitespace is trimmed.
- **Editors read the same `CredentialOut` as Owners.** That includes the masked suffix, which isn't secret.
- **Plain strings, not Postgres enums,** for provider, auth kind and status, so new providers need no enum migration. The API types them as enums.
- **The live verifier's calls.** It uses the cheapest authenticated call each provider offers: list models (no tokens) for Anthropic and OpenAI, and a one-string embed with `voyage-3.5-lite` for Voyage. A 400 or 5xx answer counts as `provider_unreachable`.
- **The registry's model IDs** are a best-effort list. 02-04 adds prices alongside them.
- **KMS calls are synchronous boto3** inside the sync envelope API, as in the SES mailer's blocking style. Seal and open happen per request, so this blocks the event loop briefly in AWS. A follow-up could move it to a thread.
- **Studio failure messages** come from the typed `reason`, not from the API's `detail`, so the Studio controls the wording.
