## Decisions and notes (best guesses recorded instead of asking)

- **A check reuses a cached session.** The verifier uses the session cache too, so a re-check within the session's life doesn't call `AssumeRole` again. That matches the criterion, and it is honest: AWS doesn't revoke sessions already issued when a trust policy changes, so the cached session is exactly what the platform can use. A newly added credential always assumes its role, because nothing is cached for it yet.
- **Model access is checked with `GetFoundationModelAvailability`**, not a real model call: it costs nothing and separates "not in this region" from "not authorised". The model checked is the first model of the credential's first capability in the registry (chat: Claude Sonnet 4.5; embeddings: Titan Text Embeddings V2; rerank: Cohere Rerank 3.5).
- **STS runs in one platform region** (`BEDROCK_STS_REGION`, default `us-east-1`); Bedrock runs in the credential's region. So when STS answers and Bedrock's endpoint can't be reached, the region is blamed (`wrong_region`) rather than the network.
- **The masked suffix of an access-key credential** is the end of the access key ID, which the Owner can match in the IAM console; the secret access key shows nothing. A role credential has no suffix and shows "IAM role" with its ARN.
- **Bedrock credentials aren't rotated with an API key.** `POST …/rotate` answers 422 ("Add a new Bedrock credential, then delete this one"), and the Studio hides "Rotate key" for them. Rotating access keys in place could be added later.
- **The setup endpoint is Owner-only**, like adding a credential. AWS doesn't treat an external ID as a secret, but only Owners need it.
- **The platform principal** defaults to a placeholder (`arn:aws:iam::000000000000:role/rag-agent-studio-local`) because `docker compose` has no AWS identity; in AWS it should be the API's task role ARN.
- **Role ARNs** are validated for any AWS partition and IAM path; regions by AWS region shape (`xx-name-N`), not against a fixed list, so new regions work and a region without Bedrock is reported as `wrong_region` by the check.
- **boto3 calls run in a worker thread** (`asyncio.to_thread`), with the check timeout and no retries.
- **Typing.** No `boto3-stubs` extras were added for STS or Bedrock (the clients are typed `Any` behind a small factory), to avoid touching `uv.lock` while other tickets build in parallel.

## Gaps and sandbox notes

- **No real AWS account, role or credentials.** STS and Bedrock are proven only with botocore `Stubber` (requests validated against the service models) and event hooks that simulate unreachable endpoints. Not proven against AWS: that `AssumeRole` with this trust policy succeeds, that the IAM action `bedrock:GetFoundationModelAvailability` is the right one to grant, and the exact error codes Bedrock returns for an unenabled model or region. No `@pytest.mark.live` test is included.
- **`BEDROCK_PLATFORM_PRINCIPAL` is not wired into Terraform.** The compute module (09-04) should pass the API task role's ARN; that belongs to the deploy work, not this ticket.
- **Bedrock model calls are not built.** 02-03's gateway expected 02-02 to build Bedrock clients; this ticket's criteria cover storing and checking credentials only, so the gateway refuses Bedrock (role credentials explicitly, access keys in the live adapters). A follow-up should build Bedrock chat, embeddings and rerank adapters on `LiveCredentialVerifier.bedrock.sessions`.
- **Migration numbering.** Resolved at merge: `0009_bedrock_credentials` follows `0008_default_models`. A ticket merged later that also branches from `0008_default_models` must re-parent.
- **Images and stack.** Images were built from the committed Dockerfiles with only the sandbox proxy CA and proxy environment added to the first stage ([build.sh](build.sh)); the stack ran as project `rag0202` with [compose.sandbox.yml](compose.sandbox.yml) (Studio `51173`, API `51800`, Mailpit `51825`). Chrome came from `/usr/bin/google-chrome`. Trivy (`make image-scan`) was not run (disk nearly full, shared by parallel tickets).
- **Flaky Studio test under load.** In the worktree, while the backend suite ran in parallel, `AcceptInvitePage.test.tsx`'s first test (unrelated to this ticket) timed out twice on its first `findByRole`. It passes alone, and the logged clean-clone run (no parallel load) passed 255/255. The 02-01 evidence records the same flake.
- **Screenshots** were taken by [shots.mjs](shots.mjs) against the running stack (its Playwright import was pointed at the clone's `@playwright/test` when it ran).
