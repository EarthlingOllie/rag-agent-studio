# Evidence: ticket 01-07, mailer, password reset and change password

Branch `ticket/01-07-mailer-password-reset`. The code is at commit `d715317`, the last code change. The commit after it only adds this folder and the ticket status. The logs come from a fresh `git clone` of the branch at `d715317`, except `mutation-proof.log`, which ran in the branch worktree at the same commit. Postgres+pgvector and Redis came from the running `docker compose` services. Other ticket builds shared those services, so the tests used their own database and Redis DB (`TEST_DATABASE_URL=…/studio_test_0107c`, `TEST_REDIS_URL=…/10`). Each log starts with its commands and ends with its exit code.

**Seams under test** (spec 01 and the shared test seams). These were picked from the spec's testing decisions; there was no one to confirm them with, so this is the recorded choice:
- The **API seam** covers reset, change password, Profile, sessions and Audit Events. It uses the in-process `httpx` client with real Postgres and Redis, the **mailer outbox** fake (`outbox` fixture) and a **controllable clock** (`clock` fixture). Both fixtures are new in `tests/conftest.py`.
- The **mailer adapters** are tested as the port's adapters. SMTP is tested through the API against a local SMTP sink (`aiosmtpd`, standing in for Mailpit). SES is tested against botocore's `Stubber`, which checks the request against the SES v2 API model. No AWS call is made.
- The **network seam** covers the forgot-password, reset-password and Profile screens: Testing Library with MSW, using handlers typed by the generated client.
- The **end-to-end seam** is Playwright against the compose stack, with Mailpit and axe.

Tests read the database directly in two places only, because neither has an API surface on this branch: reset tokens stored as hashes, and Audit Events. The Audit Event list endpoint arrives with 01-05.

## Decisions and notes (best guesses recorded instead of asking)

- **01-05 runs in parallel, and the audit module overlaps it.** 01-07 is blocked only by 01-04, but criterion 5 needs the audit `record` operation and the `audit_events` table that 01-05 builds. This branch carries a minimal version of both, written so they merge with 01-05 with as few conflicts as possible:
  - `app/audit/__init__.py`, `app/audit/models.py` and migration `20261105_0003_audit_events.py` (revision `0003_audit`) are copied unchanged from 01-05's work in progress, so git can merge them as identical additions.
  - `app/audit/service.py` keeps only `AuditTarget` and `record`, with 01-05's signature. Redaction, the list endpoint, facets and the Audit tab are 01-05's.
  - This ticket's own migration is `0004_password_reset`, and it revises `0003_audit`.
  - Whichever of 01-05 and 01-07 merges second takes 01-05's `app/audit/service.py` and keeps the 0003 → 0004 chain. If 01-05 renames its revision, `0004_password_reset.down_revision` must follow it.
- **Email is sent from the API process** (a FastAPI background task after the response), not from the Celery worker that plan section 2 lists for "email send". That keeps the outbox fake in-process for API-seam tests, and keeps the reset token out of the broker. Moving it to a Celery task later doesn't change the port.
- **Reset tokens are in Postgres** (`password_reset_tokens`, a platform-level table added to `PLATFORM_TABLES`), not Redis. The single-use check is one atomic `UPDATE … RETURNING`, and expiry is checked against the clock port, so tests control it.
- **Link and expiry.** The link is `STUDIO_URL/reset-password?token=…`, with `STUDIO_URL` defaulting to `http://localhost:5173`; compose passes `${STUDIO_URL}` through. Links expire after `PASSWORD_RESET_TTL_SECONDS`, one hour by default.
- **Reset doesn't sign the Member in.** The Member signs in afterwards, which is the spec's e2e flow.
- **Audit scope.** Only completed resets and password changes are audited. Name edits and reset requests are not.
- **Changing a password isn't rate limited.** A wrong current password gets 400. Sign-in rate limiting is 01-06's, and it could extend to this route.
- **"Copyable link for Owners".** Spec 01 says reset emails have an equivalent copyable link for Owners. An Owner-facing "copy reset link" needs Member management, which is 01-09, so it isn't built here.
- **New dependencies.** Runtime: `boto3` (SES). Dev: `aiosmtpd` (the SMTP sink) and `boto3-stubs[sesv2]` (types for `mypy --strict`).

## Gaps and sandbox notes (local and test-double routes used)

- **No real email.** Nothing was sent through AWS SES. The SES adapter is checked only against botocore's Stubber, with fake credentials. All real delivery went to Mailpit or the in-process SMTP sink.
- **Second stack and images.** As in 01-04, the images were built from the committed Dockerfiles. The only addition was the sandbox proxy CA and proxy environment in the first build stage ([mutate.sh](mutate.sh) is the mutation runner; the build used `sb0107/build.sh`, the same as 01-04's). The stack ran as compose project `rag0107` with [compose.sandbox.yml](compose.sandbox.yml), which moves the host ports (Studio `55173`, Mailpit `58025`), with `STUDIO_URL=http://localhost:55173`. `docker-compose.yml` was otherwise used as committed.
- **Chromium.** The sandbox's Chrome was used through `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.
- **gitleaks in CI.** The `security` workflow's full-history gitleaks scan fetches every branch, so it flagged two made-up keys in 01-05's test commit `1595299` (on `origin/ticket/01-05-audit-events`), and failed on `d715317`. 01-05 allowlists them by fingerprint in its `.gitleaksignore`. This branch adds the same two lines, so its scan passes and the change merges as an identical edit.
- **Flaky existing test.** `test_worker_health_is_unavailable_when_no_worker_replies` (01-01) failed once on a Redis DB another build was using. It passed on a private Redis DB and in every logged run.
