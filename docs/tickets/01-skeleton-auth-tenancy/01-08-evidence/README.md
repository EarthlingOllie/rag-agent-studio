## Decisions and notes (best guesses recorded instead of asking)

- **An Invite is bound to its email.** A new account always gets the invited email: the form doesn't ask for one. An existing Member can accept only if their email matches; any other signed-in Member gets 403, and the Invite stays usable. So a forwarded link can't be used by someone else's existing account. A copied link sent by other means still creates an account only for the invited address.
- **Copyable link with hashed tokens.** The raw token exists only in the create and renew answers and in the email. The "always available" link is therefore "New link" (renew): it makes a fresh token and a fresh 7-day expiry and stops the old link working. It doesn't email by default; `send_email: true` does. Renewing is recorded as `invite.renewed`.
- **Invite emails are sent inline,** after the Invite is committed, not as a background task like reset emails. The Owner's answer can then say whether the email went out (`email_sent`), and there's nothing to hide about whether an email is registered: the Owner typed it.
- **Expired Invites stay pending** in the list, marked "Expired", until renewed or revoked. A duplicate Invite for the same email is refused rather than replacing the pending one, so a link the Owner already sent doesn't change silently.
- **Routes.** The invited person's routes are platform-level (`/api/invites/lookup`, `/accept`, `/sign-up`) and take the token in the body. Tokens in bodies stay out of access logs and URL attributes, and the new telemetry scrubbing keeps them out of span bodies too.
  - The lookup's `account_exists` tells only a link holder whether the invited email has an account. The accept page needs it to choose between "create account" and "sign in", and the token is unguessable.
  - Lookups have no rate limit, for the same reason (256-bit tokens).
- **Members tab scope.** 01-09 builds the Members list with roles, role changes and removal. This ticket adds the Members tab for Owners with the invite form and pending Invites only, and Editors don't see the tab. 01-09 can add the Member list above the invites, and decide whether Editors see it.
- **`invites.invited_by_id` is NOT NULL with `ON DELETE CASCADE`.** No feature deletes Members yet, and a pending Invite without its inviter has no clear meaning. `accepted_by_id` is nullable (`SET NULL`).
- **Isolation test order.** `test_another_tenants_resources_are_not_found` now calls the outsider's routes before the owner's own call, so routes that change or remove the resource (revoke, renew) are checked against a resource that still exists. The assertions are unchanged.
- **Sign-in on the accept page** reuses the sign-in page's messages, now exported as `signInErrorMessage` from `auth/SignInPage.tsx`, so 01-06's delay and lockout messages appear there too.
- **Lookup retries.** The accept page doesn't retry a failed lookup (`retry: false`), so a used or revoked link says so immediately rather than after the default retries. This was found by the e2e run.
