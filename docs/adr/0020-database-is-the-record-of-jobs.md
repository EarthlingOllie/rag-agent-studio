# The database is the record of background jobs; the broker only wakes workers

A background job (ingestion, a Re-embed, an Evaluation Run, a Suggestion run, a Live Verdict, a Project deletion, an object deletion) is requested by a row in Postgres, and that row is the only thing that says the job must run. The message on the broker is a wake-up call that may be lost, late or delivered twice. Every job claims its row with one conditional update before it works, writes a heartbeat while it works, and checks it still holds the claim before its final write. One sweeper, run every minute, re-sends rows that have been queued too long and deals with rows whose heartbeat has stopped. Object deletions, which have no row of their own, are written to a small deletions table in the transaction that removes the last reference, and the sweeper drains it.

The guarantee this gives: every requested job either finishes or reaches a visible failed state, whatever dies (a worker, Beat, the API or the broker), and any job can be delivered twice or run as two copies without duplicate rows or spend counted twice. Jobs that cost nothing to redo restart on their own (ingestion, Re-embeds, deletions, the scheduled jobs). Jobs that spend an Organisation's money (Evaluation Runs, Suggestion runs) end as interrupted and are never restarted for the user, because a silent restart pays for the same answers again.

We chose this over relying on the broker (late acknowledgement, redelivery when a worker is lost, a long visibility timeout). The broker can't see a row that was committed but never published, loses everything queued when it restarts, and redelivers a killed job only after its visibility timeout, which a long Evaluation Run can outlast, so a redelivered message can't be read as "the first worker died". We also chose it over a generic jobs table or transactional outbox for every job, which would hold a second copy of state the domain tables already have ("is this Run running?") and replace most of what Celery does.

Don't decide a job was interrupted from a redelivered message; only a stale heartbeat says so. Don't publish a job without a claim that makes the extra message harmless. Don't hold a row lock across a model call to make a job safe twice; use the claim.
