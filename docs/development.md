# Local development

Prerequisites: Docker with Compose v2, GNU Make, [uv](https://docs.astral.sh/uv/) and Node 22 with pnpm (via `corepack enable`). The infrastructure and security gates also need Terraform, TFLint, Checkov, gitleaks and Trivy; `scripts/ci/install-tools.sh terraform tflint checkov gitleaks trivy` installs the pinned, checksum-verified versions CI uses into `~/.local/bin`.

| Command | What it does |
|---|---|
| `make dev` | Builds and starts the whole stack: Postgres with pgvector, Redis, RustFS, Mailpit, the API, the Celery worker, Celery Beat and the Studio. |
| `make install` | Installs backend (`uv sync`) and frontend (`pnpm install`) dependencies on the host. |
| `make services` | Starts only Postgres and Redis, which the backend tests need. |
| `make test` | Backend and frontend tests, each failing below 100% line or branch coverage (ADR-0008). |
| `make lint` | ruff, `mypy --strict`, eslint and `tsc`. |
| `make gen-client` | Regenerates `frontend/packages/api-client` from the backend's OpenAPI schema. |
| `make check-client` | Fails if the committed API client differs from a fresh generation (CI runs this). |
| `make e2e-install` | Installs the Chromium build Playwright uses. |
| `make e2e` | Starts the stack with `docker compose up --wait`, then runs the Playwright suite (fixture checks and the Studio smoke and auth tests with axe). |
| `make infra-check` | `terraform fmt`, `validate`, `terraform test`, TFLint (with the AWS ruleset) and Checkov over `infra/bootstrap`, every module in `infra/modules` and every environment in `infra/envs`, plus the S3 backend check (`infra/tests/backend.test.sh`) and the plan-gate tests (`scripts/ci/tests/plan-gate.test.sh`). No AWS account is needed: `terraform test` uses mocked providers. |
| `make security` | gitleaks over the whole history (`secret-scan`), pip-audit and pnpm audit (`audit`), and a Trivy scan of the built images (`image-scan`). |
| `make images` | Builds the API image (also used by the worker and Beat) and the Studio image. |
| `make eval` | Guardrail evaluation suite; a passing placeholder until ticket 08-07. |

Once `make dev` is up:

- Studio: <http://localhost:5173> (sign up there to create an Organisation; <http://localhost:5173/status> shows API, database, Redis and worker health through the generated client)
- API: <http://localhost:8000/api/health>, OpenAPI docs at <http://localhost:8000/docs>
- Mailpit: <http://localhost:8025>
- RustFS console: <http://localhost:9001>

## Settings

Every backend service reads typed settings from the environment (`backend/app/core/settings.py`) and refuses to start when a required one is missing or invalid, naming the setting:

```
app.core.settings.SettingsError: Invalid service settings. DATABASE_URL: Field required
```

`docker-compose.yml` supplies the local values; `.env.example` lists them.

## Sign-in and tenancy

- **Sessions.** Signing up or in starts a server-side session in Redis (key `session:<sha256 of the token>`, value the Member's ID, TTL `SESSION_TTL_SECONDS`, default 14 days). The browser holds only the opaque token, in the `studio_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`). Every sign-in or sign-up issues a new token and ends the session the browser had before. Signing out deletes the session in Redis and clears the cookie. Browsers accept `Secure` cookies from `http://localhost`, so local development needs no TLS.
- **Passwords** are hashed with argon2id (`argon2-cffi` defaults, RFC 9106). Sign-in answers `401 {"detail": "Email or password is incorrect"}` for an unknown email and a wrong password alike, and verifies against a dummy hash when the email is unknown so the timing matches too.
- **Sign-in protection** (`app/auth/throttle.py`). Failed sign-ins are counted in Redis per account (key `sign-in-failures:account:<sha256 of the normalised email>`) and per IP address (`sign-in-failures:ip:<ip>`). Unknown emails are counted exactly like registered ones. After `SIGN_IN_ACCOUNT_DELAY_AFTER_FAILURES` (3) failures for an account, or `SIGN_IN_IP_DELAY_AFTER_FAILURES` (20) from an IP, the next attempt must wait 1 second after the last failure, then 2, 4… up to `SIGN_IN_DELAY_MAX_SECONDS` (30). After `SIGN_IN_ACCOUNT_LOCKOUT_AFTER_FAILURES` (10) or `SIGN_IN_IP_LOCKOUT_AFTER_FAILURES` (100) sign-in is locked out for `SIGN_IN_LOCKOUT_SECONDS` (900). An attempt that must wait is refused before the password is checked, with `429 {"detail": "Too many failed sign-in attempts", "locked": <bool>, "retry_after_seconds": <n>}` and a `Retry-After` header; refused attempts aren't counted, so waiting always works. A successful sign-in clears the account's counter (not the IP's). A counter is forgotten `SIGN_IN_LOCKOUT_SECONDS` after its last failure. Times come from the `Clock` port (`app/core/clock.py`; tests use the `clock` fixture, a `ControllableClock`), so Redis expiry only garbage-collects. Each Lockout is logged (`Sign-in locked out`) and, when the email belongs to a Member, recorded as a `member.locked_out` Audit Event in each of their Organisations (actor none, target the Member, `after` holds scope, IP, failures and `locked_until`).
- **Client IP behind proxies.** The API takes the IP from uvicorn, which trusts `X-Forwarded-For` only from the addresses in `FORWARDED_ALLOW_IPS` (default `127.0.0.1`). Compose sets `*` and the Studio dev proxy sends the header, so local limits count per browser. A deployment must list its load balancers there; otherwise every visitor shares the load balancer's IP counter.
- **Password reset.** `POST /api/auth/password-reset` always answers `202` with the same body and sends the email after the response, so neither the answer nor its timing says whether the email is registered. The emailed link is `STUDIO_URL/reset-password?token=…`; the token is 32 random bytes, and `password_reset_tokens` stores only its SHA-256. A link works once, until `PASSWORD_RESET_TTL_SECONDS` (default one hour) has passed. Completing a reset uses up the Member's other outstanding links and ends every session they have. Each Member's session keys are indexed in Redis (`member-sessions:<member ID>`) so they can all be ended at once.
- **Profile.** `PATCH /api/auth/me` edits the Member's name. `POST /api/auth/me/password` needs the current password; it ends the Member's other sessions and gives this browser a new session token. Resets and password changes are recorded as Audit Events (`member.password_reset`, `member.password_changed`) in every Organisation the Member belongs to.
- **Mailer.** `backend/app/mail/` is the mailer port: templates render an `Email`, and `MAILER` chooses the adapter, `outbox` (in memory, the default and what tests use), `smtp` (Mailpit in `docker compose`; read mail at <http://localhost:8025>) or `ses` (AWS SES v2 in `SES_REGION`, switched on once a sending domain exists). `MAIL_FROM` sets the sender.
- **Clock.** Code that needs the time takes the `Clock` port (`app/core/clock.py`). Tests swap in a controllable clock with the `clock` fixture, and read sent email from the `outbox` fixture.
- **Invites.** Owners manage Invites under `/api/organisations/{organisation_id}/invites` (Owner-only, through `OwnerScope`): `POST` creates one for an email and role (`send_email`, default true, emails it through the mailer port), `GET` lists pending ones (not accepted or revoked, newest first, expired ones flagged `expired`), `DELETE …/{invite_id}` revokes one and `POST …/{invite_id}/renew` gives it a new link and expiry. Creating and renewing answer with the Invite Link (`STUDIO_URL/accept-invite?token=…`), so an Owner can always copy one; it is the only time the token is shown, and `email_sent` says whether the email went out (a failed email is logged, and the link still works). The token is 32 random bytes and `invites` stores only its SHA-256. A link works once, until `INVITE_TTL_SECONDS` (default seven days) has passed, and not after its Invite is revoked or renewed. An email that already belongs to a Member of the Organisation, or already has a pending Invite there, gets 409. The invited person uses `/api/invites` with the token in the body: `POST /lookup` (no session; 404 for a link that doesn't work) shows the Organisation, role and whether an account exists; `POST /sign-up` creates the account for the invited email and joins; `POST /accept` adds a signed-in Member whose email matches (another email gets 403). Both start a new session (rotation). Creating, renewing, accepting and revoking are recorded as Audit Events (`invite.created`, `invite.renewed`, `invite.accepted`, `invite.revoked`). In the Studio, Organisation settings has a Members tab for Owners (invite form, the link to copy, pending Invites), and `/accept-invite` is the page the link opens.
- **Tenancy.** `organisations`, `members`, `password_reset_tokens` and the MFA tables are platform-level tables; `invites` belongs to an Organisation. Every other table carries a non-null `organisation_id`, and a test fails if one doesn't. Tenant data is read through `app/tenancy/repository.py` functions that take an `OrganisationScope`. Routes get one from the single policy dependency, `RequireRole` in `app/tenancy/policy.py`, which each route declares with its required role: `Scope` (any Member, Owner or Editor) or `OwnerScope` (Owners only). It reads `{organisation_id}` from the path and answers 404 when the Member doesn't belong to it, exactly as for an Organisation that doesn't exist, and 403 ("Only Owners can do this") when an Editor calls an Owner-only route. The Studio hides Owner-only navigation (the Members and Audit tabs) from Editors as well.
- **Members.** `GET /api/organisations/{organisation_id}/members` lists every Member with their role, in the order they joined; `PATCH …/members/{member_id}` (`{role}`) changes a role and `DELETE …/members/{member_id}` removes a Member (all Owner-only). `POST …/leave` lets any Member leave. The last-Owner invariant (`app/tenancy/members.py`): demoting, removing or leaving as the Organisation's last Owner gets 409, and each change first locks the Organisation's row so concurrent changes can't both remove "the other" Owner. Roles and memberships are read on every request, so a role change or removal takes effect on the Member's next request, with no sign-out. Changes are recorded as `member.role_changed` (before/after `{email, role}`), `member.removed` and `member.left` (before `{email, name, role}`). In the Studio, the Owners' Members tab lists Members with a role picker and Remove (with a confirm step; not on your own row), and General settings has "Leave …" for everyone.
- **Organisation switcher.** `/api/auth/me` (and every answer that starts or reports a session) includes `active_organisation_id`: the Organisation the Member last switched to while they still belong to it, otherwise their first, or null with none. `PUT /api/auth/me/active-organisation {"organisation_id": …}` (`switchOrganisation`, `app/tenancy/switcher_api.py`) remembers a new one and answers with the session; an Organisation the Member doesn't belong to is 404 `Not found`, like one that doesn't exist. The choice is kept per Member in Redis (`active-organisation:<member ID>`, no expiry, `app/tenancy/active.py`), so it outlives sessions and sign-ins; losing it only means the first Organisation opens. It is a preference, never a permission: Organisation-scoped routes still take the Organisation from the path. In the Studio, `/` opens the Active Organisation, the header shows a switcher (`shell/OrganisationSwitcher.tsx`) to Members of two or more Organisations, and switching opens the chosen Organisation's Projects. Every Organisation page reads its Organisation from the address, and queries are keyed by it, so a reload keeps the Organisation and nothing from another one is shown.
- **Isolation test.** `backend/tests/integration/test_tenant_isolation.py` lists every Organisation-scoped route in `ORGANISATION_SCOPED_ROUTES` with its required role, and checks that another tenant's Member gets 404, a signed-out visitor 401, an Editor 403 from every Owner-only route, and an Editor through on every route open to all Members. Guard tests fail when the OpenAPI document has an `{organisation_id}` route that isn't listed, or when a route's `RequireRole` dependency (found on the routers in `app.main.ROUTERS`) isn't exactly one with the listed role. The same list also drives the checks for a Member of two Organisations (the `two_organisations` fixture): whichever is active, a third Organisation's routes are 404, a resource of one Organisation is 404 through the other's path, and each Organisation's lists hold only its own data. So adding a route means adding it there with its role (and a `prepare` step if it needs resources or Members inside the Organisation).
- **Backend test fixtures** (`backend/tests/conftest.py`): `client` (HTTPS base URL, so the `Secure` cookie round-trips), `new_client` (another browser on the same app), `tenant_factory` (signs a new Member up in a fresh client, so they own a new Organisation), `owner`, `member_factory` (adds a new signed-in Member to an Owner's Organisation with a role, through an Invite), `clock` (a `ControllableClock` installed on the app) and `join_organisation(owner, member, role)` (brings an existing Member into the Owner's Organisation through an accepted Invite Link). Each test starts with no sign-in failure counters. The test database is migrated to head once per run.

## Audit Events

- **Recording.** `app.audit.record(session, organisation_id=…, actor_id=…, action=…, target=AuditTarget(type, id), before=…, after=…)` adds an Audit Event to the caller's transaction, so the change and its event commit or roll back together. `actor_id` is `None` for events no Member caused. Actions are dotted names (`organisation.created`, the first one, is recorded at sign-up). Keys matching a secret-like pattern (`password`, `secret`, `token`, `api_key`, `credential`, `private_key`, `authorization`, `cookie`, `session`, `recovery_codes`, …) have their values replaced by `[Redacted]` at any depth before anything is stored.
- **Append-only.** Migration `0003_audit` adds triggers that refuse `UPDATE`, `DELETE` and `TRUNCATE` on `audit_events`.
- **Reading.** `GET /api/organisations/{organisation_id}/audit-events` (filters `actor_id`, `action`, `start` inclusive, `end` exclusive, both with a time zone; `page`, `page_size` up to 100; newest first) and `GET …/audit-events/facets` (the actors and actions present, for filter menus). Both are Owner-only through the `OwnerScope` dependency (`app/tenancy/policy.py`): an Editor gets `403 {"detail": "Only Owners can do this"}`, another tenant's Member 404.
- **Studio.** Organisation settings has a General tab and, for Owners only, an Audit tab (`/organisations/$organisationId/settings/audit`). Its date filters are whole UTC days, both inclusive.

## Theme

- **API** (`backend/app/theme/`). `GET /api/organisations/{organisation_id}/theme` (`getTheme`, any Member) answers the Organisation's Theme, or the default (`updated_at: null`) until an Owner saves one. `PUT …/theme` (`saveTheme`, Owners only through `OwnerScope`) replaces the whole Theme and applies at once. `GET /api/themes/fonts` (`listThemeFonts`) lists the Font Allowlist (`app/theme/fonts.py`), the default first.
- **What a Theme holds** (`app/theme/schema.py`): six Colour Tokens (`primary`, `on_primary`, `surface`, `on_surface`, `accent`, `muted`), each `{light, dark}` as `#rrggbb` (stored in lower case); `radius` (whole pixels, 0 to 24); `font` (from the allowlist); `mode` (`light`, `dark` or `auto`); `launcher_type` (`bubble` or `inline`) and `launcher_position` (`bottom-right` or `bottom-left`). Anything else is 422. Contrast is never checked by the API: it only warns, in the Studio.
- **Storage and audit.** `themes` holds at most one row per Organisation, written on the first save that changes something (migration `0007_themes`). A save locks the Organisation's row, so concurrent saves apply one after the other. Each change records `theme.updated` (target `theme/<id>`) with only what changed in `before` and `after`, nested the same way (`{"colours": {"primary": {"light": …}}}`). Saving an unchanged Theme records nothing.
- **Resolution and contrast** (`frontend/packages/ui`, `@studio/ui`). `resolveTheme(theme, scheme)` is the one pure function that turns a Theme into CSS custom properties (`--theme-primary`, `--theme-on-primary`, `--theme-surface`, `--theme-on-surface`, `--theme-accent`, `--theme-muted`, `--theme-radius`, `--theme-font-family`) for the light or dark scheme. `themeStylesheet(theme, selector)` builds a stylesheet from it, with a `prefers-color-scheme: dark` block in auto mode, for the widget to inline. `contrastWarnings(theme)` checks, with the WCAG relative-luminance formula, on-primary on primary, on-surface on surface and muted on surface against 4.5:1, and accent on surface against 3:1, in each scheme the mode shows.
- **UI primitives** (`@studio/ui`): `ThemeScope` (sets the custom properties), `ChatWindow`, `MessageBubble`, `MutedText`, `AccentLink`, `Composer` and `Launcher`. They read the Theme only through the custom properties, so the Studio preview and the widget render the same components.
- **Studio.** Organisation settings has a Theme tab for every Member (`settings/ThemePage.tsx`): a form (hex field and colour picker per Colour Token and scheme, radius, font, mode, launcher and position), the Contrast Warnings, and a live preview built from the primitives that follows every edit before it is saved. In auto mode the preview can show either scheme. Editors see it all read-only, without Save.

## MFA and envelope encryption

- **TOTP MFA** (`backend/app/auth/mfa.py`, routes in `app/auth/mfa_api.py` under `/api/auth/mfa`). RFC 6238, SHA-1, six digits, 30-second steps, accepted one step either side. Enrolment (`POST /enrolment`) returns the secret, an `otpauth://` URI and a QR code (an SVG data URI); MFA is on only after `POST /enrolment/confirm` checks a code, which returns ten Recovery Codes once. Each accepted code's step is stored, so a code works once. Recovery Codes (`XXXX-XXXX-XXXX-XXXX`, 80 random bits) are stored as SHA-256 hashes and are typed case-, dash- and space-insensitively. `POST /disable` needs the password and a code; `POST /recovery-codes` replaces the codes for a code.
- **MFA pending.** For a Member with MFA, a correct password answers `202 {"mfa_required": true}` and sets `studio_mfa_pending` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/auth`) instead of a session. Redis keeps `mfa-pending:<sha256 of the token>` for `MFA_PENDING_TTL_SECONDS` (default 300). `POST /api/auth/mfa/verify` with an authenticator or Recovery Code then starts the session; five wrong codes end the pending sign-in (`401 {"detail": "Sign in again"}`).
- **Audit Events.** Enrolling, disabling, using a Recovery Code and replacing Recovery Codes are recorded with `app.audit.service.record`, once in each Organisation the Member belongs to (`mfa.enrolled`, `mfa.disabled`, `mfa.recovery_code_used`, `mfa.recovery_codes_replaced`).
- **Envelope encryption** (`backend/app/crypto/`). `EnvelopeEncryption.seal(plaintext, context=...)` and `.open(sealed, context=...)`: AES-256-GCM with a fresh data key per record, the data key wrapped by a `KeyWrapper`. Version 1 records are `0x01 | key-ID length | key ID | wrapped-key length (2 bytes) | wrapped key | nonce (12) | ciphertext and tag`; everything before the nonce and the caller's `context` (for TOTP, the Member's ID) are authenticated, so tampering, truncation or moving a record to another Member fails with `EnvelopeError`. The local static-key wrapper takes `LOCAL_KEY_WRAPPER_KEY` (32 bytes, base64; `openssl rand -base64 32`); `docker-compose.yml` has a development default. AWS KMS comes with the AWS deployment.
- **Clock.** Code checks use the clock port (`app/core/clock.py`). Tests replace it with `ControllableClock` through the `clock` fixture.

## Telemetry and logs

The API, worker and Beat are traced with OpenTelemetry through the Logfire SDK (`backend/app/core/telemetry.py`). FastAPI requests, SQLAlchemy queries, Celery tasks (from the request that queues them through to the worker that runs them) and outbound `httpx` calls are instrumented.

- **Exporter.** With `LOGFIRE_TOKEN` set, spans go to Logfire (`LOGFIRE_BASE_URL` is only needed for a self-hosted Logfire). Without it they are written to stdout, one JSON object per span.
- **Scrubbing.** Every exporter receives spans after Logfire's scrubbing processor, extended for this project. Values under Message-carrying field names (`content`, `message`, `messages`, `prompt`, and `input`, where validation errors echo a request back) are redacted, and so are values under keys ending in `token` (`token`, `reset_token`; not `max_tokens` or `token_budget`), which is where Invite and reset links send their token. So are cookies, `Authorization` and API-key headers, and secret-like attributes. Request headers are captured, so these are redacted rather than simply absent. A log message whose template formats a scrubbed value is exported as the bare template.
- **Logs.** Every service writes JSON lines to stdout: `timestamp`, `level`, `logger`, `message`, `service` (`api`, `worker`, `beat` or `migrations`), any `extra` fields, `exception` when there is one, and `trace_id`/`span_id` inside a traced operation. Extra fields with sensitive names, and the task arguments and results Celery logs, are written as `[Redacted]`.
- **Entrypoints.** The API runs as `python -m app.serve`, so uvicorn's own lines are JSON too. Celery runs with `--quiet` so it skips its text banner; the one line Celery still prints outside logging is its `worker: Warm shutdown (MainProcess)` notice on SIGTERM.

## Tests

Backend tests run against real Postgres and Redis. With `make services` running they use the `studio_test` database and Redis database 15; override with `TEST_DATABASE_URL` and `TEST_REDIS_URL`.

## End-to-end tests

Playwright lives in `frontend/e2e`, and its config is `frontend/playwright.config.ts`. It has two projects:

- `harness` checks the shared fixtures against an in-process fake Studio, so it runs without the stack (`pnpm e2e:harness`).
- `studio` runs against the stack at `E2E_BASE_URL` (default <http://localhost:5173>).

Specs import `test` and `expect` from `frontend/e2e/fixtures`, not from `@playwright/test`. That gives every spec these fixtures:

| Fixture | What it does |
|---|---|
| `stack` (automatic, once per worker) | Waits until the Studio loads and, through its `/api` proxy, the API reports the database and Redis ok and a worker answers the health task. It gives up after `E2E_STACK_TIMEOUT_MS` (default 180 s) and names the failing check. |
| `member` | A new, unique Member (name, email, password, Organisation name) who has not signed up yet. |
| `signedInPage` | A page signed in as `member`, who has just signed up and so owns a new Organisation. It uses the auth API directly; `signUp`, `signIn` and `signInAs` in `fixtures/auth.ts` do the same for other Members. The routes it calls are the ones ticket 01-04 implements. |
| `makeAxeBuilder` | An axe scan of the page limited to WCAG 2.2 AA rules. |

Email the stack sends lands in Mailpit. `latestEmailTo` and `linkPath` in `fixtures/mailpit.ts` read it through Mailpit's API at `E2E_MAILPIT_URL` (default <http://localhost:8025>) and pull a link out of it to open on the Studio under test.

To use a Chromium that is already installed instead of Playwright's download, set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.
