# Local development

Prerequisites: Docker with Compose v2, GNU Make, [uv](https://docs.astral.sh/uv/) and Node 22 with pnpm (via `corepack enable`). The infrastructure and security gates also need Terraform, TFLint, Checkov, gitleaks and Trivy; `scripts/ci/install-tools.sh terraform tflint checkov gitleaks trivy` installs the pinned, checksum-verified versions CI uses into `~/.local/bin`.

| Command | What it does |
|---|---|
| `make dev` | Builds and starts the whole stack: Postgres with pgvector, Redis, RustFS, Mailpit, the API, the Celery worker, Celery Beat and the Studio. |
| `make install` | Installs backend (`uv sync`) and frontend (`pnpm install`) dependencies on the host. |
| `make services` | Starts only Postgres and Redis, which the backend tests need. |
| `make test` | Backend and frontend tests, each failing below 100% line or branch coverage (ADR-0008). |
| `make lint` | ruff, `mypy --strict`, eslint and `tsc`. |
| `make gen-client` | Regenerates `frontend/packages/api-client` from the backend's OpenAPI schema. |
| `make check-client` | Fails if the committed API client differs from a fresh generation (CI runs this). |
| `make e2e-install` | Installs the Chromium build Playwright uses. |
| `make e2e` | Starts the stack with `docker compose up --wait`, then runs the Playwright suite (fixture checks and the Studio smoke and auth tests with axe). |
| `make infra-check` | `terraform fmt`, `validate`, `terraform test`, TFLint (with the AWS ruleset) and Checkov over `infra/bootstrap`, every module in `infra/modules` and every environment in `infra/envs`, plus the S3 backend check (`infra/tests/backend.test.sh`) and the plan-gate tests (`scripts/ci/tests/plan-gate.test.sh`). No AWS account is needed: `terraform test` uses mocked providers. |
| `make security` | gitleaks over the whole history (`secret-scan`), pip-audit and pnpm audit (`audit`), and a Trivy scan of the built images (`image-scan`). |
| `make images` | Builds the API image (also used by the worker and Beat) and the Studio image. |
| `make eval` | Guardrail evaluation suite; a passing placeholder until ticket 08-07. |

Once `make dev` is up:

- Studio: <http://localhost:5173> (sign up there to create an Organisation; <http://localhost:5173/status> shows API, database, Redis and worker health through the generated client)
- API: <http://localhost:8000/api/health>, OpenAPI docs at <http://localhost:8000/docs>
- Mailpit: <http://localhost:8025>
- RustFS console: <http://localhost:9001>

## Settings

Every backend service reads typed settings from the environment (`backend/app/core/settings.py`) and refuses to start when a required one is missing or invalid, naming the setting:

```
app.core.settings.SettingsError: Invalid service settings. DATABASE_URL: Field required
```

`docker-compose.yml` supplies the local values; `.env.example` lists them.

## Sign-in and tenancy

- **Sessions.** Signing up or in starts a server-side session in Redis (key `session:<sha256 of the token>`, value the Member's ID, TTL `SESSION_TTL_SECONDS`, default 14 days). The browser holds only the opaque token, in the `studio_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`). Every sign-in or sign-up issues a new token and ends the session the browser had before. Signing out deletes the session in Redis and clears the cookie. Browsers accept `Secure` cookies from `http://localhost`, so local development needs no TLS.
- **Passwords** are hashed with argon2id (`argon2-cffi` defaults, RFC 9106). Sign-in answers `401 {"detail": "Email or password is incorrect"}` for an unknown email and a wrong password alike, and verifies against a dummy hash when the email is unknown so the timing matches too.
- **Sign-in protection** (`app/auth/throttle.py`). Failed sign-ins are counted in Redis per account (key `sign-in-failures:account:<sha256 of the normalised email>`) and per IP address (`sign-in-failures:ip:<ip>`). Unknown emails are counted exactly like registered ones. After `SIGN_IN_ACCOUNT_DELAY_AFTER_FAILURES` (3) failures for an account, or `SIGN_IN_IP_DELAY_AFTER_FAILURES` (20) from an IP, the next attempt must wait 1 second after the last failure, then 2, 4… up to `SIGN_IN_DELAY_MAX_SECONDS` (30). After `SIGN_IN_ACCOUNT_LOCKOUT_AFTER_FAILURES` (10) or `SIGN_IN_IP_LOCKOUT_AFTER_FAILURES` (100) sign-in is locked out for `SIGN_IN_LOCKOUT_SECONDS` (900). An attempt that must wait is refused before the password is checked, with `429 {"detail": "Too many failed sign-in attempts", "locked": <bool>, "retry_after_seconds": <n>}` and a `Retry-After` header; refused attempts aren't counted, so waiting always works. A successful sign-in clears the account's counter (not the IP's). A counter is forgotten `SIGN_IN_LOCKOUT_SECONDS` after its last failure. Times come from the `Clock` port (`app/core/clock.py`; tests use the `clock` fixture, a `ControllableClock`), so Redis expiry only garbage-collects. Each Lockout is logged (`Sign-in locked out`) and, when the email belongs to a Member, recorded as a `member.locked_out` Audit Event in each of their Organisations (actor none, target the Member, `after` holds scope, IP, failures and `locked_until`).
- **Client IP behind proxies.** The API takes the IP from uvicorn, which trusts `X-Forwarded-For` only from the addresses in `FORWARDED_ALLOW_IPS` (default `127.0.0.1`). Compose sets `*` and the Studio dev proxy sends the header, so local limits count per browser. A deployment must list its load balancers there; otherwise every visitor shares the load balancer's IP counter.
- **Password reset.** `POST /api/auth/password-reset` always answers `202` with the same body and sends the email after the response, so neither the answer nor its timing says whether the email is registered. The emailed link is `STUDIO_URL/reset-password?token=…`; the token is 32 random bytes, and `password_reset_tokens` stores only its SHA-256. A link works once, until `PASSWORD_RESET_TTL_SECONDS` (default one hour) has passed. Completing a reset uses up the Member's other outstanding links and ends every session they have. Each Member's session keys are indexed in Redis (`member-sessions:<member ID>`) so they can all be ended at once.
- **Profile.** `PATCH /api/auth/me` edits the Member's name. `POST /api/auth/me/password` needs the current password; it ends the Member's other sessions and gives this browser a new session token. Resets and password changes are recorded as Audit Events (`member.password_reset`, `member.password_changed`) in every Organisation the Member belongs to.
- **Mailer.** `backend/app/mail/` is the mailer port: templates render an `Email`, and `MAILER` chooses the adapter, `outbox` (in memory, the default and what tests use), `smtp` (Mailpit in `docker compose`; read mail at <http://localhost:8025>) or `ses` (AWS SES v2 in `SES_REGION`, switched on once a sending domain exists). `MAIL_FROM` sets the sender.
- **Clock.** Code that needs the time takes the `Clock` port (`app/core/clock.py`). Tests swap in a controllable clock with the `clock` fixture, and read sent email from the `outbox` fixture.
- **Invites.** Owners manage Invites under `/api/organisations/{organisation_id}/invites` (Owner-only, through `OwnerScope`): `POST` creates one for an email and role (`send_email`, default true, emails it through the mailer port), `GET` lists pending ones (not accepted or revoked, newest first, expired ones flagged `expired`), `DELETE …/{invite_id}` revokes one and `POST …/{invite_id}/renew` gives it a new link and expiry. Creating and renewing answer with the Invite Link (`STUDIO_URL/accept-invite?token=…`), so an Owner can always copy one; it is the only time the token is shown, and `email_sent` says whether the email went out (a failed email is logged, and the link still works). The token is 32 random bytes and `invites` stores only its SHA-256. A link works once, until `INVITE_TTL_SECONDS` (default seven days) has passed, and not after its Invite is revoked or renewed. An email that already belongs to a Member of the Organisation, or already has a pending Invite there, gets 409. The invited person uses `/api/invites` with the token in the body: `POST /lookup` (no session; 404 for a link that doesn't work) shows the Organisation, role and whether an account exists; `POST /sign-up` creates the account for the invited email and joins; `POST /accept` adds a signed-in Member whose email matches (another email gets 403). Both start a new session (rotation). Creating, renewing, accepting and revoking are recorded as Audit Events (`invite.created`, `invite.renewed`, `invite.accepted`, `invite.revoked`). In the Studio, Organisation settings has a Members tab for Owners (invite form, the link to copy, pending Invites), and `/accept-invite` is the page the link opens.
- **Tenancy.** `organisations`, `members`, `password_reset_tokens` and the MFA tables are platform-level tables; `invites` belongs to an Organisation. Every other table carries a non-null `organisation_id`, and a test fails if one doesn't. Tenant data is read through `app/tenancy/repository.py` functions that take an `OrganisationScope`. Routes get one from the single policy dependency, `RequireRole` in `app/tenancy/policy.py`, which each route declares with its required role: `Scope` (any Member, Owner or Editor) or `OwnerScope` (Owners only). It reads `{organisation_id}` from the path and answers 404 when the Member doesn't belong to it, exactly as for an Organisation that doesn't exist, and 403 ("Only Owners can do this") when an Editor calls an Owner-only route. The Studio hides Owner-only navigation (the Members and Audit tabs) from Editors as well.
- **Members.** `GET /api/organisations/{organisation_id}/members` lists every Member with their role, in the order they joined; `PATCH …/members/{member_id}` (`{role}`) changes a role and `DELETE …/members/{member_id}` removes a Member (all Owner-only). `POST …/leave` lets any Member leave. The last-Owner invariant (`app/tenancy/members.py`): demoting, removing or leaving as the Organisation's last Owner gets 409, and each change first locks the Organisation's row so concurrent changes can't both remove "the other" Owner. Roles and memberships are read on every request, so a role change or removal takes effect on the Member's next request, with no sign-out. Changes are recorded as `member.role_changed` (before/after `{email, role}`), `member.removed` and `member.left` (before `{email, name, role}`). In the Studio, the Owners' Members tab lists Members with a role picker and Remove (with a confirm step; not on your own row), and General settings has "Leave …" for everyone.
- **Organisation switcher.** `/api/auth/me` (and every answer that starts or reports a session) includes `active_organisation_id`: the Organisation the Member last switched to while they still belong to it, otherwise their first, or null with none. `PUT /api/auth/me/active-organisation {"organisation_id": …}` (`switchOrganisation`, `app/tenancy/switcher_api.py`) remembers a new one and answers with the session; an Organisation the Member doesn't belong to is 404 `Not found`, like one that doesn't exist. The choice is kept per Member in Redis (`active-organisation:<member ID>`, no expiry, `app/tenancy/active.py`), so it outlives sessions and sign-ins; losing it only means the first Organisation opens. It is a preference, never a permission: Organisation-scoped routes still take the Organisation from the path. In the Studio, `/` opens the Active Organisation, the header shows a switcher (`shell/OrganisationSwitcher.tsx`) to Members of two or more Organisations, and switching opens the chosen Organisation's Projects. Every Organisation page reads its Organisation from the address, and queries are keyed by it, so a reload keeps the Organisation and nothing from another one is shown.
- **Projects.** `app/projects/` holds the `projects` table (`organisation_id`, `name` up to 200 characters, `description` up to 2,000, `archived_at`) and its routes under `/api/organisations/{organisation_id}/projects`: `GET` lists the active Projects by name (`?archived=true` lists the archived ones instead), `POST` creates one, `GET …/{project_id}` reads one (archived or not), `PATCH …/{project_id}` renames it or edits its description, `POST …/{project_id}/archive` archives it (all open to any Member) and `POST …/{project_id}/restore` restores it (Owners only). Each Project in an answer carries `document_count` (its Documents), `agent_count` (0 until Agents arrive in 04-01, which adds the count in `app/projects/service.py`) and `embedding_model_id` (`multilingual-e5-small` unless a later ticket changes it). An archived Project is hidden from the main list and stops serving: `app.projects.service.active_project` is the gate every change or serving path takes (today renaming and archiving, later uploads and Agents), and it answers 409 "This Project is archived. An Owner can restore it.". Restoring a Project that isn't archived is 409 too. Another Organisation's Project, or an unknown one, is 404 `Not found`. Create, archive and restore are recorded as `project.created` (after `{name, description}`), `project.archived` and `project.restored` (before/after `{name, archived}`). In the Studio, Projects lists the active Projects with their counts, a New Project form, and "Show archived Projects" (Owners restore from there); each Project has a page (`/organisations/$organisationId/projects/$projectId`) with Edit details, Archive (with a confirm step), Restore for an archived Project (Owners), and tabs for Documents, Instructions, Agents, Conversations and Analytics that are placeholders until their features arrive.
- **Documents and ingestion.** Routes in `app/documents/api.py`, under `/api/organisations/{organisation_id}/projects/{project_id}`, open to any Member:
  - `GET …/uploads/limits` (`getUploadLimits`) answers `{accepted_extensions, max_upload_bytes, document_quota, documents_counted}`, which the Studio checks files against before uploading. `PUT …/document-quota` (`setDocumentQuota`, Owners only) takes `{document_quota}` (1 to 100,000; every Project starts at 500, column `projects.document_quota`). The quota counts Documents that aren't Failed; lowering it keeps the Documents already there.
  - `POST …/uploads` (`startDocumentUpload`) takes `{filename, size_bytes, replacing_document_id?}`, refuses an unsupported type (415; PDF, DOCX, PPTX, HTML, Markdown, TXT by extension), a file over `MAX_UPLOAD_BYTES` (413, default 50 MB) or a full Project (409, "This Project has reached its quota of N Documents. Delete a Document, or ask an Owner to raise the quota."; not checked when `replacing_document_id` names the Document the file will be a new edition of, as a new edition adds no Document), and answers `{upload_id, url, method: "PUT", content_type, expires_at}`. The pending upload is kept in Redis (`document-upload:<project>:<upload>`) for `UPLOAD_URL_TTL_SECONDS`.
  - The browser PUTs the file to `url` with that `Content-Type`.
  - `POST …/documents` (`confirmDocumentUpload`) takes `{upload_id, content_hash?}`: reads the stored file, computes its SHA-256 (checking the browser's, if given: 422 on a mismatch), creates the Document as `queued` and enqueues the `documents.ingest` Celery task. An unknown, expired or used upload, or one whose file hasn't arrived, is 409. It checks again what the start checked: a stored file larger than `MAX_UPLOAD_BYTES` (a presigned PUT can't bound the size) is deleted and refused with 413, and a full Project is 409; the Project's row is locked while it counts, so concurrent confirms can't overfill it.
  - `POST …/documents/{document_id}/retry` (`retryDocument`) answers 202 and puts what failed back to `queued` (clearing its error): a `failed` Document, or, when the Document is Ready and its new edition (`replacement`) is what failed, that edition. With nothing Failed, a Ready Document is processed again with the Project's current settings, such as OCR (ticket 03-08); its Chunks serve until the new ones replace them, and are dropped if it fails. It enqueues ingestion again from the stored file. A Document still `queued` or `processing`, or whose new edition is, is 409 (busy); one whose content has since been uploaded again is 409 as a Duplicate (naming the Document); an archived Project 409. A new edition (`POST …/documents/{document_id}/editions`) is checked for size on confirm as well (413), and its failures carry `error_category` in `replacement` too.
  - `GET …/documents` lists Documents newest first (`status`, `error_message`, `error_category`, `attempt_count`, `content_hash`, `chunk_count`, …); `GET …/documents/statuses` is the light endpoint the Studio polls every 2 s while any Document is `queued` or `processing`; `GET …/documents/{document_id}/chunks?offset=&limit=` (`listChunks`) answers a page of the Chunks in order, `{items, total, offset, limit}` (each item: `text`, `heading_path`, `page_start`, `page_end`, `embedding_model_id`); `limit` defaults to 50 and is at most 200 (422 beyond, or below 1, or a negative `offset`).
  - Document viewer (ticket 03-03): `GET …/documents/{document_id}` (`getDocument`) answers the Document with `markdown`, the converted markdown read back from the object store (null until the Document has been converted, so for Queued, Processing and Failed). `GET …/documents/{document_id}/download` (`downloadDocument`) answers 307 to a presigned GET of the original file (`ObjectStore.presign_get`), valid for `DOWNLOAD_URL_TTL_SECONDS` (default 300), which makes the store serve it with the Document's MIME type as an attachment under its name (`Content-Disposition` with an ASCII fallback and the UTF-8 `filename*`). Because it is a redirect, a plain link to the route downloads the file with the session cookie, and the URL is signed only when clicked, so it can't expire on an open page.
  - Uploads go through `active_project`, so an archived Project refuses them with 409.
  - Ingestion (`app/documents/pipeline.py`): Processing → fetch the original → convert through the converter port (`DOCUMENT_CONVERTER=docling|fake`) → store the markdown next to the original (`<object key>.converted.md`) → `HybridChunker` with the Embedding Model's tokenizer, at most `CHUNK_MAX_TOKENS` (default 256, capped at the model's limit) → embed in batches of 32 (`EMBEDDER=local|fake`) → write the Chunks and set Ready in one transaction. Failures (`app/documents/limits.py` holds the checks and messages) set Failed with an `error_category` and a readable `error_message`:
    - `unsupported_content`: the bytes don't match the type (no `%PDF-` header in the first KB; a DOCX or PPTX that isn't a zip with `word/document.xml` or `ppt/presentation.xml`; HTML, Markdown or TXT that isn't UTF-8 or holds NUL bytes), the converter raises `UnsupportedContentError`, or conversion yields no Chunks (the message suggests turning on OCR for a scanned PDF).
    - `conversion`: the converter raised anything else, the original is missing from storage, or something unexpected failed.
    - `provider`: the Project's provider Embedding Model can't be called at all (no Provider Credential, a credential without the `embeddings` capability or that doesn't offer the model: `UNUSABLE_ERRORS` in `app/embeddings/provider.py`), or answered with vectors of the wrong size; these fail at once with "The Embedding Model's provider can't be used: <reason> Retry once it is fixed.". Or the embedder raised `EmbeddingProviderError` (the embedder port's transient error; `ProviderEmbedder` raises it for any error from the gateway's client) on every attempt. Before the last attempt the Document goes back to `queued` with "Retrying automatically (attempt n of N)" as its message, and the task sends itself again with `attempt+1` after `min(INGESTION_RETRY_MAX_SECONDS, INGESTION_RETRY_BASE_SECONDS × 2^(attempt−1))` (defaults 10 s doubling, at most 300 s), up to `INGESTION_MAX_ATTEMPTS` (default 4) in all. In eager mode (tests) the next attempt runs at once.
    - `quota`: when a Document is claimed, the Project (locked) already holds `document_quota` other Documents that aren't Failed, for example after an Owner lowered the quota and a Failed Document was retried.
    `attempt_count` counts every start, automatic retries and retries by hand included.
  - Tables (migration `0011_documents`): `documents` and `chunks`. A Chunk stores its vector in an untyped pgvector column with `embedding_model_id`, and a generated `search_vector` (`to_tsvector('simple', text)`). Indexes: GIN on `search_vector`, and one partial HNSW index per Embedding Model on `embedding::vector(<dimension>)` (`vector_cosine_ops`, `WHERE embedding_model_id = '<model>'`); a new model in `app/embeddings/registry.py` needs its index in a migration.
  - Ports (`app/documents/ports.py`): the API builds the object store, converter and embedders at startup, keeps them on `app.state.ingestion` and installs them for tasks; the worker does the same at its start. In tests tasks run eagerly in the API's process, so they share its fakes; `app.state.ingestion.converter.failure = …` makes the fake converter raise, `app.state.ingestion.embedders["multilingual-e5-small"].failures = [error, …]` makes the next embedder calls raise, one each, and `app.state.ingestion.object_store.failure = …` makes the memory store's reads raise.
  - Object store (`app/storage/`): `OBJECT_STORE=s3|memory`. S3 and RustFS are the same adapter (`OBJECT_STORE_ENDPOINT_URL`, static keys). Presigned URLs are signed for `OBJECT_STORE_PUBLIC_ENDPOINT_URL`: in `docker compose` that is the Studio's own address, and Vite proxies `/studio-documents` (the bucket) to RustFS with the Host header unchanged, so no CORS is needed. `OBJECT_STORE_CREATE_BUCKET=true` creates the bucket at startup (compose only). `make services` now starts RustFS too; the backend tests reach it at `TEST_OBJECT_STORE_URL` (default `http://localhost:9000`).
  - Embedding Models (`app/embeddings/`): the registry (`registry.py`) lists each model's provider, dimension, tokenizer, token limit and required credential capability: `multilingual-e5-small` (local, 384 dimensions, its Hugging Face tokenizer, 512 tokens, `query: `/`passage: ` prefixes, no credential), OpenAI `text-embedding-3-small` (1536) and `-large` (3072), Voyage `voyage-3.5`, `voyage-3.5-lite` and `voyage-multilingual-2` (1024), and Bedrock `amazon.titan-embed-text-v2:0` and `cohere.embed-multilingual-v3` (1024). A unit test fails if the capability registry offers an embeddings model the Embedding Model registry lacks. The embedder port is async (`embed_passages`, `embed_query`). The local adapter uses fastembed; the fake is a deterministic SHA-256 hash embedder whose tokenizer counts words, and which embeds a query like a passage of the same text.
  - Provider Embedding Models (ticket 03-09, `app/embeddings/provider.py`, `app/projects/embedding.py`, `app/projects/embedding_api.py`): `GET /api/organisations/{organisation_id}/embedding-models` (`listEmbeddingModels`, any Member) lists the local model, then each credential with the `embeddings` capability and its provider's models, by credential name. Voyage, OpenAI and Bedrock credentials all offer their models. Bedrock embedders (`BedrockEmbeddingModel` in `app/gateway/live.py`) call Bedrock Runtime's `InvokeModel` through boto3 in the credential's region: Titan Text Embeddings V2 one text per call (`dimensions` 1024, `normalize`), Cohere Embed Multilingual v3 in batches of up to 96 (`search_document`/`search_query`, `truncate: END`). They sign with the stored access keys, or with a session of the Owner's role assumed through STS with the Organisation's external ID (`ProviderCredential.external_id`, a column property loaded with the credential) and cached by `AssumedRoleSessions`, as credential checks do. A Bedrock refusal is a Pydantic AI `ModelHTTPError`. Bedrock chat and rerank clients are still not built. `PUT …/projects/{project_id}/embedding-model` (`setProjectEmbeddingModel`, any Member) takes `{model_id, credential_id}` (no credential for the local model): 422 with the reason for an unknown model, a missing or foreign credential, or one that doesn't offer the model for embeddings; 409 for an archived Project or while the Project has any Document ("Delete its Documents first"; ticket 03-10 replaces this with re-embedding). It records `project.embedding_model_changed` (before/after `{model_id, credential_id}`); choosing the current model again changes nothing. The Project keeps `embedding_credential_id` (migration `0015_provider_embedding_models`, a foreign key to `provider_credentials`), and `project_embedding_references` is registered with the credentials' reference registry, so deleting that credential is 409 while any Project, archived or not, uses it. Ingestion resolves the embedder per Project: the local one from `app.state.ingestion.embedders`, or `ProviderEmbedder` around `ModelGateway.embedder(credential, model)`; each ingestion run opens its own `httpx2` client and gateway through `IngestionPorts.open_gateway`. Provider Chunks are sized with `ApproximateTokenizer` (one token per 3 characters), and vectors of the wrong size fail the Document. The gateway's fake embedder answers with the registered dimension. `POST …/projects/{project_id}/retrieval-probe` (`probeRetrieval`) answers the `top_k` nearest Chunks: 409 with the reason when the Project's model can't be used (no credential, a credential that no longer offers it, a credential kind the gateway can't call) and 502 only when the provider fails to embed the query. It orders by distance alone, so the model's HNSW index serves it, and sets `hnsw.iterative_scan = strict_order` for its transaction so the per-Project filter still yields `top_k` hits. In AWS the worker's task role may `kms:Decrypt` with the credentials key (and gets `CREDENTIALS_KMS_KEY_ARN`) to open the Project's credential; only the API may encrypt.
  - Retrieval probe (`app/retrieval/probe.py`): `POST …/projects/{project_id}/retrieval-probe` (`probeRetrieval`, any Member) takes `{query, top_k?}` (1 to 2,000 characters; `top_k` 1 to 50, default 5) and answers `{embedding_model_id, dimension, chunks: [{chunk_id, document_id, document_name, ordinal, text, heading_path, page_start, page_end, score}]}`, nearest first, `score` being cosine similarity. It searches only the Project's current model's Chunks of each Document's current edition, ordering on the same cast expression as that model's HNSW index. 409 for an archived Project; 502 when the provider can't embed the query. Tests replace provider calls with `app.state.model_gateway` and `app.state.ingestion.open_gateway`.
  - HNSW indexes: one per registered model; models over 2,000 dimensions (`text-embedding-3-large`) index `embedding::halfvec(<dimension>)` with `halfvec_cosine_ops`, because pgvector's HNSW indexes `vector` only up to 2,000 dimensions.
  - Studio: the Project page's **Embedding Model** section (`projects/EmbeddingModel.tsx`) shows the current model and, while the Project has no Documents, **Change Embedding Model**: a select of the choices (`name (credential name)`), **Use this model** and Cancel; the API's reason is shown when a choice is refused.
  - Docling (`docling-slim`) converts Markdown, HTML, DOCX and PPTX with no models. PDF needs the `pdf` dependency group (Docling's layout models and PyTorch, CPU index); the image installs it (`WITH_PDF=true`) and downloads the models at build time (`BUNDLE_MODELS=true`). Set both to false in `.env` for a lighter image, and `EMBEDDER=fake` if the model can't be downloaded.
  - Fixtures: `backend/tests/fixtures/documents/` holds synthetic sample PDF, DOCX and PPTX files (`make_sample_documents.py`), and `backend/tests/fixtures/docling/` real Docling output for the DOCX and PPTX (`record_docling_output.py`), which the chunking test uses. `make test-live` runs the live suite (`tests/live`, marker `live`, deselected by default): real Docling on all three samples and the local Embedding Model; it needs the `pdf` group and Hugging Face access.
  - Studio: the Documents tab (`projects/DocumentsTab.tsx`) has a dropzone and file picker (several files at once), a per-file progress bar, and the Documents table (Name, Status, Chunks, Size), which updates by polling. Files are checked against the upload limits before anything is sent (type, size, and room in the quota, counting the files picked before them), and a refused file shows the reason at once; the API's reason shows for anything it refuses. The tab shows "n of N Documents in this Project's quota". A Failed Document (or a failed new edition) shows its failure category and message, and every Ready or Failed Document has Retry among its actions (it retries what failed, or reprocesses a Ready one); a Queued one waiting for an automatic retry shows why. An archived Project shows no dropzone. Each Document's name links to the Document viewer (`projects/DocumentViewer.tsx`, `/organisations/$organisationId/projects/$projectId/documents/$documentId`): the Document's status, a Download original link (to the download route), the converted markdown rendered with `react-markdown` and `remark-gfm` (tables; raw HTML is not rendered) beside the Chunk list, where each Chunk shows its heading path (`A › B`) and pages (`Page 3`, `Pages 3–4`, nothing for formats without pages), 50 at a time with Previous and Next. The seed staff handbook is `seed/documents/northwind-staff-handbook.md`.
- **Isolation test.** `backend/tests/integration/test_tenant_isolation.py` lists every Organisation-scoped route in `ORGANISATION_SCOPED_ROUTES` with its required role, and checks that another tenant's Member gets 404, a signed-out visitor 401, an Editor 403 from every Owner-only route, and an Editor through on every route open to all Members. Guard tests fail when the OpenAPI document has an `{organisation_id}` route that isn't listed, or when a route's `RequireRole` dependency (found on the routers in `app.main.ROUTERS`) isn't exactly one with the listed role. The same list also drives the checks for a Member of two Organisations (the `two_organisations` fixture): whichever is active, a third Organisation's routes are 404, a resource of one Organisation is 404 through the other's path, and each Organisation's lists hold only its own data. So adding a route means adding it there with its role (and a `prepare` step if it needs resources or Members inside the Organisation). Routes that act on one Project (`{project_id}` in the path) also go in `PROJECT_SCOPED_ROUTES`, which drives the Project-level checks: a Project is 404 through any Organisation but its own, even for a Member of both, exactly like an unknown Project, and each Organisation lists only its own Projects, active or archived. A guard test fails when a `{project_id}` route isn't listed.
- **Backend test fixtures** (`backend/tests/conftest.py`): `client` (HTTPS base URL, so the `Secure` cookie round-trips), `new_client` (another browser on the same app), `tenant_factory` (signs a new Member up in a fresh client, so they own a new Organisation), `owner`, `member_factory` (adds a new signed-in Member to an Owner's Organisation with a role, through an Invite), `clock` (a `ControllableClock` installed on the app) and `join_organisation(owner, member, role)` (brings an existing Member into the Owner's Organisation through an accepted Invite Link). Each test starts with no sign-in failure counters. The test database is migrated to head once per run.

## Audit Events

- **Recording.** `app.audit.record(session, organisation_id=…, actor_id=…, action=…, target=AuditTarget(type, id), before=…, after=…)` adds an Audit Event to the caller's transaction, so the change and its event commit or roll back together. `actor_id` is `None` for events no Member caused. Actions are dotted names (`organisation.created`, the first one, is recorded at sign-up). Keys matching a secret-like pattern (`password`, `secret`, `token`, `api_key`, `credential`, `private_key`, `authorization`, `cookie`, `session`, `recovery_codes`, …) have their values replaced by `[Redacted]` at any depth before anything is stored.
- **Append-only.** Migration `0003_audit` adds triggers that refuse `UPDATE`, `DELETE` and `TRUNCATE` on `audit_events`.
- **Reading.** `GET /api/organisations/{organisation_id}/audit-events` (filters `actor_id`, `action`, `start` inclusive, `end` exclusive, both with a time zone; `page`, `page_size` up to 100; newest first) and `GET …/audit-events/facets` (the actors and actions present, for filter menus). Both are Owner-only through the `OwnerScope` dependency (`app/tenancy/policy.py`): an Editor gets `403 {"detail": "Only Owners can do this"}`, another tenant's Member 404.
- **Studio.** Organisation settings has a General tab and, for Owners only, an Audit tab (`/organisations/$organisationId/settings/audit`). Its date filters are whole UTC days, both inclusive.

## Theme

- **API** (`backend/app/theme/`). `GET /api/organisations/{organisation_id}/theme` (`getTheme`, any Member) answers the Organisation's Theme, or the default (`updated_at: null`) until an Owner saves one. `PUT …/theme` (`saveTheme`, Owners only through `OwnerScope`) replaces the whole Theme and applies at once. `GET /api/themes/fonts` (`listThemeFonts`) lists the Font Allowlist (`app/theme/fonts.py`), the default first.
- **What a Theme holds** (`app/theme/schema.py`): six Colour Tokens (`primary`, `on_primary`, `surface`, `on_surface`, `accent`, `muted`), each `{light, dark}` as `#rrggbb` (stored in lower case); `radius` (whole pixels, 0 to 24); `font` (from the allowlist); `mode` (`light`, `dark` or `auto`); `launcher_type` (`bubble` or `inline`) and `launcher_position` (`bottom-right` or `bottom-left`). Anything else is 422. Contrast is never checked by the API: it only warns, in the Studio.
- **Storage and audit.** `themes` holds at most one row per Organisation, written on the first save that changes something (migration `0007_themes`). A save locks the Organisation's row, so concurrent saves apply one after the other. Each change records `theme.updated` (target `theme/<id>`) with only what changed in `before` and `after`, nested the same way (`{"colours": {"primary": {"light": …}}}`). Saving an unchanged Theme records nothing.
- **Resolution and contrast** (`frontend/packages/ui`, `@studio/ui`). `resolveTheme(theme, scheme)` is the one pure function that turns a Theme into CSS custom properties (`--theme-primary`, `--theme-on-primary`, `--theme-surface`, `--theme-on-surface`, `--theme-accent`, `--theme-muted`, `--theme-radius`, `--theme-font-family`) for the light or dark scheme. `themeStylesheet(theme, selector)` builds a stylesheet from it, with a `prefers-color-scheme: dark` block in auto mode, for the widget to inline. `contrastWarnings(theme)` checks, with the WCAG relative-luminance formula, on-primary on primary, on-surface on surface and muted on surface against 4.5:1, and accent on surface against 3:1, in each scheme the mode shows.
- **UI primitives** (`@studio/ui`): `ThemeScope` (sets the custom properties), `ChatWindow`, `MessageBubble`, `MutedText`, `AccentLink`, `Composer` and `Launcher`. They read the Theme only through the custom properties, so the Studio preview and the widget render the same components.
- **Studio.** Organisation settings has a Theme tab for every Member (`settings/ThemePage.tsx`): a form (hex field and colour picker per Colour Token and scheme, radius, font, mode, launcher and position), the Contrast Warnings, and a live preview built from the primitives that follows every edit before it is saved. In auto mode the preview can show either scheme. Editors see it all read-only, without Save.

## MFA and envelope encryption

- **TOTP MFA** (`backend/app/auth/mfa.py`, routes in `app/auth/mfa_api.py` under `/api/auth/mfa`). RFC 6238, SHA-1, six digits, 30-second steps, accepted one step either side. Enrolment (`POST /enrolment`) returns the secret, an `otpauth://` URI and a QR code (an SVG data URI); MFA is on only after `POST /enrolment/confirm` checks a code, which returns ten Recovery Codes once. Each accepted code's step is stored, so a code works once. Recovery Codes (`XXXX-XXXX-XXXX-XXXX`, 80 random bits) are stored as SHA-256 hashes and are typed case-, dash- and space-insensitively. `POST /disable` needs the password and a code; `POST /recovery-codes` replaces the codes for a code.
- **MFA pending.** For a Member with MFA, a correct password answers `202 {"mfa_required": true}` and sets `studio_mfa_pending` (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/api/auth`) instead of a session. Redis keeps `mfa-pending:<sha256 of the token>` for `MFA_PENDING_TTL_SECONDS` (default 300). `POST /api/auth/mfa/verify` with an authenticator or Recovery Code then starts the session; five wrong codes end the pending sign-in (`401 {"detail": "Sign in again"}`).
- **Audit Events.** Enrolling, disabling, using a Recovery Code and replacing Recovery Codes are recorded with `app.audit.service.record`, once in each Organisation the Member belongs to (`mfa.enrolled`, `mfa.disabled`, `mfa.recovery_code_used`, `mfa.recovery_codes_replaced`).
- **Require MFA policy** (`backend/app/tenancy/mfa_policy.py`; column `organisations.require_mfa`). `PUT /api/organisations/{organisation_id}/mfa-policy {"require_mfa": bool}` (`setMfaPolicy`, Owners only) answers with the Organisation; turning it on without MFA of your own is `409`. Setting the value it already has records nothing; a change records `organisation.mfa_policy_changed` (target `organisation/<id>`, before/after `{"require_mfa": …}`). While it is on, `RequireRole` (`app/tenancy/policy.py`) answers `403 {"detail": "This Organisation requires MFA. Turn on MFA for your account to continue."}` on every route of that Organisation to a Member without MFA, before the role check; `/api/auth/*` stays open so they can enrol. `/api/auth/me` reports `member.mfa_enabled` and each Organisation's `mfa_required`; the Studio's Organisation shell uses them to send such a Member to the Security page, which names the Organisations that require MFA. `POST /api/auth/mfa/disable` answers `409` naming the Organisations while any of the Member's Organisations requires MFA, before the password or code is checked.
- **Envelope encryption** (`backend/app/crypto/`). `EnvelopeEncryption.seal(plaintext, context=...)` and `.open(sealed, context=...)`: AES-256-GCM with a fresh data key per record, the data key wrapped by a `KeyWrapper`. Version 1 records are `0x01 | key-ID length | key ID | wrapped-key length (2 bytes) | wrapped key | nonce (12) | ciphertext and tag`; everything before the nonce and the caller's `context` (for TOTP, the Member's ID) are authenticated, so tampering, truncation or moving a record to another Member fails with `EnvelopeError`. The local static-key wrapper takes `LOCAL_KEY_WRAPPER_KEY` (32 bytes, base64; `openssl rand -base64 32`); `docker-compose.yml` has a development default. With `KEY_WRAPPER=kms`, `KmsKeyWrapper` (`app/crypto/kms_key_wrapper.py`) wraps data keys with the KMS key `KMS_KEY_ID` (ARN or alias; `KMS_REGION` optional) under the encryption context `purpose=rag-agent-studio/envelope-data-key`. Records name their key as `kms:<arn>`, so records sealed under an earlier KMS key still open; a record sealed by the local wrapper is refused without calling KMS. It is tested with botocore's `Stubber`.
- **Clock.** Code checks use the clock port (`app/core/clock.py`). Tests replace it with `ControllableClock` through the `clock` fixture.

## Provider Credentials

- **Model and storage** (`backend/app/credentials/`, table `provider_credentials`, migration `0007_provider_credentials`). A credential has a name (unique in its Organisation), provider, auth kind, sealed secret, region (Bedrock only, ticket 02-02), masked suffix (the key's last 4 characters), capabilities, check status (`passed`/`failed`) with the typed failure, last-checked time and the time its secret was set. The secret is sealed with the envelope module under the context `provider-credential:<organisation id>:<credential id>`, so a sealed value moved to another row or Organisation doesn't open.
- **Capability registry** (`app/credentials/registry.py`). Each provider's auth kinds and models per capability (`chat`, `embeddings`, `rerank`), in code. `GET /api/providers` (any signed-in Member) serves it.
- **Credential verifier** (`app/credentials/verifier.py`). The port is `check(provider, api_key) -> CheckResult`, which passes or fails with a `CheckFailure`: `invalid_key`, `missing_model_access`, `quota_exceeded` or `provider_unreachable`. `CREDENTIAL_VERIFIER=live` (the default) uses `HttpCredentialVerifier`: Anthropic and OpenAI list models, Voyage embeds one short string; 401 is `invalid_key`, 403/404 `missing_model_access`, 429 `quota_exceeded`, anything else or a network error `provider_unreachable`. Its unit tests use `httpx.MockTransport` with recorded answer shapes, never a real provider. `CREDENTIAL_VERIFIER=fake` (tests and `docker compose`) passes every key except one starting `fake-fail-<reason>`, which fails with that reason. Tests can also put their own verifier on `app.state.credential_verifier`.
- **Routes** under `/api/organisations/{organisation_id}/credentials`: `GET` (list, by name) and `GET /{credential_id}` for every Member; Owner-only `POST` (add: `{name, provider: anthropic|openai|voyage, api_key, capabilities?}`), `POST /{id}/check` (re-check the stored key), `POST /{id}/rotate` (`{api_key}`; the ID stays) and `DELETE /{id}`. A failed check answers `400 {"detail", "reason"}` and stores nothing (on rotation, the old key stays). A malformed key (not 8–512 characters, or with whitespace) answers 422 without echoing it. A taken name answers 409.
- **References.** `app.state.credential_references` is a `ReferenceRegistry`. A consumer (a Project's Embedding Model, an Agent's model, a reranker, a guardrail classifier) registers an async source `(session, scope, credential_id) -> [CredentialReference(kind, id, name)]` when the app is built. `DELETE` answers `409 {"detail", "references": [...]}` while any source reports a reference. The credentials module never imports its consumers.
- **No secret out.** No response model has a secret field; `tests/integration/test_no_secret_in_responses.py` walks every response schema in the OpenAPI document (the TOTP enrolment secret is the one listed exception) and checks that no credential route, failure or Audit Event answer contains any part of a key beyond its last 4 characters.
- **Audit Events.** `credential.created`, `credential.checked`, `credential.check_failed` (also for a failed add, with no target ID, and a failed rotation, with the attempted key's suffix), `credential.rotated` (before/after suffix) and `credential.deleted`. None carries a key.
- **Studio.** Organisation settings has a Credentials tab for every Member (`/organisations/$organisationId/settings/credentials`). Owners add credentials (every provider in the registry), re-check, rotate (API keys only) and delete them; Editors only see the list.
- **Bedrock (ticket 02-02).** `POST …/credentials/bedrock` takes either `{auth_kind: "aws_role", name, role_arn, region, capabilities?}` (recommended: no secret stored) or `{auth_kind: "aws_access_keys", name, access_key_id, secret_access_key, region, capabilities?}`. Owner-only `GET /api/organisations/{organisation_id}/bedrock-setup` returns the Organisation's external ID (generated on first use, table `aws_external_ids`, migration `0009_bedrock_credentials`), the platform principal (`BEDROCK_PLATFORM_PRINCIPAL`) and the trust and permissions policies to paste, as pretty-printed JSON. The verifier port gains `check_bedrock(BedrockAccess)`; the live one (`app/credentials/bedrock_verifier.py`) assumes the role with STS in `BEDROCK_STS_REGION` (or calls `GetCallerIdentity` with the keys), then calls Bedrock `GetFoundationModelAvailability` for a model of the credential's first capability in its region. Failures: `role_not_assumable`, `invalid_key` (keys), `missing_model_access`, `wrong_region` (model not offered, or no Bedrock endpoint, in the region), `quota_exceeded`, `provider_unreachable`. `AssumedRoleSessions` caches sessions per role and external ID until `BEDROCK_SESSION_REFRESH_SECONDS` (default 300) before expiry, on the injected clock. Its tests use botocore `Stubber`; no AWS account is used. The fake verifier fails a role whose name, or a secret access key that, starts `fake-fail-<reason>`. Bedrock credentials can't be rotated with an API key (422); add a new one and delete the old.

## Model gateway and Default Model

- **Model gateway** (`backend/app/gateway/`). `ModelGateway.chat_model(credential, model)`, `.embedder(credential, model)` and `.reranker(credential, model)` are the one factory for model clients. Each checks that the credential has the capability and that its provider offers the model for it (`ModelUnavailableError`: `CapabilityNotGrantedError` or `ModelNotOfferedError`), opens the sealed secret, and asks its `ModelAdapters` to build the client. Chat models are Pydantic AI `Model`s, embedders Pydantic AI `EmbeddingModel`s, and rerankers this project's `Reranker` port (`rerank(query, documents, top_k=None) -> [RankedDocument(index, score)]`).
  - `MODEL_GATEWAY=live` (the default) uses `LiveModelAdapters`: Pydantic AI's `AnthropicModel`, `OpenAIChatModel` and `OpenAIEmbeddingModel`, plus thin `httpx2` clients for Voyage embeddings and reranking. They share `app.state.model_http` (`MODEL_TIMEOUT_SECONDS`, default 120). Bedrock credentials are refused with `UnsupportedCredentialError` until ticket 02-02 adds their clients here. Its tests use an `httpx2.MockTransport` with recorded answer shapes; no provider is called.
  - `MODEL_GATEWAY=fake` (tests and `docker compose`) uses `FakeModelAdapters`: a Pydantic AI `TestModel` that replies `Fake reply from <provider>:<model>.`, a hash-based embedder (16-dimension unit vectors, the same for the same text) and a word-overlap reranker. A test injects scripted replies with `FakeModelAdapters(chat=lambda provider, secret, model: FunctionModel(...))`, or replaces `app.state.model_gateway` outright.
- **Model lists.** `GET /api/organisations/{organisation_id}/credentials/{credential_id}/models/{capability}` (`listCredentialModels`, every Member) answers the credential's models for `chat`, `embeddings` or `rerank`: empty unless the credential has that capability.
- **Default Model** (`backend/app/default_model/`, table `default_models`, migration `0008_default_models`). `GET /api/organisations/{organisation_id}/default-model` (`getDefaultModel`, every Member) answers `{credential_id, credential_name, provider, model, model_name, updated_at}` or `null`. `PUT` (`setDefaultModel`, Owners only) takes `{credential_id, model}`; another Organisation's or an unknown credential, a credential without chat, or a model its provider doesn't offer for chat answers 422 with the reason. A change records `default_model.changed` (target `organisation/<id>`, before/after `{credential_id, credential_name, provider, model}`); choosing the current model again records nothing. `default_chat_model(session, gateway, organisation_id)` builds it through the gateway for later specs.
- **Reference.** The Default Model registers a credential-reference source when the app is built, so deleting its credential answers 409 with `{"kind": "default_model", "id": <organisation id>, "name": "Default Model (<model name>)"}`. The credential row is share-locked while the Default Model is written, and `default_models.credential_id` has a foreign key, so a concurrent delete can't leave it pointing nowhere.
- **Studio.** Organisation settings has a Models tab for every Member (`/organisations/$organisationId/settings/models`). It shows the Default Model; Owners pick a chat-capable credential, then one of its chat models. The price table is on the same tab (below).

## Price table and overrides

- **Price table** (`backend/app/pricing/price_table.json`). US dollars per million tokens for `input`, `output` and `cached_input` (cache reads), keyed by `provider` and `model`, each with an `effective_from` date (UTC midnight). Embedding and rerank models have `output` 0 and `cached_input` equal to `input`. To change a price from a date, add an entry with that date rather than editing the old one. A malformed or duplicated entry fails the migration.
- **Loaded on migrate.** Migration `0010_price_table` creates `model_prices` (platform-level, no `organisation_id`) and `price_overrides`. After every `alembic upgrade`, `migrations/env.py` calls `sync_price_table` (`app/pricing/sync.py`), which replaces the rows of `model_prices` with the file, in the migration's transaction. So `make migrate` (or the API container starting) picks up an edited file without a new migration.
- **Cost.** `app.pricing.table.cost(pricing, model, usage, at, table)` is the pure cost function: `CredentialPricing(provider, overrides)`, `TokenUsage(input_tokens, output_tokens, cached_input_tokens)` (input excludes cached), the time, and the table. Each price is the credential's override if set, else the table's entry with the latest `effective_from` not after `at`; the answer is a `Decimal` in dollars, or `None` when tokens were used at a price nobody set. `app.pricing.service.credential_cost(session, credential, model, usage, at)` loads both and calls it; cost reporting (spec 07) uses either.
- **API.** `GET /api/organisations/{organisation_id}/credentials/{credential_id}/prices` (`listCredentialPrices`, every Member) answers `{credential_id, currency: "USD", unit: "per million tokens", models: [{model, model_name, capability, platform, override, effective}]}` for every model the credential offers, with prices as decimal strings and the platform price in effect now. `PUT` (`overrideCredentialPrices`, Owners only) takes `{model, input?, output?, cached_input?}` (0 to 999999.999999, at most six decimals); a price left out or null keeps the platform's, and leaving all three out clears the override. A model the credential doesn't offer answers 422. A change records `credential.price_overridden` (target `provider_credential/<id>`, before/after `{model, input, output, cached_input}`); saving the same prices records nothing.
- **Studio.** The Models tab's Prices section shows, for a chosen credential, each model's input, output and cached input price, marking overrides with the platform price beside them. Owners override a model's prices (blank keeps the platform price) or go back to the platform prices.

## Telemetry and logs

The API, worker and Beat are traced with OpenTelemetry through the Logfire SDK (`backend/app/core/telemetry.py`). FastAPI requests, SQLAlchemy queries, Celery tasks (from the request that queues them through to the worker that runs them) and outbound `httpx` calls are instrumented.

- **Exporter.** With `LOGFIRE_TOKEN` set, spans go to Logfire (`LOGFIRE_BASE_URL` is only needed for a self-hosted Logfire). Without it they are written to stdout, one JSON object per span.
- **Scrubbing.** Every exporter receives spans after Logfire's scrubbing processor, extended for this project. Values under Message-carrying field names (`content`, `message`, `messages`, `prompt`, and `input`, where validation errors echo a request back) are redacted, and so are values under keys ending in `token` (`token`, `reset_token`; not `max_tokens` or `token_budget`), which is where Invite and reset links send their token. So are cookies, `Authorization` and API-key headers, and secret-like attributes. Request headers are captured, so these are redacted rather than simply absent. A log message whose template formats a scrubbed value is exported as the bare template.
- **Logs.** Every service writes JSON lines to stdout: `timestamp`, `level`, `logger`, `message`, `service` (`api`, `worker`, `beat` or `migrations`), any `extra` fields, `exception` when there is one, and `trace_id`/`span_id` inside a traced operation. Extra fields with sensitive names, and the task arguments and results Celery logs, are written as `[Redacted]`.
- **Entrypoints.** The API runs as `python -m app.serve`, so uvicorn's own lines are JSON too. Celery runs with `--quiet` so it skips its text banner; the one line Celery still prints outside logging is its `worker: Warm shutdown (MainProcess)` notice on SIGTERM.
